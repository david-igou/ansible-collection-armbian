U-Boot in armbian/build — a one-pass explainer

How compile.sh BOARD=… BRANCH=… turns into a specific U-Boot binary baked into an Armbian .img.xz, and why two boards on the same armbian branch can be building from completely different u-boot trees. Scoped to the rk3588 configuration shipped by armbian/build v26.2.0-trunk.844 (the ref this collection pins).

1. What armbian/build actually builds

An Armbian image is three independently-sourced pieces glued together at packaging time:

U-Boot binary
Compiled from a git tree pointed at by BOOTSOURCE / BOOTBRANCH. This is what runs from SD/eMMC/SPI at power-on, talks to DHCP/TFTP, and hands off to the kernel.
Kernel + DTB
Compiled from KERNELSOURCE / KERNELBRANCH. Separate tree, separate version cadence.
Userland rootfs
Debian/Ubuntu via debootstrap; release pinned by RELEASE= (bookworm in this repo).

This explainer is about the first piece only. The U-Boot binary is the one with PXE-first BOOT_TARGETS that this collection’s netboot invariant depends on (see architecture.md).

2. The seven variables that pick a u-boot tree

By the time compile.sh calls make on U-Boot, these seven shell variables have been resolved to concrete values. Together they fully determine the binary you get:

VariableWhat it controls
BOOTSOURCEGit remote URL of the u-boot tree (e.g. github.com/radxa/u-boot.git vs github.com/u-boot/u-boot.git).
BOOTBRANCHRef to check out: branch:<name>, tag:<name>, or commit:<sha>.
BOOTPATCHDIRDirectory under patch/u-boot/ whose .patch files are applied after checkout.
BOOTCONFIGThe defconfig argument to make, e.g. rock5b-rk3588_defconfig.
BOOTDIRDirectory name under cache/sources/ that the checkout lives in. Useful for keeping multiple u-boot trees side-by-side.
UBOOT_TARGET_MAPThe make targets and the output artifacts to capture (BL31, u-boot-rockchip.bin, etc.).
BOOT_SCENARIOHigher-level recipe (e.g. tpl-blob-atf-mainline) that prepare_boot_configuration() expands into the variables above.

The headline insight: none of these are 1:1 with the user-facing BRANCH=current|edge|vendor|legacy flag. The BRANCH flag is an Armbian-side selector that the family and board configs translate into U-Boot variables in board-specific ways. Two boards in the same family with BRANCH=edge can easily end up on two different u-boot trees.

3. How those variables get their final values

armbian/build runs a layered config-resolution pass before it touches a single source file. Each layer can override values set by an earlier one — last writer wins:

  1. Family file — config/sources/families/<family>.conf sets the family-wide defaults. For rk3588, this defaults BOOTSOURCE to the Radxa fork.
  2. Family file case $BRANCH in… arms — branch-specific overrides at family scope. For rk3588 only legacy and vendor have arms; current and edge inherit the defaults from step 1.
  3. Board file — config/boards/<board>.conf (or .csc for community-supported) sets per-board basics (BOOTCONFIG, MODULES, …) and defines hook functions — not run yet, just registered.
  4. Userpatches family overlay — userpatches/config/sources/families/<family>.conf is sourced right after the family file. Same scope, runs later, so it can override anything from step 1. This is where this collection lives.
  5. Hook cascade — armbian/build then fires named hooks in deterministic order. Hooks can mutate any of the seven variables. The relevant u-boot hooks:
    • post_family_config — once, regardless of branch.
    • post_family_config_branch_<branch> — only when BRANCH matches.
    • pre_config_uboot_target — just before make <BOOTCONFIG>; the U-Boot source tree is checked out and patched, and BOOTCONFIG/BOOTDIR are finalized. Last place to edit U-Boot source files.
    • post_config_uboot_target — after make <defconfig> but before the build. Last place to edit .config directly.

Multiple hook functions can register against the same hook name. armbian/build sorts them by an optional numeric prefix (function pre_config_uboot_target__500_foo()); functions without a prefix get an implicit 500_. Sort order is LC_ALL=C --general-numeric-sort, so __999_ reliably runs last and wins any conflicting in-tree edits.

Snippet 4 of 4 this collection · playbooks/build_image.yml (userpatches family overlay)
build_userpatches_common:
  - dest: "config/sources/families/rockchip-rk3588.conf"
    content: |
      function pre_config_uboot_target__999_pxe_first() {
          # 1. Patch the legacy `#define BOOT_TARGETS "..."` form
          declare -a t=("pxe" "dhcp" "mmc1" "mmc0" "nvme" "scsi" "usb" "spi")
          sed -i -e "s/#define BOOT_TARGETS.*/#define BOOT_TARGETS \"${t[*]}\"/" \
              include/configs/rockchip-common.h

          # 2. Force bootflow framework to enumerate PCIe at init_r time
          local defconfig="configs/${BOOTCONFIG}"
          if [[ -f "$defconfig" ]] \
             && grep -q "^CONFIG_PCI=y" "$defconfig" \
             && ! grep -q "^CONFIG_PCI_INIT_R=y" "$defconfig"; then
              echo "CONFIG_PCI_INIT_R=y" >> "$defconfig"
          fi
      }
  • This file gets written to userpatches/config/sources/families/rockchip-rk3588.conf inside the armbian/build checkout (see roles/armbian_build/tasks/apply_userpatches.yml). armbian/build sources it right after its own family file, so this adds a hook function rather than replacing the family config.
  • The __999_ numeric prefix forces this to sort last among pre_config_uboot_target hooks. rock-5b’s own board file registers pre_config_uboot_target__rock5b_patch_rockchip_common_boot_order with a default 500_ prefix that sets a vendor-preferred SD-first order; without __999_ our patch would be clobbered by Radxa’s preference.
  • The sed is a deliberate no-op on trees whose rockchip-common.h uses the X-macro BOOT_TARGET_DEVICES(func) form (Radxa’s next-dev-v2024.10). We only ship affected boards on edge (mainline), where the legacy #define form is still present.
  • The second block addresses a mainline-u-boot-specific failure: rk3588 defconfigs set CONFIG_PCI=y but not CONFIG_PCI_INIT_R=y, so PCIe NICs are not enumerated at init_r time and bootflow never sees them — TFTP requests are never made and PXE silently fails.

7. Why hooks instead of .patch files?

armbian/build does support source patches the conventional way — drop userpatches/u-boot/<BOOTPATCHDIR>/*.patch and they get applied to the checkout after fetch. The User Configurations doc spells it out: "Patches with the same file name and path in the userpatches directory tree override those in the patch directory." This collection still picks the hook-function path for the PXE-first and PCI-init-r changes. Three reasons drive that choice.

Reason 1 — conditional logic that .patch cannot express

Our __999_pxe_first hook checks $BOOTCONFIG, greps the defconfig, and only appends CONFIG_PCI_INIT_R=y when the board has CONFIG_PCI=y and doesn’t already have CONFIG_PCI_INIT_R=y. A .patch file is a diff against one specific state — it has no if. Without the gate, the change would either fail to apply on boards that don’t have CONFIG_PCI=y (no context to match) or land somewhere it shouldn’t.

Upstream uses the same gating pattern — note the [[ "${BRANCH}" != "edge" ]] && return 0 on the first line, which is impossible to express in a static diff:

Upstream armbian/build · config/boards/rock-5b.conf — defconfig changes gated by branch
function post_config_uboot_target__extra_configs_for_rock5b_mainline_environment_in_spi() {
    [[ "${BRANCH}" != "edge" ]] && return 0   # ← conditional gate

    run_host_command_logged scripts/config --enable    CONFIG_DM_PMIC_FAN53555
    run_host_command_logged scripts/config --enable    CONFIG_CMD_MISC
    run_host_command_logged scripts/config --set-val   CONFIG_ENV_IS_IN_SPI_FLASH "y"
    run_host_command_logged scripts/config --set-val   CONFIG_ENV_OFFSET          "0xc00000"
    # … ~25 more scripts/config invocations …
}
A .patch against configs/rock5b-rk3588_defconfig would always apply, regardless of branch. The hook self-gates, and scripts/config — the same tool a human runs interactively under make menuconfig — is robust to line-order changes inside the defconfig file.

Reason 2 — one file across multiple u-boot trees

Patch directories are per-tree: BOOTPATCHDIR=legacy/u-boot-radxa-rk35xx for the Radxa fork, v2026.01 for mainline rock-5b, possibly a third for some future board (see the matrix in section 5). A static .patch would need to be duplicated across every directory the family touches. The hook lives once at family-overlay scope and runs with whatever BOOTPATCHDIR the preceding hooks left in place.

This becomes load-bearing when upstream rebases. The next mainline tag (v2026.04, v2027.01, …) almost certainly shifts line numbers and context around include/configs/rockchip-common.h. A .patch generated against v2026.01 will fail to apply with error: while searching for: … at every bump until someone re-baselines it. The hook targets structural elements (a #define directive by regex, a CONFIG_ line by grep) and survives any refactor that preserves those elements.

Reason 3 — armbian/build itself uses this pattern for the same kind of change

The strongest legitimacy argument is that armbian/build’s own rock-5b config already does exactly what we do — a sed against include/configs/rockchip-common.h from a pre_config_uboot_target hook. We just need to win the ordering fight against it:

Upstream armbian/build · config/boards/rock-5b.conf — same file, same mechanism, vendor-preferred order
function pre_config_uboot_target__rock5b_patch_rockchip_common_boot_order() {
    declare -a rockchip_uboot_targets=("mmc1" "nvme" "mmc0" "scsi" "usb" "pxe" "dhcp" "spi")
    display_alert "u-boot for ${BOARD}/${BRANCH}" \
        "u-boot: adjust boot order to '${rockchip_uboot_targets[*]}'" "info"
    sed -i -e "s/#define BOOT_TARGETS.*/#define BOOT_TARGETS \"${rockchip_uboot_targets[*]}\"/" \
        include/configs/rockchip-common.h
    regular_git diff -u include/configs/rockchip-common.h || true
}
  • Identical sed pattern against the identical file as our __999_pxe_first. Vendor’s array puts mmc1 first (SD-first); ours puts pxe first. Whichever hook runs last wins the #define line.
  • This hook has no numeric prefix, so it gets armbian/build’s implicit 500_. Our __999_ sorts after it and wins — that ordering is only available because we’re a hook, not a patch. A .patch file applies once at fetch+patch time, then this in-tree hook would sed right over our change at pre_config_uboot_target time. Patches have no notion of “run after that other hook.”

Workflow example: an upstream u-boot bump

Concrete contrast. Suppose armbian/build bumps rock-5b’s BOOTBRANCH from tag:v2026.01 to tag:v2026.07, and along the way upstream adds a comment block above BOOT_TARGETS: 

--- a/include/configs/rockchip-common.h  (v2026.01)
+++ b/include/configs/rockchip-common.h  (v2026.07)
@@ -22,6 +22,9 @@
 #include <env/distro/sd_mmc.h>
 #include <env/distro/usb.h>

+/* Default boot order; boards may override via pre_config_uboot_target. */
+/* See arch/arm/mach-rockchip/board.c for runtime override hooks.       */
+
 #define BOOT_TARGETS "mmc1 mmc0 nvme scsi usb pxe dhcp spi"

Our hook still works — it matches by regex on the #define line and the new comment context is irrelevant: 

sed -i -e "s/#define BOOT_TARGETS.*/#define BOOT_TARGETS \"${t[*]}\"/" \
    include/configs/rockchip-common.h

A hypothetical .patch file generated against v2026.01 — the one we’d have shipped if we’d gone that route: 

--- a/include/configs/rockchip-common.h
+++ b/include/configs/rockchip-common.h
@@ -22,5 +22,5 @@
 #include <env/distro/sd_mmc.h>
 #include <env/distro/usb.h>

-#define BOOT_TARGETS "mmc1 mmc0 nvme scsi usb pxe dhcp spi"
+#define BOOT_TARGETS "pxe dhcp mmc1 mmc0 nvme scsi usb spi"

…fails with error: while searching for: … because the context around line 22 changed. armbian/build aborts the build. Re-baselining the patch is fresh work for every upstream bump, across every BOOTPATCHDIR the family uses.

Workflow example: adding a third rk3588 board

A future nanopc-t6 (another rk3588 board with a PCIe NIC) joins the family. Its BOOTPATCHDIR is whatever armbian/build picks for it — almost certainly different from v2026.01. With the hook approach, we add the board to vars/boards.yml and build_userpatches_common applies as-is. With the patch approach, we’d need to copy the patch into the new BOOTPATCHDIR, rebase against that tree’s exact source, and maintain N copies thereafter.

When .patch files are the right tool

Hooks aren’t a universal replacement. Use a .patch file when:

  • The change is intended to be upstreamable. An honest diff against a specific upstream commit is what git send-email produces. Issue #59’s option D1 (patch arch/arm/mach-rockchip/board.c to honour a DT MAC over the chip-hashed MAC) is a textbook example — it’s a bug fix that should go upstream, not a structural override.
  • The change is large or touches many files. A 200-line multi-file change is far more readable as a unified diff than as a sed/grep incantation, and tooling (review, three-way merge) understands diffs natively.
  • The target file is stable across the trees you build. If a file basically never moves between upstream versions, the context-fragility argument doesn’t apply, and a patch is simpler than a hook doing the same edit.

8. Fixing rock-5b’s autonomous-PXE problem

Issue #59 documents three stacked failure layers on rock-5b. Each has to be cleared for autonomous cold-boot PXE to succeed — fixing only some leaves you with a still-not-booting board and a misleading symptom. The first one (Layer 0) is already shipped in this collection; Layers 1 and 2 are what Approaches A and B (below) are about.

8.1 The three failure layers

Layer Symptom on the wire Root cause This collection ships a fix?
0 — NIC not enumerated bootflow scan finds zero ethernet bootflows; no DHCP request leaves the board at all. tcpdump on the switch port is silent. Mainline rk3588 defconfigs set CONFIG_PCI=y but not CONFIG_PCI_INIT_R=y. The PCI bus is enumerated lazily, so at bootflow scan time the RTL8125 isn’t a bootdev. Yes — __999_pxe_first family hook appends CONFIG_PCI_INIT_R=y to the defconfig when CONFIG_PCI=y is set (commit bd44240, in playbooks/build_image.yml).
1 — wrong MAC on DHCP DHCP DISCOVER goes out, but with a 0a:1e:94:81:70:c8-shaped MAC that rb5009’s static reservation doesn’t recognise. Either no lease or a dynamic lease in the wrong subnet; TFTP fetches the wrong (or no) pxelinux.cfg/01-<MAC>. rockchip_setup_macaddr() (in arch/arm/mach-rockchip/board.c) SHA-256-hashes the chip’s cpuid# into a locally-administered MAC and writes it over the DT MAC at misc_init_r time, unless env_get("ethaddr") already returns a value. No — Approach A or Approach B below.
2 — PXE addresses vanish DHCP succeeds (with the right MAC) and TFTP fetches the correct pxelinux.cfg, but bootflow scan silently skips the ethernet bootdev. No TFTP fetch of kernel / initrd / dtb follows. CONFIG_ENV_IS_IN_SPI_FLASH=y means a CRC-valid SPI env replaces the compile-time default_environment[] on every boot. PXE-required vars (pxefile_addr_r, kernel_addr_r, …) only exist in compile-time defaults, so they vanish from runtime env on any successful fw_setenv. No — Approach B clears it in one go; Approach A alone doesn’t, and needs a companion defconfig hook adding CONFIG_EXTRA_ENV_SETTINGS=….

Layer 0 is a strict prerequisite — without it the NIC isn’t a bootdev, so neither Approach A nor Approach B is even relevant. Approaches A and B are alternative ways to clear Layer 1; Approach B also clears Layer 2 in the same playbook run, while Approach A needs a Layer-2 companion fix to be complete on its own.

8.2 Status in u-boot v2026.04

Mainline u-boot’s v2026.04 release (April 2026, the successor to the v2026.01 tag this collection currently pins for rock-5b) does not clear any of the three layers:

Layerv2026.04 statusEvidence
0 — CONFIG_PCI_INIT_R Not fixed configs/rock5b-rk3588_defconfig still does not set it. In drivers/pci/Kconfig the symbol is only selected by PCIE_ECAM_SYNQUACER and implyd by PCIE_APPLE — neither in the rk3588 chain. PCIE_DW_ROCKCHIP=y (now explicit in the v2026.04 defconfig) does not select or imply it.
1 — rockchip_setup_macaddr Not fixed Function body in arch/arm/mach-rockchip/board.c is byte-identical to v2026.01 — still SHA-256-hashes cpuid# whenever env_get("ethaddr") returns NULL, with no DT-MAC check. No commit in the v2026.01..v2026.04 window touches this function.
2 — SPI env replaces defaults Not fixed U-Boot env subsystem semantics unchanged (and load-bearing, not a bug). Rock-5b’s v2026.04 defconfig still lacks CONFIG_EXTRA_ENV_SETTINGS entries for the PXE address vars.

Bumping rock-5b’s BOOTBRANCH from tag:v2026.01 to tag:v2026.04 is otherwise a free move — the defconfig was regenerated via make savedefconfig (135 → 97 lines), and CONFIG_OF_LIST="rockchip/rk3588-rock-5b rockchip/rk3588-rock-5b-plus rockchip/rk3588-rock-5t" now lets one build serve three boards via runtime DT selection. BOOT_TARGETS in include/configs/rockchip-common.h is still the legacy #define form ("mmc1 mmc0 nvme scsi usb pxe dhcp spi"), so our __999_pxe_first sed still applies cleanly. But none of the three workarounds can be retired.

Adjacent upstream pattern worth knowing. Commit b8ff4be (rk3288 tinker, 2024-11) addresses the same MAC problem on a sibling board by reading the MAC from EEPROM in rockchip_early_misc_init_r() — which runs before rockchip_setup_macaddr(). The early hook stuffs ethaddr into env, then the chip-hash function’s env_get("ethaddr") → return short-circuits. This is the canonical upstreamable shape for the Layer 1 fix: read the DT MAC in an early_misc_init_r hook rather than patch the chip-hash function. Maintainers have already accepted this pattern for tinker, so a rock-5b version is likely more reviewable on the u-boot mailing list than a direct patch to rockchip_setup_macaddr.

8.4 Two approaches to clear Layers 1 (and 2)

Two control surfaces are available: change the U-Boot binary that boots out of SD/SPI, or change the SPI env contents that already-booted U-Boot loads. Both fixes follow the same shape — Mechanism · Manual workflow · Automation lift · Trade-offs — so the comparison at the end is apples-to-apples. Both assume Layer 0 (Section 8.1) is already in place — which it is in this collection’s shipped image.

Approach A — Build-time fix via userpatches (.patch file)

Mechanism. Drop a unified diff under userpatches/u-boot/v2026.01/ that modifies arch/arm/mach-rockchip/board.c so rockchip_setup_macaddr() honours a valid DT-supplied MAC and returns before the chip-hash path runs. This is the section 7 “when patches are the right tool” case — an upstreamable bug fix against a specific upstream commit, exactly what git send-email would produce.

Manual workflow. What an operator types if they weren’t using this collection’s automation:

Approach A — manual operator-driven, against an armbian/build checkout

Approach B — Runtime fix via SPI fw_setenv

Mechanism. Boot the board once from SD into Armbian, then write the required vars into the SPI env directly using fw_setenv (the Linux-side counterpart to U-Boot’s setenv + saveenv). The next cold boot reads the updated env from SPI, U-Boot now has ethaddr in env so rockchip_setup_macaddr short-circuits, and the PXE address vars are present so bootflow scan enumerates the ethernet bootdev.

Automation lift. A new playbook that wraps the same commands with idempotency, per-host MAC lookup from inventory, and a backup-before-write safety:

Approach B — automated this collection · proposed playbooks/persist_uboot_env.yml

      become: true

      become: true

        creates: "/var/backups/uboot-env-{{ ansible_date_time.iso8601_basic_short }}.bak"

    - name: Read each var
      become: true
      ansible.builtin.command:
        cmd: "fw_printenv -n {{ item.key }}"
      register: _current
      changed_when: false
      failed_when: false
      loop: "{{ uboot_env_vars | dict2items }}"
      loop_control: { label: "{{ item.key }}" }

      become: true

      when: item.1.stdout | default('') != item.0.value
      loop: "{{ uboot_env_vars | dict2items | zip(_current.results) | list }}"
      loop_control: { label: "{{ item.0.key }}" }

  handlers:
    - name: Cold-cycle the board
      ansible.builtin.include_role:
        name: routeros_poe
      vars:
        poe_action: cycle
  • Per-board board_mac comes from inventory — same hostvar that drives pxelinux.cfg/01-<mac>, so the SPI env and the rb5009 TFTP layout can’t drift apart.
  • Read-then-set means re-running the playbook is cheap and idempotent; only drift triggers a fw_setenv and the cold-cycle handler.
  • Snapshot file gives the operator a recovery hatch: the worst fw_setenv botch can be undone by booting a recovery image and writing the saved env back.
  • Cold cycle (PoE off → on) via the existing routeros_poe role — warm reboot can skip re-reading SPI env on some RK3588 boot ROMs.

Trade-offs.

  • + One image serves any rock-5b. No per-MAC rebuild; bootstrap once with the stock edge image, then converge env state.
  • + Fast iteration: change a value, re-run the playbook, cold-cycle. Seconds, not the ∼30–60 min build + SD-reflash of Approach A.
  • + Per-board state lives in inventory, which is where every other per-board fact (MAC, PoE port, DTB) already lives — no new control plane.
  • − Requires the board to boot to Linux first. If U-Boot can’t reach an init system (SD-controller flake, PSU sag, see architecture.md’s signatures #1–#3), Approach B can’t be applied. Approach A is robust to this because the fix lives in the U-Boot binary itself.
  • − SPI env can be corrupted by a botched write. Mitigated by the pre-write snapshot, but recovery still requires an SD boot with a matching /etc/fw_env.config.
  • − State is host-local. Re-image a board and the env reverts to whatever the U-Boot binary’s defaults are — the playbook must be re-run. No problem if you treat it as a convergence loop, but it isn’t a one-shot.

8.5 Where U-Boot gets a MAC — and why rockchip_setup_macaddr always wins

Approach A’s patch assumes U-Boot has somewhere else to source a MAC from once rockchip_setup_macaddr steps aside. That assumption is correct, but seeing why requires walking the actual U-Boot resolution chain. It lives in net/eth-uclass.c::eth_post_probe() and fires once per Ethernet device the first time it’s probed (during bootflow scan, dhcp, eth list, …):

Upstream u-boot v2026.01 · net/eth-uclass.c — eth_post_probe(), abridged for the priority chain
static int eth_post_probe(struct udevice *dev)
{
    struct eth_pdata *pdata = dev_get_plat(dev);
    unsigned char env_enetaddr[ARP_HLEN];
    char *source = "DT";

    /* 1. Try DT: mac-address / local-mac-address property, or "mac-address"
     *    nvmem cell (typically OTP fuses). */
    if (!eth_dev_get_mac_address(dev, pdata->enetaddr) ||
        !is_valid_ethaddr(pdata->enetaddr)) {

        /* 2. Try the NIC's own EEPROM via the driver's read_rom_hwaddr op. */
        if (eth_get_ops(dev)->read_rom_hwaddr) {
            if (!eth_get_ops(dev)->read_rom_hwaddr(dev))
                source = "ROM";
        }
    }

    /* 3. Read the env var corresponding to this NIC's index (eth0 -> ethaddr,
     *    eth1 -> eth1addr, ...). */
    eth_env_get_enetaddr_by_index("eth", dev_seq(dev), env_enetaddr);
    if (!is_zero_ethaddr(env_enetaddr)) {
        if (memcmp(pdata->enetaddr, env_enetaddr, ARP_HLEN)) {
            printf("\nWarning: %s MAC addresses don't match:\n", dev->name);
            printf("Address in %s is\t\t%pM\n",      source, pdata->enetaddr);
            printf("Address in environment is\t%pM\n", env_enetaddr);
        }
        /* env always overrides DT/ROM */
        memcpy(pdata->enetaddr, env_enetaddr, ARP_HLEN);
    } else if (is_valid_ethaddr(pdata->enetaddr)) {
        /* env was empty; save the DT/ROM MAC to env so future boots see it. */
        eth_env_set_enetaddr_by_index("eth", dev_seq(dev), pdata->enetaddr);
    } else {
#ifdef CONFIG_NET_RANDOM_ETHADDR
        net_random_ethaddr(pdata->enetaddr);
        eth_env_set_enetaddr_by_index("eth", dev_seq(dev), pdata->enetaddr);
#else
        return -EINVAL;
#endif
    }
    eth_write_hwaddr(dev);   /* push final MAC into the NIC's hardware register */
    return 0;
}
Priority: env > (DT || ROM) > random > error. If env has anything for this NIC, env wins — the warning prints indicate U-Boot noticed the mismatch and chose env anyway. This is the rule rockchip_setup_macaddr exploits: pre-populate env, and every NIC’s DT/ROM MAC gets silently overridden.

The DT step (step 1 above) is itself a multi-source chain. Both standard DT properties and nvmem cells (OTP fuses) count as “DT” for priority purposes:

Upstream u-boot v2026.01 · net/eth-uclass.c — eth_dev_get_mac_address()
static bool eth_dev_get_mac_address(struct udevice *dev, u8 mac[ARP_HLEN])
{
#if CONFIG_IS_ENABLED(OF_CONTROL)
    const uint8_t *p;
    struct nvmem_cell mac_cell;

    /* 1a. Standard DT properties on the ethernet node. */
    p = dev_read_u8_array_ptr(dev, "mac-address",       ARP_HLEN);
    if (!p)
        p = dev_read_u8_array_ptr(dev, "local-mac-address", ARP_HLEN);
    if (p) { memcpy(mac, p, ARP_HLEN); return true; }

    /* 1b. nvmem cell named "mac-address" — typically OTP fuses linked
     *     via a nvmem-cells / nvmem-cell-names pair on the ethernet node. */
    if (nvmem_cell_get_by_name(dev, "mac-address", &mac_cell)) return false;
    return !nvmem_cell_read(&mac_cell, mac, ARP_HLEN);
#else
    return false;
#endif
}

And the env helpers compose to index-keyed env var names — ethaddr for index 0, eth1addr for index 1 (not eth0addr):

Upstream u-boot v2026.01 · net/eth_common.c
int eth_env_get_enetaddr_by_index(const char *base_name, int index, uchar *enetaddr)
{
    char enetvar[32];
    sprintf(enetvar, index ? "%s%daddr" : "%saddr", base_name, index);
    return eth_env_get_enetaddr(enetvar, enetaddr);
}

int eth_env_set_enetaddr_by_index(const char *base_name, int index, uchar *enetaddr)
{
    char enetvar[32];
    sprintf(enetvar, index ? "%s%daddr" : "%saddr", base_name, index);
    return eth_env_set_enetaddr(enetvar, enetaddr);
}

The Rockchip wrinkle: rockchip_setup_macaddr runs at misc_init_r — which fires before any network activity, so before any eth_post_probe ever runs. By the time the first bootflow scan triggers Ethernet probing, env already has the chip-hash MAC, and the “env always wins” rule does the rest:

Upstream u-boot v2026.01 · arch/arm/mach-rockchip/board.c — full body of rockchip_setup_macaddr()
int rockchip_setup_macaddr(void)
{
#if CONFIG_IS_ENABLED(HASH) && CONFIG_IS_ENABLED(SHA256)
    const char *cpuid = env_get("cpuid#");      /* SoC-unique, OTP-derived string */
    u8 hash[SHA256_SUM_LEN];
    int size = sizeof(hash);
    u8 mac_addr[6];

    if (env_get("ethaddr"))                      /* short-circuit if env already set */
        return 0;
    if (!cpuid) return -1;

    hash_block("sha256", (void *)cpuid, strlen(cpuid), hash, &size);
    memcpy(mac_addr, hash, 6);
    mac_addr[0] &= 0xfe;                         /* clear multicast bit                  */
    mac_addr[0] |= 0x02;                         /* set locally-administered bit (IEEE)  */

    eth_env_set_enetaddr("ethaddr",  mac_addr);
    mac_addr[5] ^= 0x01;                         /* derive eth1addr by xor'ing last byte */
    eth_env_set_enetaddr("eth1addr", mac_addr);
#endif
    return 0;
}
This is why Approach A’s patch is upstream of env_get rather than below it — once ethaddr lands in env, every NIC on the board will see env override its DT or ROM MAC, with no way for eth_post_probe to know the env value was synthetic.

Why this looks PCIe-specific (but isn’t)

Both rock-5b and orangepi5pro run rockchip_setup_macaddr, and both end up with chip-hash MACs on the wire. The asymmetry isn’t in U-Boot — it’s in how visible the override is to the operator setting up DHCP:

rock-5b (RTL8125 over PCIe)OPi5Pro (GMAC on SoC)
Hardware MAC source Real factory MAC programmed into the RTL8125’s own EEPROM (Realtek 00:e0:4c OUI, printed on the PCB sticker, surfaces via the driver’s read_rom_hwaddr op) None — the GMAC controller is a bare SoC block with no EEPROM. The chip-hash IS the only stable identity available
What the operator expects The sticker MAC. DHCP reservation is registered against it on day one Whatever ip link show reported after first boot — which is whatever rockchip_setup_macaddr produced. The operator never had a sticker MAC to compare against
Effect of the chip-hash override Sticker MAC and on-the-wire MAC don’t match → reservation never hits → DHCP gives a dynamic lease (or none) → PXE fails Self-consistent: the chip-hash MAC was registered in DHCP from day one; nothing to mismatch. PXE works

So the earlier shorthand “GMAC boards sidestep this” is right for the PCI-enumeration half (gotcha #6 in section 9: GMAC isn’t on the PCI bus, so CONFIG_PCI_INIT_R doesn’t matter for it) but misleading for the MAC half. GMAC boards don’t sidestep rockchip_setup_macaddr — they just don’t notice it, because they had no competing identity for the chip-hash to step on. The bug is symmetric; the visibility is asymmetric.

Net-net for Approach A: a clean upstreamable fix needs to handle both cases. Honour a DT-supplied MAC if present (the nvmem-cells = <&cpu_id> form is the upstream-canonical hook for “board has an OTP MAC slot”), and otherwise fall through to the chip-hash so OPi5Pro-class boards (no other MAC source) keep the stable identity they already had.

8.6 Layer 2 in code — CFG_EXTRA_ENV_SETTINGS and the SPI-replacement trap

Approach A clears Layer 1 (MAC). Layer 2 (the missing PXE address vars — pxefile_addr_r, kernel_addr_r, ramdisk_addr_r, fdt_addr_r, scriptaddr) is a separate problem. Its mechanism is CFG_EXTRA_ENV_SETTINGS — the string baked into u-boot.bin that becomes the runtime env when no saved env is available. (Older docs and the U-Boot codebase pre-v2022.07 spell it CONFIG_EXTRA_ENV_SETTINGS; the CONFIG_→CFG_ rename was a tree-wide mechanical change. Both spellings still appear in third-party Kconfig help text and Stack Overflow answers.) Two mechanisms produce it:

Form 1 — C preprocessor macro in the board header file

Sketch u-boot · include/configs/rock5b-rk3588.h — what would need adding for Layer 2 coverage from defaults
#define CFG_EXTRA_ENV_SETTINGS                       \
    "fdt_high=0xffffffffffffffff\0"                  \
    "initrd_high=0xffffffffffffffff\0"               \
    "fdtfile=rockchip/rk3588-rock-5b.dtb\0"          \
    "kernel_addr_r=0x02080000\0"                     \
    "fdt_addr_r=0x08000000\0"                        \
    "ramdisk_addr_r=0x06000000\0"                    \
    "scriptaddr=0x00c00000\0"                        \
    "pxefile_addr_r=0x00500000\0"                    \
    "bootmeths=pxe extlinux script efi\0"
The macro expands to a single null-separated string — the \0 between entries are concatenated by the C preprocessor into literal NUL bytes. U-Boot’s env subsystem walks it at boot, parses each var=val chunk, and that becomes the default env. The double-quoted form is mandatory; the trailing \0 on each line is what makes the parser stop at each chunk boundary.

Form 2 — Kconfig + external text file (modern)

Sketch u-boot · defconfig + env.txt — same content, Kconfig-driven
# configs/rock5b-rk3588_defconfig (additions)
CONFIG_USE_DEFAULT_ENV_FILE=y
CONFIG_DEFAULT_ENV_FILE="board/rockchip/rock-5b/env.txt"
# board/rockchip/rock-5b/env.txt
fdt_high=0xffffffffffffffff
initrd_high=0xffffffffffffffff
fdtfile=rockchip/rk3588-rock-5b.dtb
kernel_addr_r=0x02080000
fdt_addr_r=0x08000000
ramdisk_addr_r=0x06000000
scriptaddr=0x00c00000
pxefile_addr_r=0x00500000
bootmeths=pxe extlinux script efi
Same effect — a string baked into u-boot.bin. Newline-separated in the text file; U-Boot converts to null-separated at build time. The text file form is what mainline u-boot is moving toward (introduced around v2022.07, widely adopted by 2024); it’s easier to diff, easier to template, and doesn’t require touching a C header.

How this collection would set it via a build-time hook

A new pre_config_uboot_target hook in the same family overlay that already carries __999_pxe_first:

Sketch this collection · playbooks/build_image.yml — proposed Layer-2 hook
build_userpatches_common:
  - dest: "config/sources/families/rockchip-rk3588.conf"
    content: |
      function pre_config_uboot_target__999_pxe_first() { ... }   # existing

      # New: ensure PXE address vars are in the compile-time default env.
      function pre_config_uboot_target__998_pxe_addrs_in_default_env() {
          local defconfig="configs/${BOOTCONFIG}"
          [[ -f "$defconfig" ]] || return 0

          # Per-board env file under board/rockchip//
          local env_file="board/rockchip/${BOARD}/env-armbian-netboot.txt"
          mkdir -p "$(dirname "$env_file")"
          cat > "$env_file" <<EOF
kernel_addr_r=0x02080000
fdt_addr_r=0x08000000
ramdisk_addr_r=0x06000000
scriptaddr=0x00c00000
pxefile_addr_r=0x00500000
bootmeths=pxe extlinux script efi
EOF

          # Wire the file into the defconfig (idempotent — second build is a no-op)
          grep -q "^CONFIG_USE_DEFAULT_ENV_FILE=y" "$defconfig" \
              || echo "CONFIG_USE_DEFAULT_ENV_FILE=y" >> "$defconfig"
          grep -q "^CONFIG_DEFAULT_ENV_FILE=" "$defconfig" \
              || echo "CONFIG_DEFAULT_ENV_FILE=\"$env_file\"" >> "$defconfig"
      }
  • Numeric prefix __998_ sorts before __999_pxe_first; the two hooks are independent (one touches the defconfig and an env file, the other touches rockchip-common.h) but the ordering keeps the family-overlay diff easy to read.
  • Idempotent grep -q || echo means re-running the build doesn’t accumulate duplicate defconfig lines.
  • This hook is generic across rk3588 boards: any board that goes through the rk3588 family overlay gets the same default env. Per-board values (fdtfile) come from rock-5b.conf’s own post_family_config_branch_edge hook setting BOOTCONFIG="rock5b-rk3588_defconfig" upstream of this, so the defconfig that gets edited is already board-specific.

Why this isn’t sufficient on its own

Gotcha #7 (section 9) flags it briefly; here’s the full mechanism. A CRC-valid SPI env replaces the defaults entirely on env_load. The exact failure sequence after writing the hook above:

  1. First boot, fresh SD-flash: SPI is empty (bad CRC) → env_load falls back to defaults → runtime env contains every CFG_EXTRA_ENV_SETTINGS entry. PXE works.
  2. Operator runs fw_setenv ethaddr 00:e0:4c:68:00:3b from Linux:
    • fw_setenv reads /dev/mtd0 at the offset /etc/fw_env.config points it at — sees bad CRC — starts with an empty in-memory env. Crucially: fw_setenv has no access to CFG_EXTRA_ENV_SETTINGS, because that string lives inside u-boot.bin, not on disk.
    • It applies ethaddr=… to the empty env, computes a CRC, writes the whole thing (just one entry plus header) back to SPI.
  3. Next U-Boot boot: SPI env loads successfully (good CRC) → runtime env = {ethaddr=…} only. pxefile_addr_r and every other address var: gone. bootflow scan silently skips the ethernet bootdev.

So Layer-2 defaults need a partner that gets them into SPI before the first fw_setenv ever runs. Three options:

  • Partner option 1 — first-boot env-save sentinel. Extend the same CFG_EXTRA_ENV_SETTINGS with a bootcmd snippet that, on first boot (detected via a sentinel var), does env default -a; env save. Bakes the defaults into SPI as a CRC-valid saved env from day one. After that, fw_setenv reads a full env, modifies one var, writes back — the address vars survive because they were in what fw_setenv read in step 2. 
    /* Appended inside CFG_EXTRA_ENV_SETTINGS: */
"first_boot=test \"${env_baked}\" = 1 || "
            "(env default -a; env set env_baked 1; env save)\0"
"bootcmd=run first_boot; bootflow scan -lb\0"
    Clean — one extra env var — but introduces a build-time-decided bootcmd that future U-Boot bumps may want to override.
  • Partner option 2 — Approach B. Use the fw_setenv automation from Section 8.4 to converge SPI env state to the desired set every time the playbook runs. In this path the Layer-2 hook above is redundant — Approach B writes the same vars directly into SPI. This is the path this collection’s current proposal favours, because per-board MAC tracking already lives in inventory and a convergence playbook is the natural shape for that.
  • Partner option 3 — disable SPI env entirely. Drop CONFIG_ENV_IS_IN_SPI_FLASH=y in the same overlay that adds the Layer-2 defaults; defaults from u-boot.bin then always apply, and fw_setenv from Linux becomes a no-op (or errors). Drastic — loses the ability to persist any per-board state from Linux — but clean for a true netboot-only fleet where the only per-board state the U-Boot env ever needed to carry was the MAC, and Approach A’s board.c patch has already moved MAC handling into the DT resolution chain.

Practical recommendation. Approach B (Section 8.4) already covers the same surface as Partner Option 2 and is more flexible (per-board MAC from inventory, idempotent re-runs, snapshot before write). Adding the Layer-2 hook is worth doing only if/when we want fresh boards to PXE successfully before the Approach B playbook gets a chance to run — i.e. true zero-touch from first SD-flash, with no Linux-side intervention required. Without Partner Option 1’s first-boot env-save, that zero-touch is a single-boot guarantee only.

9. Gotchas

"current" and "edge" are not u-boot trees. They’re Armbian’s kernel branch labels that the build system also overloads as a per-board switch for u-boot dispatch. The actual u-boot tree for a given (board, branch) pair is whatever the last-firing hook leaves BOOTSOURCE set to. Always trace the hooks for a specific board before assuming.
Hook ordering is by string sort, not registration order. Hooks without a numeric prefix get an implicit 500_. To guarantee yours runs last (and wins), use a high prefix like __999_. LC_ALL=C --general-numeric-sort means __100_ sorts before __500_, but plain text like __zzz_ won’t override numerics reliably.
BOOTCONFIG name changes across forks. The Radxa fork ships rock-5b-rk3588_defconfig; mainline ships rock5b-rk3588_defconfig. A hook that swaps the source tree must also swap the defconfig name or make fails with "no rule to make target".
Stock images don’t boot PXE-first. Both the Radxa fork and mainline ship BOOT_TARGETS with pxe at position 6 (after SD/eMMC/NVMe). U-Boot’s bootflow scan lands on the local rootfs’s boot.scr long before it tries PXE. The PXE-first invariant requires patching BOOT_TARGETS at build time — runtime setenv boot_targets pxe … won’t survive a power cycle.
Two BOOT_TARGETS source forms exist. Older trees use a single-line #define BOOT_TARGETS "mmc1 mmc0 …" in include/configs/rockchip-common.h. Newer trees use the X-macro BOOT_TARGET_DEVICES(func) form. A sed targeting the legacy form is a silent no-op on the X-macro form — the build succeeds but boot order is unchanged. Always confirm by running strings u-boot.bin | grep -i boot_targets on a test build.
Mainline u-boot + PCIe NIC = silent PXE failure unless CONFIG_PCI_INIT_R=y. The bootflow framework only iterates bootdevs that were enumerated at init_r time. rk3588 defconfigs default CONFIG_PCI=y without CONFIG_PCI_INIT_R=y, so PCIe NICs (Rock 5B’s RTL8125, NanoPC-T6, etc.) are present in the device tree but never enumerated, never become a bootdev, and bootflow scan reports zero ethernet bootflows with no error. Boards with GMAC NICs (OPi5Pro) sidestep this entirely.
SPI env replaces compile-time defaults; it does not merge. If a board has CONFIG_ENV_IS_IN_SPI_FLASH=y and a valid env in SPI, the compile-time default_environment[] array is not used. Variables like pxefile_addr_r defined only as compile-time defaults vanish from the runtime env on the first successful fw_setenv. This is a U-Boot semantics issue, not an armbian/build issue, but board configs that enable SPI env without explicitly writing the PXE address vars to CONFIG_EXTRA_ENV_SETTINGS will produce images that work cold but break after any env write.
Userpatches files persist across rebuilds. The armbian_build role writes new userpatches but does not prune orphans. A renamed or refactored hook leaves the old file in userpatches/ on the builder host; armbian/build will source it on every rebuild, registering dead hook functions. Usually harmless, but worth knowing when a hook seems to "still work" after you thought you deleted it.
The .csc / .conf filename matters. .csc = Community Supported (no CI, maintainer-reported breakage). .conf = Armbian-supported (CI-tested). Both are buildable through the same compile.sh BOARD= path — the suffix is metadata, not a load gate. But on bug reports the suffix tells you which support tier you’re actually leaning on.
