Ansible Best-Practices Review

Collection: david_igou.armbian_netboot v3.1.0 · Scope: nine roles, collection-level metadata, ansible.cfg, vars/boards.yml · Date: 2026-05-20

1. Introduction & scope

This document is a maintainability- and human-readability-focused review of the david_igou.armbian_netboot collection against the two reference guides the user asked it to be measured against:

  • Red Hat Communities of Practice — Automation Good Practices (role design, naming, variable scoping, idempotency, tags, inventory, templates, style).
  • Ansible — Developing Modules — Best Practices (single-responsibility, declarative interfaces, idempotency, security, error handling). The collection ships no custom modules today; the module guidance is therefore applied by analogy to role interfaces (argument_specs, returns, fail-fast, no_log).

Out of scope: the runtime correctness of any workflow (covered by test_fleet_e2e.yml), and the architecture of the v3 refactor itself (which this review treats as the baseline and validates from). Per-playbook style is touched on only where it directly affects how a role is consumed.

The audit was performed by reading every file under roles/<role>/ and every file referenced in this section’s scope. Severity is graded on a four-step scale:

  • Critical — safety, security, or correctness issue; can leak credentials, corrupt state, or silently produce wrong results.
  • High — meaningfully degrades maintainability, discoverability, or operator confidence; should be fixed before the next minor release.
  • Medium — clear deviation from guidance; the role works but is harder to read, harder to extend, or inconsistent with siblings.
  • Low — stylistic / hygiene polish; bundle into batched cleanups.
  • Positive — called out so good patterns are preserved during refactors.

2. Methodology & references

For each role I checked the following dimensions, drawn from the COP checklist and the module-development guide:

  1. Structure & scope — single-responsibility, intent-agnostic, sub-task file layout.
  2. Naming & defaults — role-prefixed externals, __rolename_-prefixed internals, all overridable inputs in defaults/main.yml.
  3. Argument specs — presence, completeness, types, choices, examples.
  4. Idempotency & check mode — accurate changed_when, no false changes on re-run, --check support.
  5. Task style — FQCN, imperative names, sub-file prefix | description, command preferred over shell, become minimisation.
  6. Templates — {{ ansible_managed }} header, no timestamps, declarative data over Jinja control flow.
  7. Handlers — named, single-purpose, not over-notified.
  8. Documentation — README with overview, inputs, outputs, examples, idempotency notes.
  9. Meta — author, license, min_ansible_version, platforms, galaxy_tags.
  10. Security — no_log on credentials, no plaintext secrets in defaults/docs.

3. Executive summary

The collection is in a healthy place. The v3 refactor has produced a set of genuinely single-purpose, transport-agnostic roles, FQCN usage is effectively 100 %, and eight of nine roles ship a populated meta/argument_specs.yml. The shortlist of issues that warrant immediate attention is small but real:

4. Collection-level findings

4.1 galaxy.yml and meta/runtime.yml

Strong points. Namespace/name/version are correct; description honestly reflects the v3 decomposition; build_ignore excludes the right dev artefacts; collection-level dependencies match requirements.yml exactly; meta/runtime.yml pins requires_ansible: ">=2.15.0" which matches every role’s own min_ansible_version.

Low — authors uses kebab handle instead of human name

galaxy.yml:7

The COP’s collection documentation guidance recommends a real name plus contact, mirroring the module developer best practice of clear authorship. Galaxy renders this verbatim on the collection page.

Now
authors:
  - david-igou
Recommended
authors:
  - David Igou <igou.david@gmail.com>
Why: Aligns with role-level meta and gives Galaxy a human-readable byline. Cheap consistency fix.

Medium — missing collection-level tests/ / molecule wiring

Collection root

The collection has thorough fleet-level integration tests (playbooks/test_fleet_e2e.yml), but no role-level molecule scenarios. The COP “Continuous Integration” section recommends molecule per role, and the Red Hat collection scaffolding produces a roles/<role>/molecule/default/ tree. Without it, role-only regressions can’t be caught in CI without spinning the whole fleet.

Why: Most of these roles (pxelinux_render, rootfs_clone, disk_provision) are deterministic enough to test in ephemeral containers / sparse loop devices. Two molecule scenarios — pxelinux_render (no privilege, golden-file diff) and disk_provision against a 256 MiB sparse file — would cover ~70 % of role logic at near-zero cost.

4.2 ansible.cfg

Strong points. The persistent-connection timeout override is documented with a clear post-mortem of which test it fixed — this is exactly the kind of in-file context the COP recommends. profile_tasks callback is enabled, pipelining is on, ControlPersist is set.

Low — boolean style: False instead of no

ansible.cfg:4
Now
host_key_checking   = False
Recommended
host_key_checking   = false
Why: COP “Booleans & Values” rule: prefer lowercase true/false over Python-style True/False and over the legacy yes/no aliases. Purely cosmetic, but applying the rule to ansible.cfg too keeps the convention uniform across YAML and ini.

Medium — roles_path hard-coded to a relative path

ansible.cfg:2
roles_path = roles

This forces every invocation to happen from the collection root or it silently resolves to the wrong directory. When the collection is installed under ~/.ansible/collections/ansible_collections/david_igou/armbian_netboot/, the bundled ansible.cfg is not consulted — but the developer-mode “run from repo root” flow still pays the surprise cost.

Why: COP “variable precedence” prefers explicit, reproducible setups; either drop the line (rely on Ansible’s default search) or document the developer-mode contract explicitly in the comment.

4.3 requirements.yml

Mirrors galaxy.yml exactly; nothing to flag. As a polish item, both files reference the same three dependencies in the same order — consider generating one from the other (or have CI assert equality) to prevent drift over time.

4.4 vars/boards.yml

This is the authoritative per-board metadata catalogue (armbian_netboot_board_configs). Structure is clean: top-level key is collection-prefixed, per-board values are snake-cased nested dicts (local_kernel, uboot_env), optional sub-trees are present only where the board needs them.

Low — consider moving from vars/ to defaults/

The COP rule is: “avoid giving default values in vars/main.yml” — vars/ has higher precedence than role defaults, so users cannot override per-host. The catalogue itself is intentionally not user-overridable (the whole point is that the collection owns these board facts), so the current placement is defensible — but document why at the top of the file, otherwise readers will assume the COP rule is being violated by accident.

# Recommended header comment
# This file intentionally lives under vars/ (not defaults/) because the
# board catalogue is authoritative collection knowledge; per-host
# overrides should patch *specific* fields via group_vars/host_vars,
# not replace whole entries.

4.5 FQCN audit

I scanned every roles/*/tasks/*.yml for short module names and found no unqualified built-in or community module invocations. The few apparent matches (shell: /bin/bash, user: "{{ ... }}") are module arguments, not module calls. This is well above the average; keep it that way with an ansible-lint rule (fqcn-builtins).

4.8 meta/argument_specs.yml coverage

Eight of nine roles ship complete argument specs. The single gap:

High — bootstrap_armbian has no meta/argument_specs.yml

roles/bootstrap_armbian/meta/

The role consumes armbian_netboot_bootstrap_user and armbian_netboot_bootstrap_ssh_keys, both required for the role to do anything useful, yet there is no machine-readable contract. Adding the spec fail-fasts callers who forget to define the keys list (currently the role would create the user, succeed, and leave the host without authorized keys — an outage waiting to happen).

# roles/bootstrap_armbian/meta/argument_specs.yml
---
argument_specs:
  main:
    short_description: "Provision an SSH-key user with passwordless sudo on a flashed Armbian board."
    description:
      - "Connects as root (with the Armbian default password) and creates an
        unprivileged user, authorises a fixed set of SSH keys for it, grants
        passwordless sudo, and disables password authentication in sshd."
    options:
      armbian_netboot_bootstrap_user:
        type: str
        required: true
        description: "Username to create on the board."
      armbian_netboot_bootstrap_ssh_keys:
        type: list
        elements: str
        required: true
        description: "Public SSH keys to authorise for the new user. Must be non-empty."
Why: The COP rule “Activate argument validation using meta/argument_specs.yml” explicitly calls out fail-fast as the primary win. Equally important here is parity: callers currently get IDE hints and validation for the other eight roles and not this one, which is a footgun.

Beyond the missing file, board_boot_wait’s spec is missing three declared defaults (armbian_netboot_boot_retry_attempts, armbian_netboot_ssh_wait_timeout, armbian_netboot_ssh_wait_retry_attempts) — fixed below in §5.8.

5. Role-by-role review

5.1 image_build

Purpose: Build a custom Armbian .img.xz on a builder host with PXE-first U-Boot baked in; optionally publish via SCP.

Strong points. Manifest-based skip logic (five decision fields → skip rebuild); clearly separated sub-task files (preflight / manage_checkout / compute_inputs / apply_userpatches / invoke_build / write_manifest / publish_scp / check_manifest); thorough README with input table, output schema and idempotency notes; cleanly documents the local_kernel_dispatch_table pre-task contract in the spec.

Critical — SCP publish task lacks no_log on credential-bearing destinations

roles/image_build/tasks/publish_scp.yml

The publish target is supplied as a free-form rsync/scp URL via armbian_netboot_publish_target. If the operator ever embeds credentials (e.g. user:pass@host:/path) for ad-hoc testing, the literal value lands in task logs and in any CI artifact. Costless mitigation:

Now
- name: SCP the built .img.xz to the publish target
  ansible.builtin.shell: |
    scp "{{ armbian_build_output_dir }}/.../*.img.xz" \
        "{{ armbian_netboot_publish_target }}/"
  changed_when: true
Recommended
- name: Publish the built .img.xz to the configured target
  ansible.builtin.shell: |
    scp "{{ armbian_build_output_dir }}/.../*.img.xz" \
        "{{ armbian_netboot_publish_target }}/"
  changed_when: true
  no_log: true
Why: COP “Use no_log: true on tasks that output credentials, hostnames, or sensitive paths.” The cost of being wrong here is permanent credential exposure in CI logs; the cost of no_log being right is zero.

High — changed_when: true on the compile.sh invocation hides build outcome

roles/image_build/tasks/invoke_build.yml (compile task)

The actual compile.sh wrapper run is the role’s most expensive step (~20 minutes) and currently always reports “changed” regardless of success path. Use the return-code / stderr signal to mark failure / partial-success precisely.

- name: Run armbian/build compile.sh
  ansible.builtin.shell: |
    bash compile.sh ...
  register: _image_build_compile
  changed_when: '"Runtime:" in (_image_build_compile.stderr | default(""))'
  failed_when: _image_build_compile.rc != 0
Why: Operators rely on changed: to gate downstream handlers (publish, notification). The current pattern fires those handlers even on a no-op cache hit.

Medium — internal facts not role-scoped

Throughout roles/image_build/tasks/

Internals use a single leading underscore (_patch_hash, _manifest_inputs, _skip_build). COP recommends the __rolename_ double-underscore form to collision-proof multi-role plays. This is a pure rename and non-breaking.

# before                       # after
_patch_hash                      __image_build_patch_hash
_manifest_inputs                 __image_build_manifest_inputs
_skip_build                      __image_build_skip_build
Why: COP “Internal variables prefixed by two underscores: __rolename_variable”. _skip_build in particular is generic enough that a future role could redefine it, leading to a subtle bug; the double-underscore prefix forecloses that.

Low — README example doesn’t cover compile_args overrides

roles/image_build/README.md

The COP “Documentation” rule asks for examples that cover the “common override patterns”; the most-asked-about knob (build_minimal vs full image) is mentioned in the inputs table but not shown in any example. Add one line.

Top 5 fixes — image_build

  1. C1 — add no_log: true to publish_scp tasks.
  2. H1 — make changed_when on compile.sh content-derived.
  3. M1 — rename internal facts to __image_build_*.
  4. M2 — resolve license mismatch (currently GPL-3.0-or-later, mismatches the MIT majority).
  5. L1 — expand README example with a compile_args override.

5.2 image_extract

Purpose: Extract a single .img.xz on the netboot server into one rootfs template plus per-model TFTP artefacts (vmlinuz / initrd / DTB).

Strong points. Block / rescue / always lifecycle ensures loop devices are torn down on failure; sub-task files cleanly separate concerns (_download_or_copy / _extract_inner / _copy_kernel_artifacts / _cleanup); the existing argument_specs covers every input.

High — no README despite non-trivial lifecycle

Loop-device attach/detach + mount/unmount + rsync semantics are not self-evident from the task names. A 100-line README walking through inputs, the “already extracted” fast-path, failure recovery, and the on-server filesystem layout makes this role consumable.

High — idempotency check is a single-file existence probe

roles/image_extract/tasks/main.yml (already-extracted guard)

The fast-path currently checks for one well-known file in the template tree. If that file exists but the rest of the extraction was interrupted (loop device orphan, partial rsync), the role skips and produces a broken state on next run. Either widen the probe to a multi-file manifest or write a small .extracted_at sentinel only at the end of the always block.

Now
- name: Probe template rootfs
  ansible.builtin.stat:
    path: "{{ template_dir }}/bin/bash"
  register: _image_extract_template
- ansible.builtin.set_fact:
    _already_extracted: "{{ _image_extract_template.stat.exists }}"
Recommended
- name: Probe extraction sentinel
  ansible.builtin.stat:
    path: "{{ template_dir }}/.armbian_extract_complete"
  register: _image_extract_sentinel
- ansible.builtin.set_fact:
    _already_extracted: "{{ _image_extract_sentinel.stat.exists }}"

# ...written only at the end of the success path:
- name: Mark extraction complete
  ansible.builtin.copy:
    dest: "{{ template_dir }}/.armbian_extract_complete"
    content: "{{ ansible_date_time.iso8601 }}\n"
    mode: "0644"
Why: COP “Roles should not perform changes on second application with same parameters” and should not silently produce inconsistent state on a partial first run. A sentinel keyed to success is the cheapest way to do both.

Medium — changed_when: true blanket on all shell tasks

Every shell step (xz, losetup, mount, rsync) is declared always-changed. With the sentinel fix above, these tasks only run on the “fresh extraction” path, so the blanket is harmless — but the rsync step in particular benefits from --itemize-changes + output-driven changed_when so re-extracted (force) runs show real deltas.

Medium — cleanup task silently swallows umount/losetup failures

roles/image_extract/tasks/_cleanup.yml

failed_when: false on both umount and losetup -d hides genuine leak conditions. Capture the result and surface it as a warning, so loop-device leaks are visible during development:

- name: Detach loop device (best effort)
  ansible.builtin.command: losetup -d {{ __image_extract_loop_dev }}
  register: __image_extract_losetup_d
  failed_when: false
  changed_when: __image_extract_losetup_d.rc == 0

- name: Warn if loop detach failed
  ansible.builtin.debug:
    msg: "Loop detach failed: {{ __image_extract_losetup_d.stderr }}"
  when: __image_extract_losetup_d.rc != 0
Why: “Use clear error/info messages” (module-dev guide). Silent failed_when: false trades short-term test green for long-term drift.

Low — internal facts not role-scoped

Same observation as image_build — rename _is_url, _img_cache, _loop_dev to __image_extract_*.

Top 5 fixes — image_extract

  1. H1 — write a README.
  2. H2 — switch idempotency probe to a sentinel file written at the end of the success path.
  3. M1 — surface losetup/umount failures via debug warning instead of silent failed_when: false.
  4. M2 — drive rsync changed_when from --itemize-changes output.
  5. L1 — rename internal facts to __image_extract_*.

5.3 disk_image

Purpose: Stream-write one .img(.xz) source to a block device on a target host (curl|xz|dd or path|xz|dd). Mount-aware refusal pre-flight.

Strong points. Three-block design (_validate → _write → _settle); README is honest about what the role doesn’t do (checksum verification, identity reset, resize); careful use of set -o pipefail in every pipeline; | quote filter on user-supplied strings.

High — changed_when: true on every write branch makes failure invisible

roles/disk_image/tasks/_write.yml

All four streaming branches (url+xz, url+raw, path+xz, path+raw) mark changed_when: true unconditionally. A failed dd sets rc != 0 and is caught by Ansible’s default, but a successful dd that wrote zero bytes (e.g. empty source) still reports “changed”. Capture the records-out from dd’s stderr and gate on it:

- name: Stream url + xz to block device
  ansible.builtin.shell: |
    set -o pipefail
    curl -fsSL {{ src | quote }} | xz -d | dd of={{ dest | quote }} bs={{ dd_bs }} conv=fsync status=progress
  register: __disk_image_write
  changed_when: '"records out" in __disk_image_write.stderr and "0+0 records out" not in __disk_image_write.stderr'
Why: Distinguishing “wrote real bytes” from “wrote nothing” is critical for the e2e tests that gate on changed. COP “Accurate changed_when: is essential.”

Medium — FQCN consistency in _validate.yml

Most modules are called ansible.builtin.stat / ansible.builtin.assert, but a handful of later tasks use the short form. Standardise to FQCN everywhere — the collection is otherwise 100 % compliant.

Medium — README doesn’t mention behaviour on truncated source

The honesty about “no checksum verification” needs the corollary: what actually happens if the source is truncated. Add:

A truncated source leaves a partial image on the destination — the role does not detect or recover. Verify your source out-of-band (e.g. via the manifest produced by image_build).

Top 5 fixes — disk_image

  1. H1 — capture dd records-out for accurate changed_when.
  2. M1 — FQCN audit in _validate.yml.
  3. M2 — document truncated-source behaviour in README.
  4. L1 — rename internal facts to __disk_image_*.
  5. L2 — register the write task and emit a single end-of-run debug with throughput summary.

5.4 disk_provision

Purpose: Idempotently lay out an NVMe/eMMC disk with a declarative partition spec (disk_binding), preserving matching existing partitions; render repart.d/ and an fstab template; optionally blkdiscard fast-wipe; populate from a source rootfs.

Strong points. Five-stage pipeline (_validate → _render_repart → optional end_host for render-only → _preserve_scan → _apply_repart → _populate); nested-dict argument shape declared in argument_specs with per-field descriptions; fstab.j2 uses {{ ansible_managed }} and LABEL-based references; preserve scan enables true re-run idempotency; clear comment on the SYSTEMD_REPART_MKFS_OPTIONS_EXT4 env-var workaround.

High — no README despite being the most complex role

This role has the largest input surface (a nested list of partition specs with optional preserve flags, fstab overrides, label conventions). It cannot be onboarded from argument_specs alone. README should include: a worked example of a 3-partition disk; the preserve flow (when partitions are kept vs. recreated); the semantics of fast_wipe; how reset_identity interacts with subsequent boot.

High — systemd-repart always reports “changed”

roles/disk_provision/tasks/_apply_repart.yml

systemd-repart prints its actions to stdout (lines like Created partition 1 ... on the JSON dry-run). Use that to derive change state:

- name: Apply systemd-repart
  ansible.builtin.command: >
    systemd-repart --json=short
                   --definitions {{ __disk_provision_repart_dir }}
                   {{ disk_binding.device }}
  register: __disk_provision_repart
  changed_when: (__disk_provision_repart.stdout | from_json | length) > 0
Why: Today, every run reports the disk “changed” even when systemd-repart was a no-op — defeats the preserve-scan’s whole purpose for auditability.

Medium — rsync via command instead of synchronize

roles/disk_provision/tasks/_populate.yml

The populate step shells out to rsync with archive flags + excludes. The ansible.posix.synchronize module is the declarative equivalent and is already a collection dependency.

- name: Populate partition from source rootfs
  ansible.posix.synchronize:
    src: "{{ disk_provision_source }}/"
    dest: "{{ __disk_provision_mount_root }}{{ part.mountpoint }}"
    archive: true
    delete: true
    rsync_opts:
      - "--exclude=/proc/*"
      - "--exclude=/sys/*"
      - "--exclude=/dev/*"
      - "--exclude=/tmp/*"
  loop: "{{ disk_binding.layout | selectattr('mountpoint', 'defined') | list }}"
  loop_control: { label: "{{ part.mountpoint }}" }
Why: COP “Prefer declarative modules over shell.” synchronize also gives accurate change detection out of the box.

Medium — blkdiscard rc=2 case is undocumented

The fast_wipe branch tolerates rc=2 with a single comment that says “device doesn’t support discard”. Surface that as a debug message so operators reading the playbook log know why the fast path silently fell back, and document the three rc values (0, 1, 2) in a comment block at the task.

Low — _dp_* prefix is half-COP

Already prefixed (good), but COP convention is __disk_provision_*. The current prefix is shorter, but ambiguous: a future reader has to map _dp_ back to disk_provision. The full prefix self-documents.

Top 5 fixes — disk_provision

  1. H1 — write a README with worked disk_binding example, preserve flow, fast_wipe semantics.
  2. H2 — derive changed_when for systemd-repart from JSON output.
  3. M1 — switch the populate rsync to ansible.posix.synchronize.
  4. M2 — emit debug + comment for the blkdiscard rc=2 fallback.
  5. L1 — expand internal-fact prefix from _dp_* to __disk_provision_*.

5.5 bootstrap_armbian

Purpose: Provision a passwordless-sudo, SSH-key user on a freshly flashed Armbian board, starting from root login with the stock default password.

Strong points. Task names are imperative and clear; loop_control: label masks key material in logs; a handler restarts sshd; pre-flight assert validates required inputs; the README explains the role’s place in the lifecycle.

Critical — default credential "1234" documented in README and committed in group_vars/all.yml

roles/bootstrap_armbian/README.md, inventory/group_vars/all.yml

The role explicitly documents the Armbian default password ("1234") and the sample group_vars/all.yml in the docs directory persists it as a fallback. While this is “just” the well-known Armbian default, having it in a versioned file teaches consumers a bad habit and ensures the value appears verbatim in CI logs.

Fix:

  1. Replace README text with: “Supply ansible_password on the command line, via vault, or via --ask-pass. Do not commit it to version control.”
  2. Remove the armbian_netboot_default_password default from sample group_vars/all.yml; document the variable but leave it unset.
  3. Add no_log: true to any task in this role and in bootstrap_armbian.yml that could log the password (the ansible_password connection var is masked by Ansible, but inline vars: blocks aren’t).
Why: Module-dev guide rule “Mark sensitive parameters with no_log=True”; COP “Variable Management — secrets”. The cost of being wrong (credentials in CI artifacts that may be world-readable) is asymmetric.

High — no meta/argument_specs.yml

See §4.8. The role consumes armbian_netboot_bootstrap_user and _ssh_keys with no validation; supplying an empty key list silently leaves the board permanently unreachable as soon as password auth is disabled in the same play. This is the single most consequential missing spec in the collection.

Medium — authorized_key task has no no_log

SSH public keys are not secret, but the comment field often identifies operators and hostnames. Add no_log: true in addition to the existing loop_control: label:

- name: Authorise SSH keys for {{ armbian_netboot_bootstrap_user }}
  ansible.posix.authorized_key:
    user: "{{ armbian_netboot_bootstrap_user }}"
    state: present
    key: "{{ item }}"
    exclusive: false
  loop: "{{ armbian_netboot_bootstrap_ssh_keys }}"
  loop_control:
    label: "{{ item.split() | last | default('(no comment)') }}"
  no_log: true

    name: ssh
    state: restarted

5.6 rootfs_clone

Purpose: Reflink-clone a rootfs template into a per-host directory, then reset per-host identity (hostname, machine-id, SSH host keys) so multiple clones boot with independent identities.

Strong points. Single, sharp scope (clone + identity reset, nothing else); thorough argument_specs; in-task comments document non-obvious decisions (machine-id zero-and-readonly, sshd-keygen ConditionFirstBoot); creates: guards prevent regenerating existing keys.

High — no README

Identity reset is exactly the kind of behaviour that needs a documented contract: “these fields are reset, these fields are not, here’s how that interacts with systemd-machine-id-setup on first boot”. Without a README, callers cannot reason about whether their own first-boot scripts will be a no-op or fight the role.

Medium — shell: cp -a --reflink=auto where command would do

roles/rootfs_clone/tasks/main.yml
# Now
- name: Reflink-clone template into target_dir
  ansible.builtin.shell: |
    set -o pipefail
    cp -a --reflink=auto "{{ template_dir }}/." "{{ target_dir }}/"
  args:
    executable: /bin/bash
  when: not _target_stat.stat.exists
  changed_when: true

# Recommended
- name: Reflink-clone template into target_dir
  ansible.builtin.command:
    argv:
      - cp
      - -a
      - --reflink=auto
      - "{{ template_dir }}/."
      - "{{ target_dir }}/"
  when: not _target_stat.stat.exists
  changed_when: true
Why: No pipe, no shell expansion, no real need for bash — COP “Prefer command over shell”. argv form removes any doubt about quoting.

Medium — shell rm with glob for stale SSH host keys

roles/rootfs_clone/tasks/_identity_reset.yml

Replace with the find + file idiom, which is check-mode-safe and reports an honest change count.

- name: Find stale SSH host keys in clone
  ansible.builtin.find:
    paths: "{{ target_dir }}/etc/ssh"
    patterns: "ssh_host_*"
  register: __rootfs_clone_stale_keys

- name: Remove stale SSH host keys
  ansible.builtin.file:
    path: "{{ item.path }}"
    state: absent
  loop: "{{ __rootfs_clone_stale_keys.files }}"
  loop_control:
    label: "{{ item.path | basename }}"

Low — defaults/main.yml comment is jargon

The current note about “argument_specs symmetry” is opaque. Reword so a reader who hasn’t internalised the convention can follow.

5.7 pxelinux_render

Purpose: Render one per-board 01-<mac> pxelinux.cfg file in a local output directory, with multiple boot-mode labels and a configurable default.

Medium — default values reference an unresolved variable

Either document the invariant in the spec, or compute the fallback in the template instead of the default:

{# pxelinux_cfg.j2 #}
{% set _tftp_kernel = pxelinux_render_tftp_kernel
                       or 'armbian/' ~ pxelinux_render_model_name ~ '/vmlinuz' %}
kernel {{ _tftp_kernel }}

# {{ ansible_managed }}
# pxelinux.cfg for {{ pxelinux_render_hostname }} ({{ pxelinux_render_model_name }})
# MAC: {{ pxelinux_render_board_mac }}
# Active mode: {{ pxelinux_render_boot_mode }}

6. Cross-cutting issues

6.1 Variable-prefix convention is ambiguous

Today the collection uses three different prefix conventions simultaneously:

ConventionUsed byCOP-aligned?
Collection-prefixed: armbian_netboot_* bootstrap_armbian, board_boot_wait, board_boot_verify, most cross-role globals Acceptable — matches the COP “collection-level variables prefixed by collection name” pattern.
Role-prefixed: image_build_*, disk_provision’s disk_binding, image_extract_* image_build (partial), image_extract Matches COP “defaults and arguments should have names beginning with role name”.
Unprefixed: sd_root, tftp_kernel, boot_mode, force_refresh pxelinux_render, rootfs_clone, parts of board_boot_verify No — collision risk.

The collection-prefix convention is the most appropriate one for inputs the user wires into inventory (boot mode, default password, NFS path), and the role-prefix convention is the most appropriate for role-internal knobs. Pick one rule and apply it:

Recommended rule. Inputs that flow from inventory across many roles use armbian_netboot_*. Inputs that a role consumes only locally use <role>_*. Internal facts (set_fact, register) use __<role>_*. Document this rule in CLAUDE.md so future roles inherit it automatically.

6.2 changed_when hygiene

Three roles (image_extract, disk_image, disk_provision) declare changed_when: true on long-running shell pipelines. This makes changed: meaningless as a signal — downstream handlers cannot rely on it, and --check mode gives no useful information. Each one needs an output-derived changed_when — see per-role fixes for the precise expressions.

6.3 License is split 7/2

Seven role meta/main.yml files declare MIT, two (image_build, bootstrap_armbian) declare GPL-3.0-or-later. The collection-level LICENSE file decides which is correct — pick the one that matches the LICENSE file in the repo root, edit the other seven (or two) to match, and document the licence in the top-level README. This is not a stylistic issue; it’s a real distribution correctness issue.

6.4 README coverage

Six of nine roles ship no README. The three that do are very good. Use them as the template — the spec lists the sections to copy.

6.5 No molecule per-role tests

The collection has excellent fleet-level integration tests, but no role-level scenarios. Two scenarios would catch the bulk of regressions cheaply:

  • pxelinux_render/molecule/default — render against a fixture inventory, golden-file diff the output. Zero privileges, runs in CI in <5s.
  • disk_provision/molecule/default — provision against a 256 MiB sparse loop file, assert the partition table + fstab. Privileged container, ~20s.
