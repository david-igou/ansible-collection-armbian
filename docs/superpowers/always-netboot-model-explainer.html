Always-netboot model hypothetical

A design exploration: what would change if this collection stopped using pxelinux.cfg presence as the on/off toggle for netboot, and instead always rendered a per-board pxelinux.cfg on rb5009 whose DEFAULT line picked which boot mode the board takes. Nothing here is implemented — this is the “if we did it this way” conversation, with concrete file shapes, role contracts, and example flows so a first-time reader of the repo can judge the trade-offs.

Reader note. 1. Where the collection sits today

In v1, the collection uses one piece of state to switch a board between netboot and disk boot: the per-board file flash:/sbc/pxelinux.cfg/01-<MAC> on rb5009 (plus the matching /ip tftp row that exposes it). File present + row present ⇒ the board PXE-boots an NFS rootfs. Either piece absent ⇒ U-Boot’s PXE bootmeth fast-404s through the entire filename-fallback chain (see pxelinux-cfg-explainer §3), bootflow scan moves on to the next BOOT_TARGETS entry, and the board boots from SD.

Concretely, the rendered file contains exactly one LABEL and one DEFAULT pointing at it:

  • Written by configure_pxe.yml inside the board_boot_state role, removed by configure_disk.yml.
  • One label, one default. The directive DEFAULT is technically active but operationally trivial — there’s nothing else to default to.

1.1 Why the binary toggle starts to creak

The binary toggle is fine for v1’s single goal: can this board be flipped between an SD rootfs and an NFS rootfs? But each new thing the operator wants the board to do introduces another “mode” that has to be encoded somewhere:

  • Boot a TFTP kernel but root from a local NVMe SSD that’s been pre-installed.
  • Boot a TFTP kernel but root from eMMC.
  • Boot a one-shot installer image that lays down a rootfs onto NVMe, then hands off.
  • Boot a RAM-rooted recovery shell (no rootfs mount) when something on disk is wrong.
  • Boot the previous-known-good kernel instead of the current one, deliberately.
  • Stop PXE-booting entirely and chain to whatever the SD card has — without removing per-board state from rb5009.

All of these are still achievable with the file-presence model, but each one has to be either a different file or a flag handled inside the role. The model doesn’t generalise — it’s a one-bit channel, and we want a small-integer channel.

2. The shift: file presence → DEFAULT as the control surface

In the always-netboot model, two things change:

  1. The per-board pxelinux.cfg/01-<MAC> file is always present on rb5009. Onboarding a board writes it once; decommissioning a board removes it. Day-to-day operations never touch file existence.
  2. The DEFAULT directive inside that file is the operator-controlled mode switch. The role renders one LABEL block per supported boot mode and points DEFAULT at whichever one inventory currently asks for. U-Boot reads the file, takes the DEFAULT label, fetches its KERNEL/INITRD/FDT, applies its APPEND cmdline, and boots.

2.1 What stays the same

  • rb5009 is still the only control surface. Same /file + /ip tftp pair per board. Same net_put machinery in routeros_sbc_tftp.
  • U-Boot’s PXE-first BOOT_TARGETS baked into the custom Armbian image still drives the bootflow that reaches into rb5009 for the .cfg — see uboot-armbian-build-explainer.html.
  • The NFS server, per-host rootfs clones, per-model TFTP staging are unchanged. Even the existing NFS-root flow becomes the nfsroot menu entry under the new model — no semantic change, just one entry in a longer list.
  • The two-resource invariant (file + row written and removed as a pair) is unchanged — see pxelinux-cfg §6.

2.2 What changes

  • The Jinja template grows from one LABEL to N LABEL blocks plus a single DEFAULT line driven by a per-host inventory variable (boot_mode: nfs|nvme|emmc|sd|recovery|installer|lkg|localboot).
  • The board_boot_state role’s contract widens from boot_state: pxe|disk to something closer to boot_mode: <label>. The role still composes “configure → cycle → verify”; what “configure” and “verify” do is now data-driven.
  • “Disable netboot” stops meaning “remove the file.” In the always-netboot world, “the board should boot off SD” is the localboot menu entry being selected. The file stays. (Why this is better: §10.3.)
  • A small new lifecycle appears around per-host state. The previous-known-good kernel pointer, the per-host rootfs_partuuid, the per-host overlays — these now live in inventory and have to be discovered/maintained somehow. §4 and §8 cover the data shape.

  • One file, seven boot modes. The single line that determines the board’s next boot is DEFAULT nvmeroot.
  • Every LABEL except lkg uses the same versionless vmlinuz / initrd.img path — they pick up new bytes when stage_netboot_assets.yml re-stages them. lkg intentionally pins a versioned kernel; §8 covers why.
  • The file is ~1.5 KB total. Disk on rb5009 isn’t the constraint.
  • TIMEOUT 50 PROMPT 0: U-Boot waits 5.0 s for an operator on the serial console to type a different LABEL, then commits to DEFAULT. With PROMPT 0 the prompt is silent (no “boot:”); an operator hitting any key during the window still gets to override. See §10.5 for the trade-off.

3.1 What U-Boot does with this file

When the board powers on and U-Boot’s PXE bootmeth TFTPs this file from rb5009, the bootmeth’s behaviour is:

  1. Parse the file. Collect all LABEL blocks into a table.
  2. Read DEFAULT. Look up the named label in the table.
  3. If TIMEOUT is set, wait that many tenths of a second for keyboard input. If a key arrives and PROMPT is non-zero, show a boot: prompt. Else just keep waiting silently.
  4. After timeout, commit to the chosen label.
  5. TFTP the label’s KERNEL, INITRD (if set), FDT (if set). Apply FDTOVERLAYS (if set).
  6. Hand off via bootm with the APPEND line as the kernel cmdline.

If DEFAULT names a label that doesn’t exist in the file, U-Boot prints a parser error and falls through to the next BOOT_TARGETS entry — same fail-safe as “file absent.” So a typo in the role’s rendering of DEFAULT isn’t catastrophic; the board lands on SD.

Operator decision — it’s a deliberately retained fallback. Remove the staged files when a new LKG promotion happens.

Armbian doesn’t set this by default — see §5.1 for the validation and per-board persistence options. 5. Q1 — A menu entry that loads the kernel from a root device

Rephrased: can pxelinux.cfg name a kernel image that lives on the board’s own SD/eMMC/NVMe instead of being fetched from rb5009 over TFTP?

The honest answer is “yes, two ways, and the second is what you almost certainly want.”

5.1 Interpretation A — kernel bytes literally come from a local device

U-Boot’s PXE bootmeth resolves KERNEL / INITRD / FDT paths via TFTP, against the same server it fetched the .cfg from. There’s no syntax inside pxelinux.cfg that says “KERNEL mmc1:0:vmlinuz” or similar. To load a kernel from a local block device the bootmeth has to not be in control of the load step.

U-Boot does have a directive for handing off to a local boot path inside the .cfg: LOCALBOOT. In PXELINUX’s original semantics, LOCALBOOT 0 means “chain to the local disk’s MBR.” U-Boot’s PXE bootmeth honours LOCALBOOT but with one important caveat documented in U-Boot’s PXE docs: it doesn’t look at the argument — it just runs the localcmd U-Boot environment variable.

Before committing to this design, we need to answer two questions honestly: is localcmd ever set anywhere by default? and how do we persist a value across reboots on a board without SPI flash? Both have implications for whether the LOCALBOOT approach is viable across this collection’s board mix.

5.1.1 Is localcmd ever set by default?

No — neither upstream U-Boot nor the Armbian build framework sets localcmd anywhere. Verified three ways:

SourceSearched forResult
armbian/build localcmd (any occurrence) 0 hits. Not in config/bootenv/rockchip64.txt (only sets verbosity, bootlogo, console), not in config/bootscripts/boot-rockchip64.cmd, not in any U-Boot family include, not in any defconfig override.
All armbian/* org repos localcmd (any occurrence) 34 hits, but every one is the identifier “localcmd” used in unrelated kernel WiFi/SDIO driver code (armbian/linux, armbian/linux-rockchip, armbian/wifi-rtl8852bs). Zero U-Boot env references.

Practically, this means a stock Armbian image — including custom-built ones from this collection’s armbian_build role — boots with localcmd empty. A pxelinux.cfg with LABEL localboot / LOCALBOOT 0 would fail the from_env check, U-Boot would mark the label as failed, and the bootflow framework would move on to the next BOOT_TARGETS entry.

boot/pxe_utils.c u-boot master, label_localboot
localcmd = from_env("localcmd");
if (!localcmd)
    return -ENOENT;
  • Returns to the bootmeth’s label-handling loop, which records the failure and bubbles up to bootflow scan.
  • bootflow scan then advances to the next bootmeth in BOOT_TARGETS — on this collection’s custom Armbian images, that’s mmc1 (SD card’s boot.scr).
  • Net effect: a LOCALBOOT 0 label with no localcmd set is functionally identical to today’s “remove the pxelinux.cfg file.” The board falls through to SD. But the failure path runs through an error return inside U-Boot rather than a clean “no .cfg found” branch, and operator-side debuggability suffers (you have to read the bootflow log to spot the -ENOENT; there’s no “successfully chained to mmc” line).

5.1.2 Persisting localcmd on boards without SPI flash

Setting localcmd at the U-Boot prompt is trivial (setenv localcmd '…' ; saveenv). The hard part is durability across reboots, which depends entirely on where U-Boot saves its env. For this collection’s two-board v1 fleet:

BoardEnv storage (Armbian build defaults)Persists across SD reflash?How this collection writes it today
rock-5b SPI flash at offset 0xc00000, size 0x20000. Confirmed in config/boards/rock-5b.conf (BOOT_SUPPORT_SPI="yes", BOOT_SPI_RKSPI_LOADER="yes"). Yes — SPI is independent of SD. Already done. playbooks/persist_uboot_env.yml (this repo) writes ethaddr + PXE address vars via fw_setenv from Linux. Adding localcmd is one more variable to that playbook.
orange-pi-5-pro Config files declare BOOT_SUPPORT_SPI="yes" and generate an rkspi_loader.img with a uboot_env partition (sectors 8128–8191) — but that SPI image is only used if an operator manually writes it to SPI. Standard Armbian SD deployment (which this collection uses) leaves the SPI untouched; the running U-Boot is loaded from the SD card’s boot area and its env partition is on the SD card. No — re-flashing the SD card destroys it. Not done. There’s no equivalent persist-env playbook for orange-pi-5-pro; the assumption upstream of the collection has been that orange-pi-5-pro’s env is read-only at runtime.

Two corollaries for the no-SPI case (orange-pi-5-pro and any future board that doesn’t deploy with SPI written):

  1. fw_setenv from Linux can work in principle, but requires /etc/fw_env.config pointing at the correct SD-card offsets, and the env survives only as long as that SD card does. Two same-model boards built from the same image would each need their env written once, and a recovery operation that wipes/reflashes the SD card loses the value. The flimsiness undermines the whole “control surface lives on rb5009” model.
  2. The robust route is a compile-time default, injected via the Armbian U-Boot patch table. The CONFIG_EXTRA_ENV_SETTINGS macro in U-Boot’s board header file is concatenated into the env at first boot — if it carries localcmd=bootflow scan mmc1\0 by default, every freshly-built image has the value, no per-board write needed. The armbian_build role already patches U-Boot at this layer (the PXE-first BOOT_TARGETS reorder; see uboot-armbian-build-explainer.html), so adding a one-line localcmd default would be a structurally identical patch.

Either route requires picking a target macro and a target file in the U-Boot source tree, gating per-board, and integrating with this collection’s existing build patch mechanism (the armbian_build_userpatches contract). §5.1.5 walks the complete compile-time implementation against orange-pi-5-pro; §5.1.6 covers the runtime alternative for completeness and explains why it isn’t recommended.

5.1.3 The pxelinux LABEL once localcmd is in place

flash:/sbc/pxelinux.cfg/01-<MAC> — localboot LABEL
LABEL localboot
  MENU LABEL Chain to local SD bootflow
  LOCALBOOT 0
  • Three lines. No kernel/initrd/dtb of its own.
  • Setting DEFAULT localboot makes the board PXE-fetch the .cfg from rb5009, parse it, take the LOCALBOOT path, run ${localcmd}, and from there the SD’s standard boot.scr takes over.
  • End result: kernel + initrd + dtb come from the SD card’s /boot exactly as they would if rb5009 weren’t in the picture. The PXE-fetch step on every boot adds ~1 s of TFTP for the .cfg before the local boot starts.
  • The 0 argument to LOCALBOOT is honoured for PXELINUX-compat but ignored by U-Boot — the whole local-boot intent is in the localcmd env var, not in the directive’s argument.

5.1.5 Implementing the compile-time default on orange-pi-5-pro

This subsection is the full how-to for adding a baked-in localcmd to the orange-pi-5-pro U-Boot binary that this collection’s armbian_build role produces. Every step is keyed to existing repo machinery — there’s no new role, no new build artefact, no new control-plane state. The patch lands as one more entry in the same build_userpatches_common list that already carries the PXE-first BOOT_TARGETS rewrite.

5.1.5.1 Where the env default lives in U-Boot

Across modern rk3588 U-Boot trees the relevant macro is named CFG_EXTRA_ENV_SETTINGS (it was CONFIG_EXTRA_ENV_SETTINGS before the v2022.10 macro rename — both forms exist in the wild, and the sed in §5.1.5.2 matches either). On U-Boot v2025.10 — the tag Armbian’s mainline branch (current / edge) pins for orange-pi-5-pro — the macro is defined in:

include/configs/rk3588_common.h u-boot v2025.10, family-level
#define CFG_EXTRA_ENV_SETTINGS                  \
        "fdtfile=" CONFIG_DEFAULT_FDT_FILE "\0" \
        ENV_MEM_LAYOUT_SETTINGS                 \
        ROCKCHIP_DEVICE_SETTINGS                \
        "boot_targets=" BOOT_TARGETS "\0"
  • This file is shared by every rk3588 board — patching it once seeds the env on every rk3588 board this collection builds. Per-board gating happens at the bash level inside the hook (§5.1.5.2), not in the C header.
  • Each segment is a null-terminated string literal; the preprocessor concatenates them into one long blob that U-Boot uses as the initial env when SPI / mmc env is empty or invalid.
  • The "boot_targets=" BOOT_TARGETS "\0" trailing segment is what U-Boot uses as the runtime boot_targets env — separate from the compile-time BOOT_TARGETS macro the existing PXE-first hook rewrites in rockchip-common.h. Don’t confuse them: BOOT_TARGETS (the macro) feeds boot_targets (the env var); the PXE-first patch changes the former, this patch adds a sibling env var.

The Armbian vendor branch for orange-pi-5-pro uses orangepi-xunlong/u-boot-orangepi at v2017.09-rk3588, which pre-dates the macro rename and still uses CONFIG_EXTRA_ENV_SETTINGS (and a different per-board header file layout entirely). This collection’s orange-pi-5-pro builds run on the mainline branch — Armbian’s current / edge — so this section targets v2025.10. The sed pattern in the next subsection is written to match either form so a future pin bump doesn’t silently fail.

5.1.5.2 The hook function

This collection’s existing PXE-first patch lives in build_userpatches_common inside playbooks/build_image.yml as a { dest, content } entry where dest is config/sources/families/rockchip-rk3588.conf. The armbian_build role drops that file into <armbian_build_cache_dir>/build/userpatches/<dest>, and Armbian’s source_family_config_and_arch() sources both the in-tree family file and the userpatches overlay — so anything defined in our overlay is additive, not replacement.

Inside the overlay we register a bash function whose name matches an Armbian extension-manager hook point. The pre_config_uboot_target__<sort>_<label> family of names hooks just before U-Boot’s defconfig is materialised, with the U-Boot source already checked out — exactly the moment to sed a header file. The __999_ prefix is the same priority trick the existing PXE-first hook uses (extension-manager sorts hooks numerically; 999 wins over Armbian-internal hooks which auto-prefix to 500_).

playbooks/build_image.yml add to build_userpatches_common
build_userpatches_common:
  - dest: "config/sources/families/rockchip-rk3588.conf"
    content: |
      # ... existing pre_config_uboot_target__999_pxe_first() and
      # post_family_config_branch_edge__999_rock5b_uboot_v2026_04()
      # hooks remain as today (omitted for brevity) ...

      # Seed CFG_EXTRA_ENV_SETTINGS with a compile-time `localcmd`
      # default so a pxelinux.cfg LABEL with `LOCALBOOT 0` chains to
      # the SD's boot.scr instead of returning -ENOENT.
      #
      # Per-board gating: only boards listed below get the patch. This
      # is opt-in — rock-5b doesn't need it (SPI env, persist_uboot_env.yml
      # handles it at runtime) and adding boards to the list is a
      # deliberate choice, not a default-on for the whole family.
      function pre_config_uboot_target__999_localcmd_default() {
          local -A boards_localcmd=(
              [orangepi5pro]="bootflow scan mmc1"
              # Add other no-SPI boards here as they're onboarded.
          )

          [[ -z "${boards_localcmd[${BOARD}]:-}" ]] && return 0

          local cmd="${boards_localcmd[${BOARD}]}"
          local header="include/configs/rk3588_common.h"

          # Sanity check — fail loudly if the upstream macro has been
          # renamed or moved. Pinning U-Boot versions across rebases is
          # the operator's job; this hook's job is to refuse to silently
          # do nothing.
          if ! grep -qE '\b(CFG|CONFIG)_EXTRA_ENV_SETTINGS\b' "${header}"; then
              display_alert "${BOARD}" \
                  "CFG_EXTRA_ENV_SETTINGS not found in ${header} — patch skipped" "wrn"
              return 0
          fi

          # Idempotency — if a previous build of the same checkout has
          # already injected the line, don't double-inject.
          if grep -q '"localcmd=' "${header}"; then
              display_alert "${BOARD}" \
                  "localcmd default already present in ${header}" "info"
              return 0
          fi

          # Inject the line immediately after the first segment of
          # CFG_EXTRA_ENV_SETTINGS. Works on both the v2022.10+ macro
          # name (CFG_EXTRA_ENV_SETTINGS) and the legacy form
          # (CONFIG_EXTRA_ENV_SETTINGS) — sed is anchored on the
          # *_EXTRA_ENV_SETTINGS substring.
          sed -i -E \
              "/^#define[[:space:]]+(CFG|CONFIG)_EXTRA_ENV_SETTINGS/,/[^\\\\]$/{
                  s|(ENV_MEM_LAYOUT_SETTINGS[[:space:]]*\\\\)|\"localcmd=${cmd}\\\\0\" \\\\\n        \\1|
              }" "${header}"

          display_alert "${BOARD}" \
              "patched ${header}: localcmd default = '${cmd}'" "info"
      }
  • Per-board associative array instead of a global default — onboarding a new no-SPI board is one line. rock-5b is not in the array; the hook short-circuits for it and the SPI-env path (persist_uboot_env.yml) keeps owning rock-5b’s env.
  • Anchored on ENV_MEM_LAYOUT_SETTINGS — the sed inserts the new line right before that token, which is line 2 of the macro definition on v2025.10. If the macro layout changes upstream the grep guard catches it; if the token moves to a different line the insertion still lands inside the macro (which is what matters — anywhere inside is fine).
  • \\\\0 in the sed — that’s a literal \0 (null terminator) escaped through bash heredoc → bash sed → C preprocessor. Each layer eats a backslash. The C output must read "localcmd=bootflow scan mmc1\0".
  • Idempotency check on grep -q '"localcmd=' — same defensive pattern the existing PXE-first hook uses for its CONFIG_PCI_INIT_R append.
  • display_alert is Armbian’s build-log primitive — output shows up in the build console. Operator-visible at build time which is the right surface to spot “the patch didn’t land.”
5.1.5.3 Wiring into build_image.yml

No new entry — the hook lives inside the existing { dest, content } for config/sources/families/rockchip-rk3588.conf. The content field is a heredoc that concatenates every hook function this collection wants registered against the rk3588 family; add the new function alongside the existing pre_config_uboot_target__999_pxe_first and post_family_config_branch_edge__999_rock5b_uboot_v2026_04. Armbian’s extension manager auto-discovers all pre_config_uboot_target__* functions sourced into the family file and runs them in sort order.

Once the function is in place, running ansible-playbook playbooks/build_image.yml rebuilds the image and the resulting .img.xz carries the patched U-Boot. The role’s compute_inputs.yml task already hashes armbian_build_userpatches into the manifest’s patch_hash, so the change invalidates the “skip rebuild” check and a new build is triggered automatically. No -e armbian_build_force=true needed.

5.1.5.4 Determining the right MMC index per board

bootflow scan mmc1 is right for orange-pi-5-pro. It is not automatically right for every no-SPI rk3588 board. The index is whichever mmc dev N in the U-Boot device tree corresponds to the SD slot, and that depends on which other MMC controllers the U-Boot DT exposes:

BoardU-Boot DT MMC nodesSD lands atSource of truth
orange-pi-5-pro eMMC slot + SDIO + SD mmc 1 CLAUDE.md repo-level convention; verify with mmc list at the U-Boot prompt on a freshly-built image.
orangepi5 (non-pro) SD only mmc 0 Per CLAUDE.md “SBC ecosystem reality” — the SD-only DT lands SD at index 0.
(hypothetical) board with eMMC + SD, no SDIO eMMC + SD typically mmc 1 Per-board — must be verified at the U-Boot prompt before pinning.

This is why the hook takes the command string as data in the per-board associative array, not a hard-coded value: the array entry for a new board is the operator’s contract that they’ve verified mmc list for that board. A wrong index isn’t catastrophic — bootflow scan mmc5 on a board without an mmc5 just reports “no bootflow found” and the bootflow framework moves to the next entry in BOOT_TARGETS — but it is wasted boot time and a confusing failure mode.

5.1.5.6 Operational notes
Interaction with saveenv
CFG_EXTRA_ENV_SETTINGS seeds the env when the persistent env (SPI on rock-5b, SD-card env partition or nowhere on orange-pi-5-pro) is empty / corrupt / invalid. Once a user runs saveenv at the U-Boot prompt, the saved env wins and the compile-time default becomes the fallback. On orange-pi-5-pro with no SD env partition explicitly written, U-Boot has nowhere to save to — so the compile-time default is effectively the only value the variable ever takes, on every boot. That’s exactly the property we want for fleet automation: the value is determined by the U-Boot binary in .img.xz and survives reflashes.
SD reflash behaviour
Reflashing the SD card with the same .img.xz replaces the U-Boot bytes with the patched ones again — localcmd is back in place. Reflashing with a different Armbian build (e.g. a stock Armbian image, or one built without this hook) removes the default and LOCALBOOT 0 reverts to the -ENOENT → mmc1 fall-through. Document this explicitly anywhere the fleet’s recovery procedure says “flash the SD with a stock image to start over” — the answer might still be fine (you’re recovering, not relying on LOCALBOOT semantics), but it’s worth knowing.
Multi-board fleets
The hook patches once per build, but the resulting .img.xz is one image flashed to N boards of the same model — every board has the same compile-time default. This is the right granularity for the always-netboot model: per-board variation lives in pxelinux.cfg on rb5009 (the runtime mode selector), per-model variation lives in the built image (localcmd, kernel cmdline defaults, BOOT_TARGETS).
What if the operator wants per-board localcmd?
Two options if it ever comes up. (1) Per-board built images — expensive, fragments the build farm. (2) Inject a small first-boot systemd unit into build_userpatches that calls fw_setenv from Linux with a value derived from the host’s inventory entry — moves the per-board state from inventory through the first-boot path. For a fleet of two boards of one model, neither is justified; if the fleet expands and the requirement appears, this is where to look. (3) A simpler version of the requirement “every board chooses a different SD index or NVMe” can be served by the U-Boot bootflow framework itself: localcmd=bootflow scan (no argument) scans everything in BOOT_TARGETS and picks the first one that works — no per-board pinning needed.
Interaction with the existing PXE-first patch
Both hooks are pre_config_uboot_target__999_*. Armbian’s extension manager runs them in alphabetical order after the 999 sort prefix — so __999_localcmd_default runs after __999_pxe_first (alphabetical “l” > “p” — wait, “l” < “p”, so actually localcmd sorts before pxe_first). Order doesn’t matter functionally here — they patch different files (rk3588_common.h vs rockchip-common.h + the defconfig) — but if a future patch lives in the same file as an earlier one, double-check the sort order or rename to force explicit ordering (__999a_, __999b_).

5.1.6 Runtime alternative — fw_setenv into the SD env partition

For completeness: the runtime path is technically achievable on orange-pi-5-pro and worth documenting so an operator considering it understands the trade-offs. It is not recommended for fleet use under the always-netboot model.

Armbian’s SD image lays out the boot region with a small reserved env partition at a fixed offset (the offset comes from the family’s BOOT_FAT_OFFSET_KB / UBOOT_ENV_* conventions; verify on the specific image with parted -l on the flashed SD before relying on it). Linux can write to that partition through the standard fw_setenv tool from u-boot-tools, given a correct /etc/fw_env.config:

/etc/fw_env.config orange-pi-5-pro, illustrative
# Device       Offset      Env size        Flash sector size       Number of sectors
/dev/mmcblk1   0x3F8000    0x8000          0x200                   64
  • The offsets above are illustrative, not authoritative. The real offsets for any given Armbian image depend on the build’s UBOOT_ENV_OFFSET / UBOOT_ENV_SIZE at compile.sh time. Read them off the running U-Boot binary with grep ENV_OFFSET on the build artefacts, or inspect the flashed SD with a hex tool. A wrong offset turns fw_setenv into a corruption-on-write tool. Do not copy these numbers without verification.
  • /dev/mmcblk1 assumes the SD lands at mmcblk1 from Linux’s perspective — same per-board variation that affects bootflow scan mmcN (§5.1.5.4) applies here. Verify with lsblk after flashing.
The runtime “persist localcmd” playbook (sketch)
# playbooks/persist_uboot_env_sd.yml — analogue of persist_uboot_env.yml
# but targeting boards whose U-Boot env lives on the SD card, not SPI.

- name: Persist U-Boot localcmd via fw_setenv on no-SPI boards
  hosts: orange_pi_5_pro    # explicit per-board gate, not a generic group
  become: true
  tasks:
    - name: Ensure u-boot-tools is installed
      ansible.builtin.apt:
        name: u-boot-tools
        state: present

    - name: Install /etc/fw_env.config
      ansible.builtin.template:
        src: fw_env.config.orange-pi-5-pro.j2
        dest: /etc/fw_env.config
        owner: root
        group: root
        mode: '0644'

    - name: Set localcmd via fw_setenv
      ansible.builtin.command:
        argv:
          - fw_setenv
          - localcmd
          - bootflow scan mmc1
      register: _fw_setenv
      changed_when: "'== ' in _fw_setenv.stdout or _fw_setenv.rc == 0"

    - name: Verify localcmd is set
      ansible.builtin.command: fw_printenv localcmd
      register: _fw_printenv
      changed_when: false
      failed_when: "'localcmd=bootflow scan mmc1' not in _fw_printenv.stdout"

Why this is the wrong answer for a fleet:

  • State is per-board, not per-image. Reflashing the SD card with the same image wipes the value. Recovery procedures that include “flash a fresh image” have to also re-run this playbook, and there’s no compile-time guarantee that won’t be forgotten.
  • The offset table in /etc/fw_env.config is Armbian-build-specific. If Armbian changes its env-partition layout (which has happened across releases), every board’s /etc/fw_env.config has to be updated in lockstep with the image bump.
  • The control-plane invariant moves off rb5009. One of the points of the always-netboot model is “rb5009 is the only thing that decides what mode a board boots.” If localcmd has to be runtime-poked per-board, the control plane fragments — and a board whose env got corrupted (or whose SD card was replaced) will silently fall through on the next LOCALBOOT 0 with no visible diff in rb5009’s state.
  • It requires SSH access to a board already running. For a board that’s not yet bootstrapped (or that’s in LOCALBOOT and the SD’s root won’t mount), there’s no shell to write the env from. Bootstrapping circularity.

If you do want a runtime path anyway — say, for ad-hoc experiments before committing to the compile-time patch — the playbook sketch above is the right shape, and the file layout mirrors playbooks/persist_uboot_env.yml’s rock-5b equivalent. Treat it as a development convenience, not a production mechanism.

The honest take: Interpretation A is viable across the fleet, but only on rock-5b is it cheap. If that’s not appetising, the degenerate path (rely on the -ENOENT→mmc1 fall-through) works as a no-effort backstop — treat it as “LOCALBOOT semantically marks the LABEL as ‘please fall through’” rather than “LOCALBOOT actively boots local.”

5.2 Interpretation B — TFTP the kernel but root from a local device

This is the “locally-rooted, always-netbooted” pattern sketched in pxelinux-cfg-explainer §9. The kernel + initrd + dtb come from rb5009 (1.5 KB .cfg + ~12 MB vmlinuz + ~40 MB initrd + ~50 KB dtb in total over TFTP), and the rootfs is on the board’s NVMe / eMMC / SD.

Worth being explicit: this is the same kernel image you’d boot if it came off the SD card’s /boot/vmlinuz — same bytes, same kernel modules, same config. The only difference is where the file came from on the way into RAM. Once the kernel is decompressed and running, there is no distinction between “a TFTP-fetched kernel” and “a kernel loaded by U-Boot from mmc” — they’re identical kernel processes.

nvmeroot LABEL — kernel via TFTP, rootfs on NVMe
LABEL nvmeroot
  MENU LABEL Armbian on NVMe (orange-pi-5-pro-01)
  KERNEL armbian/orange-pi-5-pro/vmlinuz
  INITRD armbian/orange-pi-5-pro/initrd.img
  FDT    armbian/orange-pi-5-pro/board.dtb
  APPEND root=PARTUUID=8a7c1234-01 rootfstype=ext4 rootwait rw console=ttyS2,1500000n8
  • No ip=dhcp, no nfsroot=, no root=/dev/nfs. The kernel doesn’t need a network address to mount its own NVMe.
  • Identical KERNEL/INITRD/FDT paths to the nfsroot label — they pull the same Armbian build bytes. Only the APPEND differs.
  • This is the answer to “how do I take advantage of central kernel management without locking the rootfs to NFS”: split the channels. Kernel = network, rootfs = local. MAAS and Tinkerbell’s production-fleet patterns are this exact split (see §9.2 of the cfg explainer).

5.4 Aside — Armbian has no “installer cmdline”

A natural-looking shape for the installer LABEL would be to put the install intent on the kernel cmdline — e.g. armbian.install_target=/dev/nvme0n1. This is not a real Armbian convention. The actual installer is /usr/bin/armbian-install, a Bash + whiptail script that runs interactively from a booted system; it reads /proc/cmdline only to display the current root= and rootfstype=, not to be steered. Grepping armbian/build for armbian.install_target, armbian_install, or any equivalent namespaced cmdline arg returns zero hits.

So “installer” in this design isn’t a LABEL that carries the install plan in its APPEND — it’s just a separate NFS rootfs the board boots into so an Ansible play (the provision_nvme_rootfs role in §6.3) can do the actual partitioning + copy + PARTUUID capture over SSH. The “one-shot” flavour comes from the playbook flipping boot_mode away from installer on success, not from anything the kernel does. This keeps the design honest with upstream Armbian and locates the install logic in code we control rather than fictional cmdline conventions.

6. Q2 — Workflow: NFS → prepare NVMe → reboot rooted on NVMe

The end-to-end story for taking a board from “just flashed, PXE-boots NFS root” to “PXE-boots a TFTP kernel, roots on its own NVMe.” This is the canonical multi-step orchestration the always-netboot model unlocks — under v1, there’s no intermediate state for an Ansible play to run against.

6.2 Concrete playbook shape

Hypothetical playbook a user would run:

playbooks/promote_to_nvme.yml hypothetical
---
# Take a board from NFS root to NVMe root.
# Idempotent — a board already on NVMe lands at step 4 with no changes.
#
# Usage:
#   ansible-playbook playbooks/promote_to_nvme.yml \
#     --limit orange-pi-5-pro-01

# Step 1 — guarantee the board is up via NFS root so the rest of the

# does not get re-cycled.
- name: Ensure board is on NFS root
  hosts: boards
  roles:

      vars:
        boot_mode: nfs

# Captures the resulting PARTUUID as a host fact.
- name: Provision NVMe rootfs
  hosts: boards
  tasks:
    - name: Partition and format /dev/nvme0n1
      include_role:
        name: provision_nvme_rootfs  # new role; see below

    - name: Persist rootfs_partuuid back into inventory
      include_role:
        name: persist_host_fact
      vars:
        fact_name: rootfs_partuuid

- name: Switch board to NVMe boot mode
  hosts: boards
  roles:
    - role: board_boot_state
      vars:
        boot_mode: nvme        # new contract; replaces boot_state: pxe|disk
        cycle_board: true
        verify_state: true
  • Three plays, one playbook. Each play is a discrete state transition; if step 2 fails, the board is still on NFS root and the operator can fix and re-run.
  • Step 1’s cycle_board guard is the idempotency hook — re-running the playbook on a board that’s already on NVMe doesn’t accidentally PoE-cycle it back to NFS.
  • Step 3 calls the same board_boot_state role today’s enable_netboot.yml uses — same retry stack, same verify play. The only thing that’s new is what “verify” means (see §6.4).

6.3 The new role: provision_nvme_rootfs

This is the only piece that doesn’t exist today. What it would do:

  1. Run parted /dev/nvme0n1 to create a GPT + a single ext4 partition. (Or a small esp + ext4 if the operator wants UEFI-style headroom; orthogonal.)
  2. mkfs.ext4 on the new partition.
  3. Mount the partition at a staging directory.
  4. Use rsync -aHAX from / (the NFS rootfs) to the staging directory. Skip /dev /sys /proc /run /tmp and the staging dir itself.
  5. Patch /etc/fstab on the staging copy to reference the new PARTUUID instead of NFS.
  6. Unmount. Capture the new partition’s PARTUUID from blkid.
  7. Register the PARTUUID as a host fact for the next play.

This is a single, focused role. It has one job, takes the board as input, produces a PARTUUID as output. Same style as bootstrap_armbian: agnostic to why the caller wants NVMe set up, just enforces the state.

6.4 Verify needs to grow up

Today’s verify_state.yml asserts fstype in ['nfs', 'nfs4'] for boot_state=pxe and the inverse for boot_state=disk. Under always-netboot, the verify step needs a per-mode expectation:

roles/board_boot_state/tasks/verify_state.yml hypothetical, mode-aware
- name: Capture root mount
  set_fact:
    _root_fstype: "{{ ansible_mounts | selectattr('mount', 'equalto', '/')
                                     | map(attribute='fstype') | first }}"
    _root_device: "{{ ansible_mounts | selectattr('mount', 'equalto', '/')
                                     | map(attribute='device') | first }}"

- name: Per-mode rootfs expectations
  set_fact:
    _expected: "{{ boot_mode_expectations[boot_mode] }}"

# boot_mode_expectations lives in vars/boot_mode_expectations.yml:
#   nfs:        { fstype_in: [nfs, nfs4],                       device_match: '.*' }
#   nvme:       { fstype_in: [ext4, btrfs, xfs],                device_match: '^/dev/nvme[0-9]n[0-9]p[0-9]' }
#   emmc:       { fstype_in: [ext4, btrfs, xfs],                device_match: '^/dev/mmcblk[0-9]p[0-9]' }
#   sd:         { fstype_in: [ext4, btrfs, xfs],                device_match: '^/dev/mmcblk[0-9]p[0-9]' }
#   recovery:   { fstype_in: [tmpfs, rootfs, ramfs],            device_match: '.*' }
#   installer:  { fstype_in: [nfs, nfs4],                       device_match: '.*' }
#   lkg:        # same as the host's pre-flip mode; assert
#              # ansible_kernel matches lkg_kernel_version
#   localboot:  # delegate to whatever the SD bootflow lands on
#              # — assert ansible_kernel exists and uname -m is the expected arch

- name: Assert rootfs matches mode
  assert:
    that:
      - _root_fstype in _expected.fstype_in
      - _root_device is match(_expected.device_match)
  • The current binary assertion becomes a small table of per-mode constraints. Adding a new mode is a new row, not a new conditional branch.
  • Distinguishing sd from emmc at verify time can be tricky — both land on mmcblk* and the index ordering is board-dependent. One option is to verify against PARTUUID directly: blkid /dev/$(findmnt -no SOURCE /) -s PARTUUID must equal the inventory’s declared PARTUUID for that mode.

7. Q3 — Useful menu entries and how to manage them

Four design choices behind the catalog in §4:

7.1 Render everything the host could plausibly need; gate by DEFAULT

Rather than re-render the file every time the operator wants to switch modes, render every LABEL the host has the prerequisites for, and let DEFAULT pick. The cost is small (kilobytes on rb5009’s flash, milliseconds parsing); the benefit is large (an operator on the serial console during boot can pick a different LABEL without any control-node interaction, and an automation step that wants to bounce the board between two modes only has to re-render one line).

7.2 One inventory variable selects DEFAULT; the rest fall out of host state

Per-host inventory carries a single boot_mode (free-form string matching one of the role’s known modes), plus the data each mode needs as separate variables:

boot_mode
Names the DEFAULT label. Required.
rootfs_partuuid
Used by APPEND for the nvme / emmc modes (whichever block device the operator considers the primary).
sd_partuuid
Used by APPEND for the sd mode. Kept separate so a board can have NVMe primary and SD-as-recovery.
lkg_kernel_version
Names the versioned kernel filename the lkg LABEL TFTPs from rb5009. Optional — when unset the LABEL is suppressed.
fdt_overlays
(Bonus) List of per-host DT overlays to apply. Becomes FDTOVERLAYS in each label that mounts a kernel. See pxelinux-cfg-explainer §9.6.

Variables that aren’t set make their LABEL un-renderable. A board with no rootfs_partuuid gets a file without LABEL nvmeroot in it — so a typo in boot_mode on that host (boot_mode: nvme) renders DEFAULT nvmeroot pointing at a missing label, U-Boot prints “Couldn’t find label,” and falls through to SD via bootflow scan. Fail-safe.

7.3 Adding a new mode

Concrete checklist for adding (hypothetical example) a usbroot mode that boots a TFTP kernel and roots on a USB stick:

  1. Append a new {% if hostvars[target_board_host].usb_partuuid is defined %}LABEL usbroot ...{% endif %} block in pxelinux_cfg.j2.
  2. Add a row to boot_mode_expectations in vars/boot_mode_expectations.yml (e.g. usb: { fstype_in: [ext4], device_match: '^/dev/sd[a-z][0-9]' }).
  3. Document the new variable (usb_partuuid) in inventory/group_vars/boards.yml ’s comment header.
  4. That’s it.

The role’s public contract (boot_mode: <string>) doesn’t change. The state machine widens; nothing else moves.

7.4 Removing a mode

Deleting a LABEL block from the template removes it from every newly-rendered file. Hosts with that mode as their boot_mode will render a DEFAULT pointing at a missing label — they fall through to SD on next cycle. An operator-friendly version of the removal would fail in the role at render time if any inventory host still references the mode, so the operator catches it before a PoE cycle.

8. Q4 — Extending the model for a last-known-good kernel

This section deliberately doesn’t propose implementation — it describes the shape of the extension and the trade-offs an operator would need to weigh in to commit to it.

8.1 Kernel-staging today

stage_netboot_assets.yml stages three files per model on rb5009:

flash:/sbc/armbian/<model>/ today
vmlinuz       # latest only, force-removed and replaced on each stage
initrd.img    # same — paired bytes with vmlinuz
board.dtb     # rarely changes; force-removed and replaced on each stage

Pxelinux.cfg references these via the versionless filename (armbian/<model>/vmlinuz). Updating the kernel is one operation: stage_netboot_assets.yml overwrites the three files; every board with that model’s pxelinux.cfg picks up the new bytes on next PoE cycle. There’s no “previous kernel” preserved anywhere.

8.2 Versioned-staging shape

An “LKG kernel” LABEL needs the previous kernel to still exist as fetchable bytes on rb5009. The minimal shape:

flash:/sbc/armbian/<model>/ hypothetical, versioned
vmlinuz                  # symlink-equivalent: re-uploaded on each stage
initrd.img               # ditto
board.dtb

vmlinuz-6.10.0           # current kernel, also kept under its versioned name
initrd.img-6.10.0
vmlinuz-6.6.0            # previous kernel, kept around for lkg
initrd.img-6.6.0

# /lib/modules/<version>/ trees live on the NFS server's
# per-host rootfs clones, plus a parallel pinned copy under
# nfs_rootfs_path/_kernel-modules/<version>/ that the lkg
# rootfs can chroot-style mount or that the NFS-rooted board
# can keep alongside its current modules tree.
  • RouterOS flash is small (~16 MB free after the v1 staging). Two kernels + two initrds = ~80–100 MB. The flash budget is the dominant constraint here; it’d need verification on your specific rb5009 before committing.
  • An alternative for tight flash budgets: keep only one alternate kernel under flash:/sbc/armbian/<model>/_lkg/, pruned on every promotion.

The lkg LABEL block then references the versioned filenames:

The lkg LABEL hypothetical
LABEL lkg
  MENU LABEL Last-known-good kernel (nvme rootfs, kernel {{ lkg_kernel_version }})
  KERNEL armbian/{{ board_model }}/vmlinuz-{{ lkg_kernel_version }}
  INITRD armbian/{{ board_model }}/initrd.img-{{ lkg_kernel_version }}
  FDT    armbian/{{ board_model }}/board.dtb
  APPEND root=PARTUUID={{ hostvars[target_board_host].rootfs_partuuid }} rootfstype=ext4 rootwait rw console={{ board_configs[board_model].console }}
  • lkg_kernel_version is per-host or per-model — typically per-model (every board of a model shares the LKG pin), but per-host gives finer-grained control if one board is on a bisect.
  • The same APPEND as nvmeroot — same rootfs, just an older kernel.
  • The DTB is left at the versionless path because Armbian DTBs change far less often than kernels. If you need a versioned DTB for a regression bisect, switch this LABEL’s FDT line to board.dtb-{{ lkg_kernel_version }} and stage that file alongside.

8.3 Lifecycle: who decides what “last-known-good” is

The LKG promotion lifecycle is the part with real design content. Two models suit different operational styles:

Manual promotion
Operator runs playbooks/stage_netboot_assets.yml with -e promote_current_to_lkg=true before staging a new kernel. The stage step renames the existing vmlinuz-<current> + initrd.img-<current> to be the new LKG, drops the previous LKG, and updates the inventory’s lkg_kernel_version. Predictable; no surprises.
Auto-promotion on health check
A cluster-side observer (cron, watchdog, K8s readiness probe, etc.) decides “all boards have been on the current kernel for at least N hours and are healthy” and writes the promotion via Ansible inventory mutation. More moving parts; closer to the Sidero/Tinkerbell production pattern.

8.5 Why this is an extension, not a rewrite

Notice: every change is additive. None of the existing roles change behaviour for hosts that don’t opt into LKG. The template gets a new conditional block; the stage role keeps a few extra files; verify gets a new branch. board_boot_state’s public contract grows by one optional input. A board with no lkg_kernel_version doesn’t render the LABEL, the template falls through unchanged, the verify play takes the existing branches. The extension lands cleanly because the always-netboot model already gave us the structural piece — multi-LABEL files driven by inventory — without baking LKG into the core.

10. Gotchas & migration notes

10.1 Don’t change req-filename regex shape. The /ip tftp row still uses req-filename=".*01-<MAC>" — see Gotcha §10.5 of pxelinux-cfg-explainer. The file the row points at has more content under the always-netboot model, but the on-the-wire request from U-Boot is unchanged.
10.2 APPEND must still be exactly one line per LABEL. Every LABEL block carries its own APPEND. The single-line constraint is per-APPEND — see pxelinux-cfg §10.1. If you find yourself wanting two lines, you almost certainly want a separate LABEL.
10.3 “Disable netboot” isn’t deletion any more. Under v1, the absence of the pxelinux.cfg file is the disabled state. Under always-netboot, an absent file would be a decommissioned host. Day-to-day disable becomes boot_mode=localboot. The collection should keep disable_netboot.yml as a compatibility alias for at least one minor version; otherwise an operator’s muscle memory tears down their host’s pxelinux.cfg during the migration window.
10.4 PARTUUID stability matters more than today. Today’s NFS-root flow doesn’t reference PARTUUID anywhere. Under always-netboot, the nvme/emmc/sd modes embed PARTUUID into APPEND, which means a board that gets its local rootfs reformatted needs its inventory PARTUUID re-captured before the next render. Prefer PARTUUID (lives in the partition table, survives mkfs) over UUID (in the filesystem superblock, changes on mkfs). The provision_nvme_rootfs role’s last step would be to set this fact for the operator.
10.5 TIMEOUT means every boot waits. Setting TIMEOUT 50 (5.0 s) means the board pauses for 5 seconds during PXE every time it powers on. That’s acceptable for a small fleet but multiplies across the per-board TFTP-fallback latency (~5–10 s, cfg §3). Setting TIMEOUT 1 (0.1 s) is the right trade-off for most fleets — fast enough that boot times aren’t affected, slow enough that an alert operator on the serial console can interrupt. Set TIMEOUT 0 if you never want operator override (saves the fractional second; trades it for less in-band recovery surface).
10.6 Migration: don’t flip mid-cycle. The cleanest rollout path is: keep v1 in place; ship the new template gated on a collection-level feature flag (always_netboot_model: true); let operators try it on one board at a time. The same per-board pxelinux.cfg file gets overwritten with the multi-LABEL shape on next enable_netboot.yml run, but the file’s wire-level filename + path doesn’t change, so U-Boot doesn’t care. Operators who don’t flip the flag keep the v1 behaviour unchanged. After a release of confident dual-mode operation, drop the flag and the old template.
10.7 PSU-margin hardware failures don’t change. Same caveat as the locally-rooted variant in cfg §9.5. The five hardware failure signatures in docs/architecture.md “Known issues” are PSU/SoC-level and orthogonal to where the rootfs lives. Verbose APPEND (see today’s pxelinux_verbose flag) still works as a diagnostic — it just becomes a per-LABEL choice rather than a global toggle.
