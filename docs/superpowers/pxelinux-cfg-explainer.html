pxelinux.cfg in this collection — a one-pass explainer

What U-Boot is fetching when it reaches for pxelinux.cfg/01-<MAC>, what each line of the rendered file does, how this collection writes and removes those files on rb5009, and what would change if you used the same mechanism to boot from a non-network rootfs. Scoped to the v1 invariant — per-board pxelinux.cfg presence on rb5009 is the only mode switch between SD and NFS root.

1. Where pxelinux.cfg comes from

The pxelinux.cfg/<name> convention started with PXELINUX, a member of the SYSLINUX family — an x86 network bootloader from the late 1990s that PXE-booted BIOS PCs in classrooms and datacentres. PXELINUX read a small text config file off a TFTP server and used it to decide which kernel + initrd to boot and what kernel cmdline to pass. The file format proved so compact and useful that U-Boot grew a PXE bootmeth that consumes the same format, identical filenames and all. ARM SBCs that boot via U-Boot can therefore reuse the decades-old PXELINUX config grammar without running PXELINUX itself.

In this collection nothing called PXELINUX is running anywhere. The piece on the SBC is U-Boot 2025.10’s built-in PXE bootmeth. All it borrows from PXELINUX is the on-the-wire file format and the filename-search algorithm. The .cfg file isn’t executable code — it’s a tiny declarative document the bootmeth parses to decide what to TFTP next and what cmdline to hand to the kernel.

PXELINUX (the original)
x86 BIOS PXE network bootloader from the SYSLINUX project. Loaded as netboot.xyz.kpxe equivalents via DHCP option 67, runs its own TFTP/menu loop, executes kernels itself.
U-Boot PXE bootmeth (what we use)
A built-in U-Boot feature that imitates PXELINUX’s file format and search order. The bootloader on the SBC is U-Boot — there’s no second-stage loader. U-Boot reads the .cfg, fetches kernel/initrd/DTB itself, applies the APPEND line, and boots Linux.
pxelinux.cfg/<name>
The TFTP-relative path U-Boot looks under for a board-specific config. Each connecting board can get a different file by virtue of its MAC address forming the filename.

2. How U-Boot finds a pxelinux.cfg

Boot-time fetch sequence on a board that’s been flashed with one of this collection’s custom Armbian images (PXE-first BOOT_TARGETS baked into U-Boot — see uboot-armbian-build-explainer.html for why that’s necessary):

2.1 Why does U-Boot TFTP from rb5009 specifically?

Because BOOTP siaddr (the “next-server” field on the DHCP OFFER) points there. U-Boot 2025.10’s PXE bootmeth reads siaddr exclusively for serverip selection — DHCP option 66 / option 67 are parsed but silently ignored for this purpose. next-server on the SBC’s RouterOS network is owned by the operator’s separate igou-ansible repo; this collection asserts the per-model /ip tftp rows on rb5009 exist (plumbing-check preflight), but does not write next-server itself.

3. The 01-<MAC> filename + fallback chain

Inherited verbatim from PXELINUX. The U-Boot PXE bootmeth tries a sequence of filenames under pxelinux.cfg/ and uses the first one that returns successfully. For a board with MAC c0:74:2b:fb:4d:fd and IP 10.10.9.25:

Fallback chain (this MAC + IP) tried in order
pxelinux.cfg/01-c0-74-2b-fb-4d-fd     ← MAC, lowercased, '-' separated, '01-' prefix (ARP type 1)
pxelinux.cfg/0A0A0919                 ← full IP as uppercase hex (10.10.9.25)
pxelinux.cfg/0A0A091                  ← strip the rightmost hex digit ...
pxelinux.cfg/0A0A09                   ← ... until the prefix is gone
pxelinux.cfg/0A0A0
pxelinux.cfg/0A0A
pxelinux.cfg/0A0
pxelinux.cfg/0A
pxelinux.cfg/0
pxelinux.cfg/default-arm-rk3588-evb_rk3588   ← arch + sub-arch defaults
pxelinux.cfg/default-arm-rk3588
pxelinux.cfg/default-arm
pxelinux.cfg/default                  ← last resort
  • This collection only writes the 01-<MAC> form. Everything else 404s, and the bootmeth falls through.
  • When no file matches anywhere in the chain, the bootmeth aborts and U-Boot’s bootflow scan moves on to the next entry in BOOT_TARGETS — which on these images is the SD card (mmc1 / boot.scr). This fall-through is the v1 invariant’s “disable” path: absent 01-<MAC> ⇒ disk boot.
  • The whole 13-file chain costs ~5–10 s of TFTP 404s. Not free, but not slow enough to redesign around.

3.1 How the role computes the filename

roles/routeros_sbc_tftp/tasks/write_pxelinux_cfg.yml :18-21
- name: Compute pxelinux.cfg filename for {{ target_board_host }}
  ansible.builtin.set_fact:
    _pxe_filename: "01-{{ board_mac | lower | replace(':', '-') }}"
  • board_mac is per-host inventory data — typed by the operator at board onboarding.
  • U-Boot is case-insensitive on the MAC hex but expects - separators.

4. Anatomy of this repo’s rendered config

The Jinja template lives at roles/routeros_sbc_tftp/templates/pxelinux_cfg.j2. A rendered example for orange-pi-5-pro-01 on the default (non-verbose) path:

flash:/sbc/pxelinux.cfg/01-c0-74-2b-fb-4d-fd rendered
# pxelinux.cfg for orange-pi-5-pro-01 (orange-pi-5-pro)
# MAC: c0:74:2b:fb:4d:fd
# Verbose diagnostics: False
# Generated by Ansible — do not edit manually.

DEFAULT nfsroot

LABEL nfsroot
  MENU LABEL Armbian NFS Root (orange-pi-5-pro-01)
  KERNEL armbian/orange-pi-5-pro/vmlinuz
  INITRD armbian/orange-pi-5-pro/initrd.img
  FDT    armbian/orange-pi-5-pro/board.dtb
  APPEND root=/dev/nfs nfsroot=10.10.9.213:/mnt/ssd/netboot/rootfs/orange-pi-5-pro-01,nfsvers=3,rw ip=dhcp console=ttyS2,1500000n8 rootwait rw
  • Six lines do the actual work: DEFAULT, LABEL, KERNEL, INITRD, FDT, APPEND.
  • The three TFTP paths (armbian/<model>/...) are per-model, shared by every orange-pi-5-pro-01..N. The nfsroot= path is per-host, pointing at this board’s own writable rootfs clone.
  • The first line (# pxelinux.cfg for ...) is a comment that helps an operator ssh rb5009 / file print contents the file and confirm which board it’s for. Comments are silently ignored by U-Boot’s PXE bootmeth.

4.1 Verbose variant — what an operator gets with -e pxelinux_verbose=true

APPEND line, verbose path same KERNEL/INITRD/FDT
APPEND root=/dev/nfs nfsroot=10.10.9.213:/mnt/ssd/netboot/rootfs/orange-pi-5-pro-01,nfsvers=3,rw \
       ip=dhcp console=ttyS2,1500000n8 rootwait rw \
       earlycon=uart8250,mmio32,0xfeb50000 loglevel=8 ignore_loglevel initcall_debug \
       printk.devkmsg=on systemd.log_level=debug systemd.log_target=console \
       systemd.journald.forward_to_console=1
  • The backslashes above are display-only. On the wire it’s one line — U-Boot does not honour line continuations (see Gotcha §10.1).
  • The role asserts board_configs[board_model].earlycon exists at render time before allowing verbose=true, so the operator gets a clear failure instead of a silently-empty earlycon= arg.

5. Major parameters reference

5.1 The pxelinux directives this collection uses

DirectiveValue (this repo)What it does
DEFAULT nfsroot Names which LABEL block is selected automatically (no menu prompt). Must match a LABEL name exactly.
LABEL nfsroot Begins a bootable entry. Can have multiple LABELs in one file (e.g. nfsroot + recovery + memtest); DEFAULT picks one.
MENU LABEL Armbian NFS Root (...) Human-readable label. Only relevant if you build a menu UI on top; U-Boot logs it during boot for operator visibility.
KERNEL armbian/<model>/vmlinuz TFTP-relative path to the kernel image to load via tftpboot. Resolved against the same TFTP root as the .cfg file.
INITRD armbian/<model>/initrd.img TFTP-relative path to the initial ramdisk. Linux uses it to mount the real rootfs (in this collection, an NFS export).
FDT armbian/<model>/board.dtb TFTP-relative path to the Flattened Device Tree blob. Critical on ARM — wrong DTB = wrong peripheral wiring (board may even appear to boot then hang).
APPEND (see §5.2) Kernel cmdline. Single line only.

PXELINUX has many more directives (PROMPT, TIMEOUT, MENU TITLE, LOCALBOOT, ...). U-Boot’s PXE bootmeth recognises a subset of them. This collection uses only the six above because they’re sufficient for the v1 invariant — there’s no menu, no per-boot operator choice, no fall-through to disk inside the .cfg (the fall-through happens because the .cfg is absent).

5.2 What ends up on the kernel cmdline (the APPEND breakdown)

ArgWhy it’s there
root=/dev/nfs Tells the kernel: don’t look for a block-device rootfs, look in the nfsroot= arg next.
nfsroot=<ip>:<path>,nfsvers=3,rw NFS server IP + export path on TrueNAS + flags. nfsvers=3 is non-negotiable — the Debian klibc-nfs in the initramfs only speaks NFSv2/v3 (see Gotcha §10.3). rw is required so the per-host rootfs clone can be modified at first boot (machine-id, ssh host keys).
ip=dhcp Have the kernel re-do DHCP after handoff. Without this, the kernel doesn’t come up with a configured interface and the NFS mount in initramfs fails because there’s no route.
console=ttyS2,1500000n8 Per-board UART path + baud. Sourced from vars/boards.yml — see board_configs.<model>.console. Wrong here = silent boot.
rootwait Wait for the rootfs device to be ready before mounting. For NFS, slightly redundant with the initramfs retry loop, but harmless.
rw Mount the rootfs read-write. Duplicates rw inside nfsroot= — historical, harmless.

6. How Ansible writes & removes it

pxelinux.cfg state on rb5009 lives in two places at once — a file on flash, and a /ip tftp row that exposes that file to TFTP clients. Both must be in sync for U-Boot to fetch it; neither alone is enough.

6.1 The two-resource invariant — file and row

RouterOS’s TFTP daemon doesn’t serve the flash filesystem automatically. It serves only what a /ip tftp row exposes, and uses the row’s req-filename field to pattern-match incoming TFTP requests. A file on flash with no row is invisible to TFTP; a row pointing at a missing file gives the client “cannot read file”. Both pieces matter, and this collection ensures both are written/removed as a pair.

RouterOS commands the role runs condensed
:if ([/file find name="sbc/pxelinux.cfg" type=directory] = "")
  do={/file add name="sbc/pxelinux.cfg" type=directory}

# size-gated idempotency check
/file print count-only where name="sbc/pxelinux.cfg/01-<mac>" and size=<local-size>
# net_put only fires when count is 0

/ip tftp print count-only where req-filename=".*01-<mac>"
                           and real-filename="sbc/pxelinux.cfg/01-<mac>"
# /ip tftp add only fires when count is 0
/ip tftp add  req-filename=".*01-<mac>"
              real-filename="sbc/pxelinux.cfg/01-<mac>"
              allow=yes  read-only=yes
  • The .* prefix in req-filename is not cosmetic — it’s a regex match against the wire-level TFTP request, and U-Boot’s actual request string includes path-prefix characters that do not literally string-match the bare pxelinux.cfg/01-<mac>. See Gotcha §10.5.
  • Idempotency is gated on size for the file and (req-filename, real-filename) tuple presence for the row. Re-running an enable that’s already in place lands as changed=0.

7. Example usages

7.1 Day-to-day: flip a board into NFS root, then back to SD

Operator workflow
# Send orange-pi-5-pro-01 into NFS-root mode (writes pxelinux.cfg + /ip tftp
# row on rb5009, PoE-cycles the board, asserts the rootfs is NFS)
ansible-playbook playbooks/enable_netboot.yml --limit orange-pi-5-pro-01

# Send it back to SD (removes /ip tftp row first, then the flash file,
# PoE-cycles, asserts the rootfs is the local block device)
ansible-playbook playbooks/disable_netboot.yml --limit orange-pi-5-pro-01

# Same enable but with verbose kernel cmdline for serial debugging
ansible-playbook playbooks/enable_netboot.yml --limit orange-pi-5-pro-01 \
  -e pxelinux_verbose=true

7.2 First-time setup of a new board model

Once-per-model
# 1. Build the custom Armbian image with PXE-first U-Boot
ansible-playbook playbooks/build_image.yml

# 2. Operator manually flashes the resulting .img.xz to a microSD card,
#    inserts into the board, powers up (no Ansible step)

# 3. Bootstrap an SSH user on the freshly-flashed board (uses Armbian's
#    default password from inventory)
ansible-playbook playbooks/bootstrap_armbian.yml --limit orange-pi-5-pro-01

# 4. Stage per-model assets to TrueNAS (NFS rootfs template + clone) and
#    rb5009 (kernel/initrd/dtb + /ip tftp rows). Per-board pxelinux.cfg
#    files come later; this is the per-model groundwork.
ansible-playbook playbooks/stage_netboot_assets.yml

# 5. Toggle the board into NFS-root mode (this is the per-board pxelinux.cfg
#    write step, identical to day-to-day usage)
ansible-playbook playbooks/enable_netboot.yml --limit orange-pi-5-pro-01
  • Step 1 only changes when you update the U-Boot patch table or the pinned armbian/build ref. Daily operation doesn’t need it.
  • Step 4 is the heavy one — it downloads the Armbian image, extracts it on TrueNAS, copies kernel/initrd/dtb up to rb5009. Subsequent runs of step 4 are idempotent (size-gated re-uploads of the kernel/initrd/dtb, NFS template re-extract).

7.3 Pre-staging without rebooting the board

Operator workflow
# Write pxelinux.cfg + /ip tftp row but do NOT power-cycle the board.
# Useful if the board is currently powered off — it will PXE-boot the
# next time it’s powered on (whenever that happens).
ansible-playbook playbooks/enable_netboot.yml --limit orange-pi-5-pro-01 \
  -e netboot_reboot=false

8. Common questions answered

Q: How does updating the kernel work in an automation workflow?

There are two kernels in play, and the operation that bumps each one is different:

  1. The vmlinuz / initrd / dtb served via TFTP by rb5009. These come from the Armbian .img.xz’s /boot/ directory. To update them: re-run playbooks/stage_netboot_assets.yml. It re-extracts the image on TrueNAS, refreshes the per-model NFS rootfs template (which includes the matching /lib/modules/<version>/ tree), force-removes the router-side files, and net_puts the new vmlinuz / initrd / dtb. The force-remove is deliberate — an earlier size-gated check silently skipped re-uploads when an updated kernel happened to compress to the same byte count as the previous one (causing the well-known “kernel lacks NFS v3 support” symptom; see Gotcha §10.6). The per-board pxelinux.cfg/01-<MAC> files do not change when you update the kernel — they reference stable TFTP paths (armbian/<model>/vmlinuz etc.), and the bytes those paths resolve to change underneath. So a kernel bump is a one-step operation: re-run stage_netboot_assets.yml; existing per-board enables continue working on the new kernel after the next PoE cycle.
  2. The U-Boot binary on the SD card. Lives inside the .img.xz Armbian build. To update: rebuild via playbooks/build_image.yml, then operator manually reflashes the SD card (no on-host bootloader flashing in v1). U-Boot is fixed for the life of the SD card; daily operation never touches it.

CI-style automation for kernel bumps would therefore drive stage_netboot_assets.yml on a cron (or webhook from an upstream image-bump signal), and let it re-stage idempotently. Day-to-day enable_netboot.yml calls are agnostic — they only manipulate the per-board pxelinux.cfg file, which doesn’t reference kernel versions.

Q: Can an SBC always netboot, but pxelinux points to a local rootfs (SD/eMMC/NVMe) instead of NFS?

Yes — and this is a deliberately interesting pattern. It’s how Talos/Sidero Metal, Canonical MAAS, LTSP, and Tinkerbell ship Linux to bare-metal fleets in production. There’s enough to say about it that it gets its own section: see §9 — Variant: always-netboot, locally-rooted.

Q: What if I want one board to boot a kernel that’s different from the rest of the same model?

Today the KERNEL/INITRD/FDT paths in the rendered pxelinux.cfg are hard-coded to armbian/<model>/... via the Jinja template, so all boards of a model share a kernel. To give one board its own kernel you’d need to either:

  • Stage a per-host kernel under flash:/sbc/armbian/per-host/<inventory_host>/ and extend the template + role to render a different path for that one host (probably gated on an kernel_override host var). Per-host pxelinux.cfg files are already per-host, so this is purely a template change plus a new stage_* task.
  • Add a second LABEL block to the .cfg and change DEFAULT per-host. Saves a TFTP path but doesn’t save anything operationally.

v1 doesn’t need this. It’s mentioned because it’s a natural extension of the file-presence-is-the-toggle model.

Q: Why is the req-filename a regex and not a literal path?

RouterOS’s /ip tftp matches req-filename as a regex against the wire-level TFTP request, not as a string. U-Boot prints to the console things like Filename ‘pxelinux.cfg/01-c0-74-2b-fb-4d-fd’, but the bytes on the wire don’t literally string-match the bare pxelinux.cfg/01-<mac> path (likely some leading-byte encoding difference; confirmed empirically that a literal rule got zero hits while a permissive .*<filename> rule worked). The role uses .*01-<mac> for that reason. Per-model rules (armbian/<model>/{vmlinuz,initrd.img,board.dtb}) use literal strings and do match — only the MAC-bearing filename needs the regex. The MAC is unique enough that an end-anchor is unnecessary — and $ must be avoided because RouterOS’s shell interprets $ inside double-quoted strings as a variable reference, mangling the rule.

9. Variant: always-netboot, locally-rooted

The v1 invariant in this collection treats pxelinux.cfg presence as a binary toggle: file exists ⇒ board boots NFS root; file absent ⇒ board falls through to SD. But pxelinux.cfg has no inherent affinity for NFS — it’s a carrier for “which kernel, which initrd, which DTB, what cmdline.” Swap the cmdline and you get a meaningfully different deployment pattern: always boot the kernel via TFTP, but root from a local block device (SD/eMMC/NVMe). This section walks the rationale, the concrete pxelinux.cfg shape for this repo’s boards, what would change in the collection, and how the pattern shows up in production fleet tools.

9.1 Why anyone ships kernels this way

Splitting “where the kernel comes from” (network) and “where the rootfs comes from” (local) is the same split that production bare-metal fleet tools make. The reasons are consistent across them:

  • Centrally managed kernel, locally persistent state. Bump the bytes that armbian/<model>/vmlinuz resolves to on rb5009, and every board running that pxelinux.cfg picks up the new kernel on next PoE cycle. Nothing on the board has to change. Rootfs (packages, configs, data) survives across kernel bumps because it’s on the board’s own NVMe / eMMC / SD.
  • Post-boot NFS independence. The current NFS-root path needs the TrueNAS server reachable for as long as the board is running — every page-fault that misses cache touches NFS. A locally-rooted variant only needs TFTP at boot; after that the board is independent of the storage box. Useful when the storage box is itself a board you’re trying to keep simple.
  • A/B kernel rollouts with rollback. Stage two LABELs in one pxelinux.cfg — primary on the new kernel, fallback on the previous one. U-Boot’s FALLBACK directive (combined with bootcount/bootlimit in U-Boot env) can boot the fallback automatically after N failed primary attempts.
  • Per-board hardware variation via FDTOVERLAYS. U-Boot supports FDTOVERLAYS in pxelinux.cfg — pre-apply DT overlays before bootm. You can stage a single base DTB per model + small overlays for optional hardware (NVMe HAT, fan controller, PCIe switch), and reference different overlays from per-board pxelinux.cfg files. Today this collection ships a frozen DTB per model; FDTOVERLAYS would unlock per-board hardware variation without rebuilding the Armbian image.

9.2 How production fleet tools use this exact pattern

Four well-known projects ship Linux to bare metal the same way — TFTP for the kernel handoff, local-or-network rootfs after that. They differ in what kind of rootfs they ship (immutable squashfs, full disk install, ephemeral RAM disk) but the kernel-side mechanism is the same family pxelinux.cfg lives in.

ToolKernel sourceRootfs strategyWhere pxelinux.cfg-style fits
Talos Linux / Sidero Metal iPXE / PXE TFTP Immutable, read-only SquashFS booted via initramfs (no local install). Kernel + SquashFS sourced over the network on every boot. No package manager, no per-node config writes. Closest to this repo’s current NFS-root pattern but in-RAM instead of NFS-mounted.
Canonical MAAS iPXE → ephemeral kernel from MAAS server Ephemeral initramfs installs the chosen OS to local disk, sets up GRUB on the disk, reboots into local boot. First boot is netboot-driven; subsequent boots come from local disk. Perfect example of “netboot kernel, locally-rooted thereafter.”
LTSP TFTP kernel + initramfs NBD-served SquashFS image used as rootfs. (Network-rooted, but block-image-served rather than NFS-mounted.) Closer to the v1 invariant — kernel and rootfs are remote. Just shows the third common rootfs strategy after NFS and local-block.
Tinkerbell iPXE / Boots Workflow engine; typical workflow installs an OS to local disk and switches the board to local boot after. Same pattern as MAAS — ephemeral kernel does install + handoff, then locally rooted forever.

None of these run PXELINUX itself; they all consume the same family of TFTP-served boot configs that U-Boot’s PXE bootmeth reads. pxelinux.cfg is the format, not the bootloader.

9.3 Concrete examples for this repo’s two boards

Both orange-pi-5-pro and rock-5b have three potential persistent storage targets:

SD card
Exposed as mmcblk1 on orange-pi-5-pro (U-Boot DT enumerates eMMC slot + SDIO + SD, so SD lands at index 1), and on rock-5b typically also mmcblk1 with an eMMC pad at mmcblk0. Block-device numbering is a U-Boot-DT-determined property — confirm on a live board with lsblk before relying on a specific /dev/mmcblk* path.
eMMC
If a board has an eMMC module socketed, it appears as another mmcblk*. Both rk3588 boards support eMMC; the rock-5b explicitly has a pad/socket for it.
NVMe via M.2
Both boards have an M.2 slot wired to rk3588 PCIe lanes. Linux side: nvme0n1. The kernel-side for an NVMe-rootfs PXE boot only needs nvme.ko available in the initramfs (Armbian’s stock initramfs includes it). U-Boot-side PCIe init does not need to be running for this path, because U-Boot is only fetching kernel/initrd/dtb over TFTP — it doesn’t touch NVMe at all. (The same PCIe-init concern that drives build_branches: picking edge over current for rk3588 boards in build_image.yml applies only if you want U-Boot itself to boot from NVMe.)

9.3.1 Pxelinux.cfg shape per rootfs target

NVMe-rooted variant orange-pi-5-pro
# pxelinux.cfg for orange-pi-5-pro-01 (NVMe rootfs)
DEFAULT nvmeroot

LABEL nvmeroot
  MENU LABEL Armbian on NVMe (orange-pi-5-pro-01)
  KERNEL armbian/orange-pi-5-pro/vmlinuz
  INITRD armbian/orange-pi-5-pro/initrd.img
  FDT    armbian/orange-pi-5-pro/board.dtb
  APPEND root=PARTUUID=8a7c1234-01 rootfstype=ext4 rootwait rw console=ttyS2,1500000n8
  • The kernel + initrd + DTB come from rb5009 (same per-model TFTP path the current NFS variant uses).
  • The root=PARTUUID=... hex is the partition’s PARTUUID, not the filesystem UUID. Find it on the board with lsblk -o NAME,PARTUUID,FSTYPE after a one-time SD or stock-image boot.
  • No ip=dhcp, no nfsroot=, no root=/dev/nfs. The kernel doesn’t need a network address to mount its own NVMe.
  • rootfstype=ext4 short-circuits the kernel’s autodetection — slightly faster boot, harmless if you got the FS type right.
eMMC-rooted variant rock-5b
DEFAULT emmcroot

LABEL emmcroot
  KERNEL armbian/rock-5b/vmlinuz
  INITRD armbian/rock-5b/initrd.img
  FDT    armbian/rock-5b/board.dtb
  APPEND root=PARTUUID=9b3e5678-01 rootfstype=ext4 rootwait rw console=ttyS2,1500000n8
Recovery LABEL (RAM-rooted) alongside primary
DEFAULT nvmeroot
TIMEOUT 50
PROMPT 0

LABEL nvmeroot
  KERNEL armbian/orange-pi-5-pro/vmlinuz
  INITRD armbian/orange-pi-5-pro/initrd.img
  FDT    armbian/orange-pi-5-pro/board.dtb

LABEL recovery
  MENU LABEL Recovery initramfs (no rootfs mount)
  KERNEL armbian/orange-pi-5-pro/vmlinuz
  INITRD armbian/orange-pi-5-pro/recovery-initrd.img
  FDT    armbian/orange-pi-5-pro/board.dtb
  APPEND root=/dev/ram0 init=/bin/sh console=ttyS2,1500000n8
  • TIMEOUT 50 means “wait 5.0 s before booting DEFAULT” (units are tenths of seconds, inherited from PXELINUX).
  • An operator on the serial console can interrupt the 5 s window and pick recovery manually — useful for in-place rescue without reflashing the SD card.
  • The recovery initrd is something this repo doesn’t ship today; staging it under armbian/<model>/recovery-initrd.img on rb5009 would be one more /ip tftp row in stage_rb5009.yml.

9.3.2 A/B kernel rollouts via FALLBACK

U-Boot supports a FALLBACK directive on the same level as DEFAULT: if the default label fails to boot (detected via U-Boot’s bootcount / bootlimit environment variables), the fallback label runs on the next attempt. Combined with TFTP-served per-model kernels, this enables painless kernel rollouts across the fleet:

A/B kernel layout for a rolling fleet upgrade
DEFAULT  new
FALLBACK old
TIMEOUT  30

LABEL new
  KERNEL armbian/orange-pi-5-pro/vmlinuz-6.10.0
  INITRD armbian/orange-pi-5-pro/initrd.img-6.10.0
  FDT    armbian/orange-pi-5-pro/board.dtb
  APPEND root=PARTUUID=8a7c1234-01 rootwait rw console=ttyS2,1500000n8

LABEL old
  KERNEL armbian/orange-pi-5-pro/vmlinuz-6.6.0
  INITRD armbian/orange-pi-5-pro/initrd.img-6.6.0
  FDT    armbian/orange-pi-5-pro/board.dtb
  APPEND root=PARTUUID=8a7c1234-01 rootwait rw console=ttyS2,1500000n8
  • U-Boot increments bootcount in its persistent env on every boot attempt. If a kernel never finishes its handoff to a healthy userland (and a userland-side service doesn’t reset bootcount), bootlimit is exceeded and U-Boot picks FALLBACK next time.
  • This means the staging step would lay down kernel files as versioned filenames (vmlinuz-6.10.0, initrd.img-6.10.0) rather than the current versionless vmlinuz path. Operationally simple: instead of force-removing the old vmlinuz, you keep both.
  • The rk3588 family has the “PSU margin during DDR re-init” class of cold-boot failures (see docs/architecture.md); FALLBACK doesn’t help with hardware-level failures, but it does insulate a fleet from a bad kernel rollout.

9.4 What would change in this collection to support local rootfs

This is concretely a small refactor — there’s no impedance mismatch with the existing architecture. The pieces that would change:

PieceToday (NFS-root)Local-rootfs variant
Template (pxelinux_cfg.j2) Hard-coded root=/dev/nfs nfsroot=... ip=dhcp APPEND. Jinja branch on a new per-host var (e.g. rootfs_source: nfs|nvme|emmc|sd) selecting the APPEND shape. KERNEL/INITRD/FDT lines stay identical.
vars/boards.yml console, earlycon, dtb. Same. Per-board rootfs_partuuid lives in inventory, not in boards.yml — it’s per-instance, not per-model.
roles/netboot_assets/tasks/per_host.yml Clones the NFS rootfs template, resets hostname / machine-id / SSH host keys on the cloned tree. Skipped entirely when rootfs_source != nfs. The board already has its own identity from the one-time bootstrap_armbian.yml run against the SD-installed rootfs.
Stage paths on TrueNAS nfs_rootfs_path/<host>/ per board. None needed. The per-model TFTP staging on rb5009 (kernel/initrd/dtb) is unchanged.
routeros_sbc_tftp role Writes a pxelinux.cfg/01-<MAC> with NFS APPEND. Writes the same filename with a local-rootfs APPEND. The Ansible code is identical — the difference is one Jinja branch in the template.
v1 invariant (file presence ⇒ NFS) File absent ⇒ falls through to SD bootflow (boot.scr-driven). Still holds: file absent ⇒ falls through to SD bootflow. File present ⇒ TFTP kernel + whatever APPEND you chose. The control surface (file presence) doesn’t change.
State verification (roles/board_boot_state/tasks/verify_state.yml) Asserts fstype is nfs|nfs4 when boot_state=pxe. Would need a third assertion path (or a relaxation): assert the rootfs device matches the host’s declared local-rootfs target, not NFS.

Importantly: the “disable” semantics don’t change. Today, disable_netboot.yml removes the per-board pxelinux.cfg and the board falls through to its SD card’s boot.scr. For a local-rootfs deployment that also wants to flip back to SD boot occasionally (e.g. for SD-card-side recovery), the same disable path works — the SD card’s boot.scr can carry a different rootfs reference (typically the SD’s own ext4 partition), and removing pxelinux.cfg routes the board there.

9.4.1 The bootstrap-the-rootfs question

Today’s NFS path has a neat answer to “how does a fresh board get its rootfs?”: stage_netboot_assets.yml extracts an Armbian image into _templates/<model>/ on TrueNAS, then cp --reflink snapshots a per-host clone. Local-rootfs deployments need a different first-touch story:

  1. Operator pre-flashes the local target. Most common: the SD card / eMMC / NVMe is written with an Armbian image (or with a board state captured via dd from a golden node) before the board ever joins the network. This collection’s bootstrap_armbian.yml already handles the post-flash “create my SSH user” step.
  2. One-shot install via the netboot kernel. The MAAS / Tinkerbell pattern: the netbooted kernel runs an installer initramfs, partitions the local target, dds a rootfs image onto it, then reboots into the local rootfs. This is what an “install” pxelinux.cfg LABEL would do — fire once per board, then remove.
  3. Hybrid: PXE-only as a recovery surface. Boards default to SD boot (no pxelinux.cfg). When something goes wrong on a board, an operator stages a per-board pxelinux.cfg with a recovery LABEL (RAM-rooted shell), fixes the local rootfs, removes the pxelinux.cfg, board returns to local boot.

9.5 Hardware caveats specific to this repo’s boards

PARTUUID vs UUID. Armbian’s armbianEnv.txt defaults to rootdev=UUID=... (filesystem UUID, set at mkfs.ext4 time). The kernel root= arg accepts both UUID= and PARTUUID=. PARTUUID lives in the partition table and survives mkfs; UUID lives in the filesystem superblock and changes if you ever reformat. For pxelinux-controlled fleets, PARTUUID= is the safer choice — you can wipe and reinstall the rootfs without re-rendering pxelinux.cfg files. Find both on a live board with lsblk -o NAME,PARTUUID,UUID,FSTYPE.
Block-device numbering is per-board. Don’t hard-code /dev/mmcblk1p2 across the fleet. orange-pi-5-pro’s SD card lands at mmcblk1 because the U-Boot DT also exposes the eMMC controller (which takes mmcblk0); rock-5b can differ depending on whether eMMC is socketed. NVMe is nvme0n1, USB storage is sda, but these still vary with what’s plugged in. PARTUUID sidesteps the whole problem.
The kernel needs the rootfs device’s driver in initramfs. Armbian’s stock initramfs includes nvme.ko, mmc_block.ko, usb_storage.ko, and the common filesystem modules (ext4.ko, btrfs.ko). Custom kernels built without one of these would hang in initramfs with “cannot find rootfs.” If you go this route, do one trial boot on a representative board before staging the kernel across the fleet.
NVMe on rk3588 PCIe needs the kernel-side PCIe init, not the U-Boot one. U-Boot only needs to TFTP — it doesn’t touch NVMe at all on this path. The kernel handles PCIe enumeration itself once it boots. (This is the inverse of the situation that drives build_image.yml’s build_branches: edge for rk3588 boards — that one is about U-Boot itself bringing up PCIe to reach the NIC for DHCP/TFTP. For NVMe-rootfs PXE, U-Boot’s PCIe state is irrelevant.)
The PSU-margin hardware failures don’t change. The serial-fingerprint table in docs/architecture.md §“Known issues” lists five hardware failure classes (#1 SD voltage-select, #3 mid-kernel DDR re-init, #4 silent post-kernel-start, etc.). These are PSU/SoC-level and happen regardless of where rootfs lives — moving rootfs from NFS to local doesn’t make a marginal PSU stop browning out during kernel-image load. The PXE-path verbose APPEND (PR #40) is still the right diagnostic for signature #4 whether the rootfs is NFS or local.

9.6 Bonus: FDTOVERLAYS for fleet hardware variation

Today each board_model gets one DTB. For hardware-tier variation within a model (one orange-pi-5-pro has an NVMe HAT, another has a fan controller HAT, another has neither), the cleanest mechanism is FDTOVERLAYS in pxelinux.cfg:

Per-board DT overlays from pxelinux.cfg
LABEL nvmeroot
  KERNEL    armbian/orange-pi-5-pro/vmlinuz
  INITRD    armbian/orange-pi-5-pro/initrd.img
  FDT       armbian/orange-pi-5-pro/board.dtb
  FDTOVERLAYS armbian/orange-pi-5-pro/overlays/nvme-hat.dtbo armbian/orange-pi-5-pro/overlays/fan-controller.dtbo
  APPEND    root=PARTUUID=8a7c1234-01 rootwait rw console=ttyS2,1500000n8
  • U-Boot fetches each overlay via TFTP, stores at fdtoverlay_addr_r, and applies them in load order to the FDT before bootm.
  • This collection doesn’t stage overlays today — adding one would be another /ip tftp row + flash file per overlay in stage_rb5009.yml, plus an overlays: list on the per-host inventory entry.
  • Useful when one of your three orange-pi-5-pros has an NVMe HAT and the others don’t — you avoid having to build three distinct Armbian images.

10. Gotchas

10.1 APPEND must be exactly one line. U-Boot’s PXE bootmeth does not honour backslash line continuations. If you split the APPEND across two lines with \, the second-and-onwards lines become “Ignoring unknown command:” in U-Boot’s output and only the first line’s args reach the kernel. The template enforces this on render and the comment block in pxelinux_cfg.j2 calls it out explicitly.
10.2 The pxelinux.cfg path is TFTP-relative, not absolute. KERNEL armbian/<model>/vmlinuz is resolved by U-Boot against the TFTP root the .cfg itself came from — i.e. the same TFTP server (rb5009). It doesn’t have a leading / and doesn’t carry the flash:/sbc/ prefix (that’s rb5009-internal pathing, not on the wire). Per-file /ip tftp rows map each TFTP-relative path to the rb5009 flash path.
10.3 nfsvers=3 is non-negotiable for NFS rootfs on this stack. Debian klibc-nfs in the initramfs only supports NFS v2/v3. Using nfsvers=4 makes nfsmount fail with “bad NFS version ’4’” and the board falls into a rescue (initramfs) prompt. v4 root mount would require either nfs-utils’ mount.nfs in the initramfs (extra hooks) or kernel-side NFS root via CONFIG_ROOT_NFS_V4 (kernel rebuild). Neither is wired up.
10.4 rw is required on the NFS mount, not optional. Each board has its own per-host rootfs at nfs_rootfs_path/<inventory_hostname>/, so concurrent writes from different boards don’t collide. RW is needed because first-boot ssh-keygen writes /etc/ssh/ssh_host_*_key (those keys were deleted from the rootfs by per_host.yml) and systemd-machine-id-setup writes /etc/machine-id. Without RW those services fail and the board has no SSH access.
10.5 The /ip tftp row uses .*01-<mac>, not the literal path. See the Q&A in §8 for the empirical reasoning. The other rows (per-model kernel/initrd/dtb) do use literal strings — only the MAC-bearing filename needs the regex prefix. Don’t use $ as an anchor; it’s interpreted as a RouterOS shell variable reference and mangles the rule on submission.
10.6 “kernel lacks NFS v3 support” is almost always a stale vmlinuz, not the kernel cmdline. If the initramfs reports mount: the kernel lacks NFS v3 support while looping on Begin: Retrying nfs mount, it’s a kernel/module version mismatch between the vmlinuz rb5009 serves and the /lib/modules/<version>/ tree in the freshly-staged initramfs and NFS rootfs. The earlier size-gated re-upload check silently skipped pushing a new vmlinuz when its byte count happened to match the previous one. stage_rb5009.yml now force-removes the router-side vmlinuz/initrd/dtb before net_put for that reason. Re-running stage_netboot_assets.yml is the right first response.
10.7 Remove the /ip tftp row before the flash file. disable_netboot.yml removes the row first, then the file. If the order is reversed and the file remove fails mid-way, the row would still point at a now-absent file — clients would get “cannot read file” but the row would still be live. With the row-first order, a mid-teardown failure fails closed: no row ⇒ no serve, regardless of whether the file is still there. (The orphan file is at most ~1 KB on flash; re-running disable_netboot cleans it up.)
10.8 Stock Armbian Rockchip current can’t use this flow. Stock images ship U-Boot with BOOT_TARGETS ordered such that PXE is at position 6, and bootflow scan lands on mmc1’s boot.scr before it ever tries PXE. Until a board has been flashed with one of this collection’s custom Armbian images, the writes to rb5009 will be correct but the board itself won’t honour them. See uboot-armbian-build-explainer.html for how the U-Boot patches that fix this get baked in at image build time.
10.9 next-server is owned externally. This collection does not write next-server on the SBC RouterOS network — that’s the operator’s separate RouterOS-config repo (e.g. igou-ansible’s deploy_netboot_binaries.yml). Without next-server set correctly for the SBC subnet, U-Boot can’t reach rb5009’s TFTP daemon, no pxelinux.cfg/01-<MAC> lookup happens, and the board silently falls through to SD boot regardless of what enable_netboot.yml just wrote. The plumbing_check.yml preflight catches per-model TFTP row mistakes but cannot catch a missing next-server.
