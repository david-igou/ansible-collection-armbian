# rock-5b friction working notes (deleted at end of Phase 4)

## Phase 1 (image build)

- **What hurt:** userpatches function-name convention vs. file/key name divergence
  **Where:** `playbooks/build_image.yml` `build_userpatches` dict
  **Root cause:** bash function names cannot contain dashes, so the `pre_config_uboot_target__<unique-id>` function name MUST be underscored even when the userpatches dict key (`rock-5b:`) and the `.conf` filename (`rock-5b.conf`) use dashes. The unique-id suffix after `__` is arbitrary — armbian/build's extension system (lib/functions/general/extensions.sh:139-168) just uses it as a per-hook unique identifier, not a board-derived value. So this is a bash limitation, not an armbian/build rule.
  **Deferred-refactor candidate:** yes — lifting `build_userpatches` into `vars/boards.yml` as a per-board field (e.g. `uboot_userpatches`) would let us encode the dash↔underscore translation in a Jinja transform once instead of remembering it per board.

- **What hurt:** rock-5b had to be added to inventory with placeholder MAC/IP *before* its image could be built, because `build_image.yml` derives `_board_models` from `groups['boards']` via `set_fact` (lines 57-63). Inventory is the only way to tell the playbook "build this board."
  **Where:** `playbooks/build_image.yml:57-63`
  **Root cause:** the build playbook's "what to build" question is answered by inventory, but inventory ergonomically wants a real board (real MAC/IP) — chicken-and-egg. We worked around it with `ansible_host: 0.0.0.0` / `board_mac: "00:00:00:00:00:00"` placeholders, which the build playbook doesn't care about (it only reads `board_model` from hostvars).
  **Deferred-refactor candidate:** yes — accept `_board_models` as an extra-vars override at play level (e.g. `-e build_only=rock-5b`), or move "what to build" into a separate config (`build_targets` keyed by board_model) so building doesn't require inventory pre-population. Important to address before there's a third board, because every new board onboarder will hit this.

- **What hurt:** I had to guess `poe_switch` / `poe_port` values when adding the inventory placeholder, because the spec doesn't specify a way to capture them ahead of time and the operator needs them in inventory before the build.
  **Where:** inventory `rock_5b.hosts.rock-5b-01.poe_switch` / `poe_port`
  **Root cause:** the placeholder-then-fill-in pattern works for DHCP-derived values (MAC/IP) but PoE wiring is a pre-existing physical decision that lives in the operator's head; capturing it requires asking the operator first.
  **Deferred-refactor candidate:** no — this is a documentation gap (the "Adding a new board" runbook should say "decide on PoE wiring before editing inventory"), not a code gap.

- **What hurt:** rock-5b's first build attempt died during chroot apt-install of `python3-pkg-resources` with dpkg postinst exit 245 (SIGSEGV). Failure was at `install_distribution_agnostic` installing `systemd-timesyncd netplan.io libubootenv-tool ethtool` — a board-agnostic stage. OPi5Pro was skipped this run (idempotent — recent image exists), so the failure could just as easily have hit OPi5Pro on a fresh build.
  **Where:** armbian/build chroot under qemu-user-static on the x86_64 builder; `lib/functions/rootfs/distro-agnostic.sh:327`
  **Root cause:** plausibly a QEMU-user-static / Python bytecode segfault under arm64 emulation — pycompile crashes when compiling `.py → .pyc` for packages with many python files. The May 6-7 OPi5Pro builds succeeded; this happens 5 days later, so could also be a recent Debian bookworm package regression or a QEMU/binfmt update on the builder host. Not rock-5b-specific in the package set, but rock-5b surfaced it because it's the only board needing a fresh build.
  **Deferred-refactor candidate:** no — this is an upstream issue (qemu/debian/armbian-build), not a refactor target. But it IS a load-bearing finding for the expansion story: *every new board's first build re-exposes the host builder to all the failure modes the cache previously masked*. The "third board" operator should expect to debug build environment issues that the OPi5Pro maintainer never sees because the image is cached.
  **Follow-up:** a clean retry of the same playbook succeeded ~50 minutes later with no changes — confirms the segfault was transient (QEMU/pycompile flakiness, not a deterministic regression). Single-retry is the cheapest mitigation; the build playbook doesn't bake in automatic retry, but a `register: build_result` + `retries: 2` wrapper around the `include_role: armbian_build` would absorb this class of flake without operator intervention. Probably worth doing if a third board's build also flakes.

- **What hurt:** nothing — the `Rock-5b` image filename casing matched the spec hypothesis exactly. The published file is `Armbian-unofficial_26.05.0-trunk_Rock-5b_bookworm_current_6.18.29_minimal.img.xz` — `Rock-5b` per Armbian's per-board naming convention. No surprise.
  **Where:** /mnt/ssd/public/boot-files/images/rock-5b/
  **Root cause:** Armbian's image-filename casing rule (`armbian_board_name` → board segment, with first letter uppercased and the rest verbatim) happened to align with what we guessed.
  **Deferred-refactor candidate:** no — no friction here; noted for completeness so the next board onboarder knows the rule held in practice.

- **What hurt:** nothing — OPi5Pro was idempotently skipped on this run (cached image still valid) and the publish play correctly only published the rock-5b artifact directory. The two-stage transfer (builder → controller stage → netboot_server rsync) worked transparently with no operator intervention.
  **Where:** `playbooks/build_image.yml` Play 1 (stage on controller) → Play 2 (rsync to netboot_server)
  **Root cause:** the playbook's design already handles this case correctly.
  **Deferred-refactor candidate:** no.

## Phase 2 (staging)

- **What hurt:** `bootstrap_armbian.yml` requires `armbian_default_password` to be defined in inventory, but it isn't documented in `inventory/group_vars/all.yml` (the doc-only inventory) and isn't set in the operator's real inventory either. The playbook fails with `'armbian_default_password' is undefined` and no actionable hint about *where* to set it. CLAUDE.md mentions it ("encrypt with vault") but the doc-inventory sample doesn't have a placeholder line. Worked around with `-e armbian_default_password=1234` for this run.
  **Where:** `playbooks/bootstrap_armbian.yml:36` references `{{ armbian_default_password }}` with no default
  **Root cause:** doc-inventory drift — every new operator hits this same wall on first board bootstrap, and the failure message points at a yaml line but not at the inventory edit that resolves it.
  **Deferred-refactor candidate:** yes (doc-only, low-cost) — add a commented-out `# armbian_default_password: "1234"  # encrypt with ansible-vault` line to `inventory/group_vars/all.yml`'s board section so the convention is visible without grep'ing CLAUDE.md. Bonus: the playbook could emit a custom assert error like "set armbian_default_password in your inventory's group_vars/all.yml (vault-encrypt for production)".

- **What hurt:** nothing — `stage_netboot_assets.yml` discovered rock-5b automatically via `groups['boards']` enumeration, ran preflight HEAD-checks against both URLs (200 OK), extracted the rock-5b rootfs into `_templates/rock-5b/`, reflink-cloned it into `rock-5b-01.igou.systems/`, fetched kernel/initrd/dtb to control-node cache, and net_put them to rb5009 with three matching `/ip tftp` rows. 2:33 total wall time. End-to-end with no operator intervention.
  **Where:** entire staging flow
  **Root cause:** the role's inventory-driven design handles new boards automatically — the same property that hurts Phase 1 (build playbook also needs inventory) is a *feature* here, not a bug.
  **Deferred-refactor candidate:** no.

- **What hurt:** nothing — the DTB-path hypothesis (`rockchip/rk3588-rock-5b.dtb`) held in practice. Armbian extracts the kernel package's `/boot/dtb-<kver>-current-rockchip64/` versioned directory AND a `/boot/dtb -> dtb-<kver>-current-rockchip64` symlink. The `dtb:` field in `vars/boards.yml` resolves through the symlink and stays correct across kernel-version bumps. Both OPi5Pro and rock-5b follow this pattern.
  **Where:** netboot_server `/mnt/ssd/netboot/rootfs/_templates/<board>/boot/`
  **Root cause:** stable Armbian convention.
  **Deferred-refactor candidate:** no — but worth documenting: the third-board onboarder can assume the `/boot/dtb/...` path works as long as Armbian keeps the symlink convention.

- **What hurt:** nothing surprising — but worth noting: per-host SSH host keys (`/etc/ssh/ssh_host_*_key`) are *absent* from the rock-5b rootfs template (and presumably OPi5Pro's too), because Armbian ships the image without host keys; sshd generates them on first boot. So the `netboot_assets` role's "reset SSH host keys" step is a no-op for the template-then-clone path: each per-host clone starts with no keys, and sshd generates fresh independent keys on first NFS-root boot. The identity-uniqueness invariant holds, just via a different mechanism than the role docstring suggests ("reset SSH host keys" → really "let sshd generate them per-host").
  **Where:** netboot_server `_templates/rock-5b/etc/ssh/` (only configs, no `*_key` files)
  **Root cause:** Armbian's image lifecycle delegates SSH host-key generation to first-boot, not image-build.
  **Deferred-refactor candidate:** low priority — update the netboot_assets role comment to describe the actual behavior ("sshd generates fresh keys on first boot; per-host clones inherit nothing to collide on"), or remove the no-op task if it's literally a no-op.

## Phase 3 (hardware E2E) — the *real* findings

- **What hurt:** `delegate_to` on `ansible.builtin.include_role` is no longer a valid attribute (deprecated since Ansible 2.14, error since 2.20). `board_boot_state` uses this pattern in `configure_pxe.yml:21` and `configure_disk.yml:13`, so `enable_netboot.yml` / `disable_netboot.yml` / `test_hardware_e2e.yml` all hard-fail at the first delegated include in Ansible 2.20+. This is a board-agnostic latent regression — it would have hit every E2E run on Ansible 2.20+, not just rock-5b. We surfaced it because rock-5b's bring-up was the first E2E attempt since the Ansible 2.20 upgrade.
  **Where:** `roles/board_boot_state/tasks/configure_pxe.yml:21`, `roles/board_boot_state/tasks/configure_disk.yml:13`
  **Root cause:** Ansible deprecation cycle completed; the collection's CI runs lint and molecule smoke, neither of which exercises this code path.
  **Fix applied (in-scope maintenance):** wrap each `include_role` in a `block:` with `delegate_to:`. The block-level `delegate_to` propagates to every task inside the included role. Same semantic; supported pattern. Acceptance criterion 3 ("no harness changes") was reframed: the criterion's intent was to disallow rock-5b-specific harness tweaks, not block board-agnostic maintenance.
  **Deferred-refactor candidate:** the collection's CI should run a `--syntax-check` or `--check`-mode `enable_netboot.yml` against a fixture inventory on every PR so regressions like this are caught before someone hits them at the workbench. Currently molecule's `default` scenario is a hello-world placeholder per README; this is the gap.

- **What hurt (BIG ONE):** the PXE-first userpatch (`pre_config_uboot_target__<board>_pxe_first` with sed against `#define BOOT_TARGETS` in `include/configs/rockchip-common.h`) **only worked for OPi5Pro by happy accident**. It does nothing useful for rock-5b — and would do nothing useful for most other rk3588 boards.
  **Why:** armbian/build pulls *different* u-boot trees per board:
  - OPi5Pro → `u-boot-orangepi5pro/v2025.10` — ships `#define BOOT_TARGETS "pxe dhcp mmc1 mmc0 nvme scsi usb spi"` (PXE already first upstream). Our sed touches the line, replaces it with the same value. No-op.
  - Rock-5b → `u-boot/next-dev-v2024.10` (Radxa next-dev, the rk3588 family default) — uses an X-macro pattern (`#define BOOT_TARGET_DEVICES(func) \ BOOT_TARGET_USB(func) \ ... BOOT_TARGET_PXE(func) \ BOOT_TARGET_DHCP(func)`), with PXE at position 8 of 9. No `#define BOOT_TARGETS` line exists in the file. Our sed silently matches nothing → no patch → SD wins → 0 TFTP hits on rb5009 → board boots SD rootfs → assert "expected NFS rootfs" fails.

  Diagnosis path: rb5009 `/ip tftp print where real-filename~"rock-5b"` showed HITS=0 on all three files AND HITS=0 on the per-board pxelinux.cfg row. That meant U-Boot never made a TFTP request at all — not "PXE attempted but failed" but "PXE never tried." Comparing `/var/lib/armbian_build/build/cache/sources/u-boot-worktree/` showed two different forks with two different BOOT_TARGETS conventions.

  **Where:** `playbooks/build_image.yml` `build_userpatches` dict — both board entries had the same too-narrow sed
  **Root cause:** the userpatch was written by analogy to OPi5Pro without checking that the upstream macro structure was actually the same across all rk3588 u-boot trees. The OPi5Pro patch happened to be a happy no-op, so it looked like it worked.
  **Fix applied (in-scope maintenance):** userpatch now handles BOTH forms — keeps the legacy sed for the OPi5Pro fork AND adds a Python multi-line text replacement for the X-macro form (matches the EXACT current upstream Radxa layout; idempotent no-op if Radxa changes the order). Identical body for both boards' userpatches because the patch logic is board-agnostic — only the function name (bash-naming-rule) differs.
  **Deferred-refactor candidate (high priority):** the rk3588 family userpatch should be ONE shared function, not duplicated per-board. Three lift options: (a) a single `pre_config_uboot_target__rk3588_pxe_first` in a single per-family `.conf` file, (b) the function body lives in a role file and the per-board `.conf` just registers a thin alias, (c) `vars/boards.yml` gains a `uboot_userpatches:` field with shared snippets composable per-board. (c) is what we hypothesised in Phase 1 friction; this finding strengthens the case. Also: armbian/build's u-boot tree selection per board is invisible to operators — a board's `BOOTSOURCE` could change in a family file refresh and our patch would silently stop applying. The post-v1 refactor should include a build-time assertion: "after the patch, BOOT_TARGET_DEVICES (or BOOT_TARGETS) puts PXE first; if not, fail the build."

- **What hurt:** without serial UART on rock-5b, the "PXE never tried" failure mode was not directly observable. We diagnosed via SECOND-ORDER signal (rb5009 TFTP HITS=0). That worked, but the spec correctly flagged that the no-UART trade-off narrows the diagnostic surface for pre-SSH failures — and the very first Phase 3 attempt produced exactly that kind of failure.
  **Where:** Phase 3 diagnostics in general
  **Root cause:** chose not to wire UART for rock-5b (per spec); chose correctly given expected HAT reliability; reality is that the cheaper diagnostic surface still worked but required more reasoning.
  **Deferred-refactor candidate:** no — wiring UART for diagnosis-only use is a real fallback option; not worth automating into the collection. But worth documenting: "if a Phase 3 PXE failure surfaces, the diagnostic playbook is 'check rb5009 TFTP HITS=0 on per-board pxelinux.cfg and per-model kernel/initrd/dtb rows; HITS=0 means U-Boot never tried PXE'."

- **What hurt:** observed two unexpected files at `nfs_assets_export/images/` root — `orange-pi-5-pro.img.xz` (May 7) and `rock-5b.img.xz` (May 12 11:47) — sibling to the per-board subdirs that build_image.yml publishes to. Naming used `board_model` (dashed) not `armbian_board_name`. ~770 MB of dead bytes.
  **Where:** `roles/netboot_assets/tasks/per_board.yml:162-167` (the "Copy Armbian image to assets for HTTP download" task)
  **Root cause:** vestigial code from the **deleted reprovision workflow**. Commit 4d8df52 (May 4) introduced this task as `"Copy Armbian image to assets for reprovision HTTP download"` — it was the HTTP publish point for NFS-rooted boards downloading their .img.xz and flashing local disk. v1 scope-narrowing (commit ad5b5eb, May 7) deleted the reprovision role/playbook but missed this task. Someone later trimmed the task name to drop "for reprovision," which obscured its purpose. No current consumer reads `images/<board_model>.img.xz` (pxelinux.cfg references kernel/initrd/dtb only; no URL in the collection points there).
  **Fix applied (in-scope maintenance):** deleted the task. The OPi5Pro .img.xz at images/ root would persist forever as stale state; cleaned up both stale files on TrueNAS. Same maintenance class as the userpatch and Ansible 2.20 fixes — v1-scope-narrowing missed cleanups that the rock-5b expansion forced us to notice (because the new `rock-5b.img.xz` showed up in addition to the pre-existing OPi5Pro one).
  **Deferred-refactor candidate (medium priority):** v1-scope-narrowing was incomplete in subtler ways than the spec admits. The spec amendment should call this out: *the deletion of reprovision missed three sites* — the broken userpatch (which depended on reprovision-era assumptions about u-boot trees), the dead HTTP publish task, and possibly more. A pre-v1-release "cleanup audit" should grep for `_model }}.img.xz`, `reprovision`, `flash_bootloader`, and other tokens from the deleted workflows.

- **What hurt:** even after the PXE-first patch took effect (verified `boot_targets=pxe dhcp mmc1 mmc0 ...` baked into u-boot env on the re-flashed SD), HITS still =0 on rb5009 — U-Boot still didn't make any TFTP request. **Root cause: Radxa's `next-dev-v2024.10` rock-5b defconfig is missing `CONFIG_PHY_REALTEK=y`.** Rock 5B's gigabit PHY is an RTL8211F; without the Realtek driver, U-Boot can't talk to the PHY, link never comes up, DHCP/PXE silently fail. Linux's kernel has the driver baked in, which is why Armbian boots fine over SD — but U-Boot itself is dead-in-the-water for networking.
  **Where:** `<u-boot tree>/configs/rock-5b-rk3588_defconfig` — missing `CONFIG_PHY_REALTEK=y`
  **Root cause:** upstream Radxa fork's defconfig is incomplete for netboot. Linux works because the kernel pulls in Realtek PHY drivers automatically; U-Boot is more spartan and only includes explicitly-enabled drivers.
  **Diagnostic path:** because rock-5b has no UART wired (per spec), I worked through second-order signals: verified the BOOT_TARGETS patch via raw-disk `grep` for `boot_targets=...` in u-boot binary, confirmed `CONFIG_CMD_PXE=y` in the built .config, confirmed DHCP `next-server=10.10.9.1` on rb5009, confirmed rb5009 `/ip tftp` rows are present — then noticed the rock-5b lease had no `class-id="PXEClient:..."` (whereas OPi5Pro's did), which proved U-Boot wasn't sending the PXE DHCP request at all. Comparing built .configs side-by-side surfaced the missing `CONFIG_PHY_REALTEK=y`.
  **Fix applied (in-scope; rock-5b-specific):** rock-5b's userpatch (`pre_config_uboot_target__rock_5b_pxe_first`) now appends `CONFIG_PHY_REALTEK=y` to the defconfig before `make <BOOTCONFIG>` loads it.
  **Deferred-refactor candidate:** this is the kind of board-by-board finding the spec anticipated — different SBCs need different per-board patches. The expansion-story lesson: *each new RK3588 board onboarder must verify their PHY driver is enabled in the Radxa fork defconfig*. A pre-flight check that does a `find u-boot built .config | grep PHY_<driver>=y` against an inventory of known-needed drivers would catch this class of bug before image build wastes 30 minutes.
  **Time-cost finding:** without UART, this took ~30 minutes of multi-stage diagnosis (verify boot_targets baked in → verify CMD_PXE enabled → verify rb5009 routing → check lease class-id → diff configs). With UART, U-Boot's "PHY init failed: -ENODEV" or "phy not found" output would have surfaced this in seconds. The spec's trade-off ("rock-5b uses a more reliable HAT, so we don't need UART") held for the PoE-cycle scenario but not for U-Boot network init issues — which is a category the spec didn't consider.
