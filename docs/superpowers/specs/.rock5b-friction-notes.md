# rock-5b friction working notes (deleted at end of Phase 4)

## Phase 1 (image build)

- **What hurt:** userpatches function-name convention vs. file/key name divergence
  **Where:** `playbooks/build_image.yml` `build_userpatches` dict
  **Root cause:** bash function names cannot contain dashes, so the `pre_config_uboot_target__<unique-id>` function name MUST be underscored even when the userpatches dict key (`rock-5b:`) and the `.conf` filename (`rock-5b.conf`) use dashes. The unique-id suffix after `__` is arbitrary — armbian/build's extension system (lib/functions/general/extensions.sh:139-168) just uses it as a per-hook unique identifier, not a board-derived value. So this is a bash limitation, not an armbian/build rule.
  **Deferred-refactor candidate:** yes — lifting `build_userpatches` into `vars/boards.yml` as a per-board field (e.g. `uboot_userpatches`) would let us encode the dash↔underscore translation in a Jinja transform once instead of remembering it per board.

- **What hurt:** rock-5b had to be added to inventory with placeholder MAC/IP *before* its image could be built, because `build_image.yml` derives `_board_models` from `groups['boards']` via `set_fact` (lines 57-63). Inventory is the only way to tell the playbook "build this board."
  **Where:** `playbooks/build_image.yml:57-63`
  **Root cause:** the build playbook's "what to build" question is answered by inventory, but inventory ergonomically wants a real board (real MAC/IP) — chicken-and-egg. We worked around it with `ansible_host: 0.0.0.0` / `board_mac: "00:00:00:00:00:00"` placeholders, which the build playbook doesn't care about (it only reads `board_model` from hostvars).
  **Deferred-refactor candidate:** yes — accept `_board_models` as an extra-vars override at play level (e.g. `-e build_only=rock-5b`), or move "what to build" into a separate config (`build_targets` keyed by board_model) so building doesn't require inventory pre-population. Important to address before there's a third board, because every new board onboarder will hit this.

- **What hurt:** I had to guess `poe_switch` / `poe_port` values when adding the inventory placeholder, because the spec doesn't specify a way to capture them ahead of time and the operator needs them in inventory before the build.
  **Where:** inventory `rock_5b.hosts.rock-5b-01.poe_switch` / `poe_port`
  **Root cause:** the placeholder-then-fill-in pattern works for DHCP-derived values (MAC/IP) but PoE wiring is a pre-existing physical decision that lives in the operator's head; capturing it requires asking the operator first.
  **Deferred-refactor candidate:** no — this is a documentation gap (the "Adding a new board" runbook should say "decide on PoE wiring before editing inventory"), not a code gap.

- **What hurt:** rock-5b's first build attempt died during chroot apt-install of `python3-pkg-resources` with dpkg postinst exit 245 (SIGSEGV). Failure was at `install_distribution_agnostic` installing `systemd-timesyncd netplan.io libubootenv-tool ethtool` — a board-agnostic stage. OPi5Pro was skipped this run (idempotent — recent image exists), so the failure could just as easily have hit OPi5Pro on a fresh build.
  **Where:** armbian/build chroot under qemu-user-static on the x86_64 builder; `lib/functions/rootfs/distro-agnostic.sh:327`
  **Root cause:** plausibly a QEMU-user-static / Python bytecode segfault under arm64 emulation — pycompile crashes when compiling `.py → .pyc` for packages with many python files. The May 6-7 OPi5Pro builds succeeded; this happens 5 days later, so could also be a recent Debian bookworm package regression or a QEMU/binfmt update on the builder host. Not rock-5b-specific in the package set, but rock-5b surfaced it because it's the only board needing a fresh build.
  **Deferred-refactor candidate:** no — this is an upstream issue (qemu/debian/armbian-build), not a refactor target. But it IS a load-bearing finding for the expansion story: *every new board's first build re-exposes the host builder to all the failure modes the cache previously masked*. The "third board" operator should expect to debug build environment issues that the OPi5Pro maintainer never sees because the image is cached.
  **Follow-up:** a clean retry of the same playbook succeeded ~50 minutes later with no changes — confirms the segfault was transient (QEMU/pycompile flakiness, not a deterministic regression). Single-retry is the cheapest mitigation; the build playbook doesn't bake in automatic retry, but a `register: build_result` + `retries: 2` wrapper around the `include_role: armbian_build` would absorb this class of flake without operator intervention. Probably worth doing if a third board's build also flakes.

- **What hurt:** nothing — the `Rock-5b` image filename casing matched the spec hypothesis exactly. The published file is `Armbian-unofficial_26.05.0-trunk_Rock-5b_bookworm_current_6.18.29_minimal.img.xz` — `Rock-5b` per Armbian's per-board naming convention. No surprise.
  **Where:** /mnt/ssd/public/boot-files/images/rock-5b/
  **Root cause:** Armbian's image-filename casing rule (`armbian_board_name` → board segment, with first letter uppercased and the rest verbatim) happened to align with what we guessed.
  **Deferred-refactor candidate:** no — no friction here; noted for completeness so the next board onboarder knows the rule held in practice.

- **What hurt:** nothing — OPi5Pro was idempotently skipped on this run (cached image still valid) and the publish play correctly only published the rock-5b artifact directory. The two-stage transfer (builder → controller stage → netboot_server rsync) worked transparently with no operator intervention.
  **Where:** `playbooks/build_image.yml` Play 1 (stage on controller) → Play 2 (rsync to netboot_server)
  **Root cause:** the playbook's design already handles this case correctly.
  **Deferred-refactor candidate:** no.

## Phase 2 (staging)

- **What hurt:** `bootstrap_armbian.yml` requires `armbian_default_password` to be defined in inventory, but it isn't documented in `inventory/group_vars/all.yml` (the doc-only inventory) and isn't set in the operator's real inventory either. The playbook fails with `'armbian_default_password' is undefined` and no actionable hint about *where* to set it. CLAUDE.md mentions it ("encrypt with vault") but the doc-inventory sample doesn't have a placeholder line. Worked around with `-e armbian_default_password=1234` for this run.
  **Where:** `playbooks/bootstrap_armbian.yml:36` references `{{ armbian_default_password }}` with no default
  **Root cause:** doc-inventory drift — every new operator hits this same wall on first board bootstrap, and the failure message points at a yaml line but not at the inventory edit that resolves it.
  **Deferred-refactor candidate:** yes (doc-only, low-cost) — add a commented-out `# armbian_default_password: "1234"  # encrypt with ansible-vault` line to `inventory/group_vars/all.yml`'s board section so the convention is visible without grep'ing CLAUDE.md. Bonus: the playbook could emit a custom assert error like "set armbian_default_password in your inventory's group_vars/all.yml (vault-encrypt for production)".

- **What hurt:** nothing — `stage_netboot_assets.yml` discovered rock-5b automatically via `groups['boards']` enumeration, ran preflight HEAD-checks against both URLs (200 OK), extracted the rock-5b rootfs into `_templates/rock-5b/`, reflink-cloned it into `rock-5b-01.igou.systems/`, fetched kernel/initrd/dtb to control-node cache, and net_put them to rb5009 with three matching `/ip tftp` rows. 2:33 total wall time. End-to-end with no operator intervention.
  **Where:** entire staging flow
  **Root cause:** the role's inventory-driven design handles new boards automatically — the same property that hurts Phase 1 (build playbook also needs inventory) is a *feature* here, not a bug.
  **Deferred-refactor candidate:** no.

- **What hurt:** nothing — the DTB-path hypothesis (`rockchip/rk3588-rock-5b.dtb`) held in practice. Armbian extracts the kernel package's `/boot/dtb-<kver>-current-rockchip64/` versioned directory AND a `/boot/dtb -> dtb-<kver>-current-rockchip64` symlink. The `dtb:` field in `vars/boards.yml` resolves through the symlink and stays correct across kernel-version bumps. Both OPi5Pro and rock-5b follow this pattern.
  **Where:** netboot_server `/mnt/ssd/netboot/rootfs/_templates/<board>/boot/`
  **Root cause:** stable Armbian convention.
  **Deferred-refactor candidate:** no — but worth documenting: the third-board onboarder can assume the `/boot/dtb/...` path works as long as Armbian keeps the symlink convention.

- **What hurt:** nothing surprising — but worth noting: per-host SSH host keys (`/etc/ssh/ssh_host_*_key`) are *absent* from the rock-5b rootfs template (and presumably OPi5Pro's too), because Armbian ships the image without host keys; sshd generates them on first boot. So the `netboot_assets` role's "reset SSH host keys" step is a no-op for the template-then-clone path: each per-host clone starts with no keys, and sshd generates fresh independent keys on first NFS-root boot. The identity-uniqueness invariant holds, just via a different mechanism than the role docstring suggests ("reset SSH host keys" → really "let sshd generate them per-host").
  **Where:** netboot_server `_templates/rock-5b/etc/ssh/` (only configs, no `*_key` files)
  **Root cause:** Armbian's image lifecycle delegates SSH host-key generation to first-boot, not image-build.
  **Deferred-refactor candidate:** low priority — update the netboot_assets role comment to describe the actual behavior ("sshd generates fresh keys on first boot; per-host clones inherit nothing to collide on"), or remove the no-op task if it's literally a no-op.
