1. TL;DR

PR #9656 introduces a first-class opt-in netboot extension in armbian/build. The headline switch is a new ROOTFS_TYPE=nfs-root case in main-config.sh, which:

  • auto-enables the new extensions/netboot/netboot.sh extension,
  • skips the SD-card image pipeline entirely (no .img.xz deliverable — the build does not even allocate a root partition),
  • directly produces the TFTP payload (Image/zImage, DTB tree, optional uInitrd, pxelinux.cfg/…),
  • turns the chroot rootfs into the deliverable: it is either tarred (.tar.zst / .tar.gz) or rsynced directly into a directory you specify via the new ROOTFS_EXPORT_DIR variable,
  • fires two new generic hooks — post_create_rootfs_archive and artifact_ready — so a sibling netboot-deploy extension can rsync everything to a remote NFS+TFTP server in one shot.

For david_igou.armbian_netboot, the most consequential delta is where the rootfs is materialised:

Today (this collection): the build produces a stock .img.xz, we publish it to TrueNAS, then on TrueNAS we losetup + mount + rsync the rootfs partition out of the image. That requires become: true on TrueNAS plus losetup/mount privileges — an awkward dependency on a NAS appliance we’d rather treat as an unprivileged file server.
With PR #9656: the build itself produces the unpacked rootfs tree directly into a path of our choosing — including a path that lives on NFS export storage. losetup, mount, image extraction, DTB hunting all disappear from the TrueNAS side. TrueNAS becomes just an NFS server; the rest of the pipeline runs as the build user.

The rest of this document explains the design in enough depth to plan that migration, flags the two areas of real overlap with this collection (rootfs staging + pxelinux.cfg generation) and the non-trivial gaps that mean we still need our existing roles (per-board PXE multi-label, RouterOS TFTP plumbing, PoE-based boot mode flips, per-host SD-fallback PARTUUID, custom U-Boot baked with PXE-first BOOT_TARGETS).

3. Deep dive: how the extension creates filesystems

This is the part that materially affects this collection. The end-state question is: given ROOTFS_TYPE=nfs-root, where does the rootfs that boards will mount over NFS actually come from, and what privilege does writing it require?

3.1 Source of the rootfs: the build’s own $SDCARD chroot

In a normal Armbian image build, $SDCARD is the chroot that debootstrap populates and that post_customize_image hooks modify. Today (without this PR) that chroot is then rsynced into a mounted partition inside a loop-mounted .img file, the image is finalised, compressed, etc.

PR #9656 short-circuits everything from the second step onwards for ROOTFS_TYPE in {nfs, nfs-root}. Inside create_image_from_sdcard_rootfs the new branch in rootfs-to-image.sh does (paraphrased): 

if [[ $ROOTFS_TYPE == nfs || $ROOTFS_TYPE == nfs-root ]]; then
    # --- (A) archive path ---
    if [[ "$ROOTFS_COMPRESSION" != "none" ]]; then
        ROOTFS_ARCHIVE_PATH="${FINALDEST}/${version}-rootfs.${archive_ext}"
        rootfs_archive_tmp="${FINALDEST}/.${version}-rootfs.${archive_ext}.tmp"
        ( set -o pipefail
          tar cp --numeric-owner --xattrs \
              --xattrs-include="${ROOTFS_TAR_XATTR_INCLUDE:-security.*}" \
              --acls --selinux --sparse "${ROOTFS_TAR_EXTRA_FLAGS[@]}" \
              --directory="$SDCARD/" "${tar_excludes[@]}" . \
            | pv ... \
            | ${archive_filter} > "${rootfs_archive_tmp}"  ## zstd -T0 -c | gzip -c
        )
        mv -v "${rootfs_archive_tmp}" "${ROOTFS_ARCHIVE_PATH}"
    fi

    # --- (B) direct-tree path (additive or exclusive) ---
    if [[ -n "${ROOTFS_EXPORT_DIR}" ]]; then
        ## safety: realpath check rejects /, /etc, ${SDCARD}, ..-segments
        rsync -aHWh -AXS --numeric-ids --delete --delete-excluded $rsync_ea \
            --exclude="/boot/*" --exclude="/dev/*" --exclude="/proc/*" \
            --exclude="/run/*"  --exclude="/tmp/*" --exclude="/sys/*" \
            $exclude_home --info=progress0,stats1 \
            "$SDCARD/" "${ROOTFS_EXPORT_DIR}/"
    fi
fi

And then, critically, for nfs-root it skips the entire SD-card image emission — no parted, no mkfs, no losetup, no partprobe, no .img.xz. The build artifacts are just:

  1. ${FINALDEST}/${version}-rootfs.tar.zst — the rootfs archive (skippable via ROOTFS_COMPRESSION=none)
  2. ${FINALDEST}/${version}-netboot-tftp/ — the TFTP payload tree (${PREFIX}/Image, ${PREFIX}/dtb/…, optional ${PREFIX}/uInitrd, pxelinux.cfg/…)
  3. And optionally: ${ROOTFS_EXPORT_DIR}/ — the unpacked rootfs tree, written in place.

3.2 Identity correctness: --xattrs --acls --selinux --numeric-ids

The PR fixes a real correctness bug across the board (not just for netboot): the old tar cp --xattrs dropped POSIX ACLs, SELinux contexts, and — the one that actually bites in practice — file capabilities (security.capability xattr), which is the namespace setcap cap_net_raw+ep /usr/bin/ping lives in. The new flags include security.* by default; tar in create-cache.sh and rootfs-create.sh got the same treatment.

For our use case the practical implication is: per-host rootfs trees produced this way preserve original ownership and SUID/capability bits without a chroot or qemu pass on the deploy side. That matters because the moment we stop building images and start materialising trees directly, the integrity of those bits has to live in the rsync, not in partclone/tar2img.

3.3 The two on-disk write targets

The PR distinguishes three modes of writing the rootfs tree:

Variable comboResultUse case
ROOTFS_COMPRESSION=zstd (default)
ROOTFS_EXPORT_DIR unset		 Single ${version}-rootfs.tar.zst in FINALDEST. Build host ships the archive to a separate NFS server (the netboot-deploy reference path).
ROOTFS_COMPRESSION=zstd
ROOTFS_EXPORT_DIR=…		 Both: archive in FINALDEST + tree rsynced to the dir. Local builder publishes a tree and keeps an archive for cold standby.
ROOTFS_COMPRESSION=none
ROOTFS_EXPORT_DIR=…		 Only tree-rsync; no tar produced. Build host is the NFS server (or has the export NFS-mounted). The single fastest path — one rsync, no compress/decompress cycle.

3.4 Safety on the rsync target

rsync --delete on an operator-supplied path is sharp. The PR spends visible care on this:

  • NETBOOT_EXPORT_DIR_BLACKLIST rejects /, /etc, /usr, /bin, /sbin, /lib, /lib64, /boot, /proc, /sys, /dev, /run, /tmp, /var/log, /var/run (extendable via netboot_export_dir_blacklist hook).
  • .. segments are rejected.
  • A non-empty target without the .netboot_export_marker stamp at its root is refused (the marker is written via post_customize_image so a previously-exported tree carries it). Override with NETBOOT_EXPORT_FORCE=yes.
  • realpath -m validates the resolved path even when symlinks are involved, so a misaimed symlink under the under-base namespace can’t escape into /etc.

3.5 Per-host vs shared rootfs — built into the variable schema

The PR formalises the per-host pattern this collection already implements manually: 

# shared rootfs (multiple boards mount the same path; not what we want)
NETBOOT_NFS_PATH = /srv/netboot/rootfs/shared/${LINUXFAMILY}/${BOARD}/${BRANCH}-${RELEASE}${_FLAVOR}

# per-host rootfs (NETBOOT_HOSTNAME=<name> -> own writable copy)
NETBOOT_NFS_PATH = /srv/netboot/rootfs/hosts/<hostname>

Crucially, in the per-host mode the build is run once per host — each invocation produces a full rootfs at hosts/<hostname>. That is a different shape than this collection’s “build once per model + cheap reflink per host” approach. See §5.3.

3.6 Initramfs work the extension does for you

Even though the PR’s end-state assumes a kernel with CONFIG_ROOT_NFS=y that mounts NFS without an initramfs, it still bothers to build a sane initramfs path because not every distro+board combination guarantees a working ip=dhcp + builtin NFS root path:

  • 71-netboot-rootpath + companion initramfs-tools hook — fixes the “ROOTSERVER=default-gateway” bug from stock 70-net-conf: reads bootserver from /proc/net/pnp instead.
  • zz-netboot-watchdog — arms a 10-minute hardware watchdog at init-premount, cancelled at nfs-bottom once / is up. A board whose initramfs hangs on /dev/nfs reboots instead of becoming an unreachable serial console.
  • update-initramfs -u is invoked inside the chroot so the shipped uInitrd on TFTP carries these hooks.

This collection’s pxelinux template currently relies on the kernel-side ip=dhcp + builtin NFS, plus a fixed nfsroot=<ip>:<path> baked at render time. The watchdog primitive is something we’d strictly benefit from inheriting — today a stuck NFS mount manifests as “board silent on serial for 20 min” and the only recovery is a PoE cycle. §6.3.

4. How this collection creates filesystems today

Authoritative file: roles/netboot_assets/tasks/per_board.yml plus tasks/per_host.yml. Summarised:

  1. (builder) playbooks/build_image.yml runs Armbian build in Docker on armbian_builders, producing a stock-looking .img.xz (with our custom PXE-first U-Boot patches), and rsyncs it to ${armbian_netboot_nfs_assets_export}/images/<board>/ on the netboot server via a controller-mediated relay.
  2. (TrueNAS, become: true) playbooks/stage_nfs_rootfs.yml → roles/netboot_assets/tasks/per_board.yml:
    • xz -dk the cached .img.xz,
    • losetup --find --show --partscan the .img,
    • lsblk to discover the rootfs partition node, then mount /dev/${PART} …,
    • rsync -aHAX --exclude '/proc/*' … the rootfs tree into _templates/<model>/,
    • cp /boot/vmlinuz-*, cp /boot/initrd.img-* and DTB-hunt (try /boot/dtb/, /boot/dtbs/<ver>/, /boot/dtb-*/) into a TrueNAS-side TFTP cache,
    • umount + losetup -d + remove /dev/* entries from the template fstab.
  3. (TrueNAS, become: true) tasks/per_host.yml creates ${nfs_rootfs_path}/<hostname>/ by cp -a --reflink=auto of the model template — CoW cheap on XFS/btrfs/ZFS, full copy on ext4. Then it customises hostname, /etc/hosts, removes machine-id, removes ssh_host_*, drops a /root/.no_armbian_first_login marker.
  4. (control node + rb5009) playbooks/stage_tftp_assets.yml + role routeros_pxe_config: fetch kernel/initrd/dtb from TrueNAS to a controller cache, then net_put them into flash:/sbc/ on rb5009 and register matching /ip tftp rules. Render pxelinux.cfg/01-<mac> from templates/pxelinux_cfg.j2 (multi-label nfs + sd, controlled by default {{ armbian_netboot_boot_mode }}).

The privileged-on-TrueNAS chain is exactly steps 2(b)–2(d): losetup, mount, then a directory-as-root rsync. Removing those is the explicit goal.

5.3 The per-host cost-shape question

The single biggest design difference is where the per-host distinction happens. PR #9656 expects you to build once per host (or once with a hostname and re-run with another hostname). This collection builds once per model and reflink-clones N hosts.

Build-per-host (PR shape)Build-per-model + reflink (ours)
CPU + IO cost for 4 hosts of the same model 4 × full debootstrap + post_customize_image + tar/rsync. ~7 min × 4 = ~28 min on helios64-class hardware. 1 × full debootstrap, then 3 × cp -a --reflink=auto. Reflink completes in seconds on XFS/btrfs/ZFS.
Disk usage on the NFS server 4 × full tree. Roughly 1.5 GB × 4 = 6 GB. 1 template + 4 hosts. On XFS/btrfs/ZFS the hosts share blocks with the template until written; closer to ~1.5 GB.
Per-host identity fields Whatever the build sets (hostname is the only one the extension differentiates). hostname, /etc/hostname, /etc/hosts 127.0.1.1, machine-id, ssh_host_*, firstlogin skip marker.
Refresh latency after a kernel change Kernel-only deploy — one compile.sh kernel + N rsyncs (the PR’s new path is essentially what we’d build by hand today). Today: rebuild image, re-extract, re-clone. Days/weeks of toil.
Recommendation: adopt PR #9656’s ROOTFS_EXPORT_DIR for the per-model template, keeping our existing per_host.yml reflink+identity flow on top of it. That preserves the cheap N-host shape, drops the privileged image extraction step, and gets us the kernel-only refresh path for free. This combination is what §7.1 describes in detail.

6. The privileged-on-TrueNAS problem, and how PR #9656 removes it

6.1 What we are doing on TrueNAS today, that we don’t want to

From per_board.yml:

# requires: become: true
losetup --find --show --partscan /path/to/orange-pi-5-pro.img
mount /dev/${PART} /mnt/extract
rsync -aHAX --exclude '/proc/*' … /mnt/extract/ /export/_templates/<model>/
cp /mnt/extract/boot/vmlinuz-* /export/_tftp_cache/<model>/vmlinuz
…
umount /mnt/extract
losetup -d ${loopdev}

The capabilities that demands on the NAS:

  • Kernel-loop module loaded.
  • Permission to allocate /dev/loopN nodes.
  • Permission to mount arbitrary block devices into a host directory — on TrueNAS this means we’re running as root (or via a sudoers entry that explicitly allows mount/umount/losetup on arbitrary arguments — functionally root).
  • Read access to the rootfs partition’s contents (which include /etc/shadow, SSH host keys, etc.).

On TrueNAS Scale this isn’t just an ergonomics problem — it means we’re effectively maintaining a privileged Ansible footprint on an appliance whose entire selling point is not being a general-purpose Linux box. The OS upgrade path can and does break losetup behaviour, kernel module availability, sudoers semantics.

6.2 What changes when the build writes the tree itself

If the build produces ${ROOTFS_EXPORT_DIR}/<model>/ as its primary output, the entire image-extraction step on TrueNAS goes away. Two viable transport patterns:

  1. Builder writes to an NFS mount of the export. The builder host (currently armbian_builders) mounts the TrueNAS NFS export as a regular client. ROOTFS_EXPORT_DIR points at the mount. rsync writes through NFS as a non-root remote user (use NFSv4 with krb5 or no_root_squash + a dedicated build UID); xattrs and ACLs are preserved as long as the export is on a filesystem that supports them (ZFS does on TrueNAS Scale).
  2. Builder writes locally, pushes via unprivileged SSH+rsync. ROOTFS_EXPORT_DIR stays on the builder. A netboot-deploy.sh-style hook rsync --deletes the tree to TrueNAS as a regular SSH user with a per-export directory the user owns. No losetup, no mount, no become: true needed on TrueNAS.

Either way, TrueNAS’s job collapses to: own the NFS export, own the disk, export it over NFS. The Ansible role talks to it as a remote SSH user (or doesn’t need to talk to it at all in pattern 1).

6.3 What we still need root for on the NAS — and how to bound it

Two residual privileges are worth being honest about:

  • Ownership of files inside the tree. Boards expect /etc, /usr, /var, etc. to be owned by uid 0. Whichever process writes the tree must therefore be able to create uid-0-owned files in the export. Two options:
    • NFS server-side: configure the export with no_root_squash for the build client’s IP only, or use NFSv4 with krb5 and an export ACL pinning that principal.
    • SSH-and-rsync from the builder: use rsync_path: 'sudo rsync' on the receive side, with a narrow sudoers entry that whitelists only the destination path. This is much narrower than today’s arbitrary-mount sudoers.
  • NFS export ownership semantics. The directory that holds the per-host rootfs trees still has to be ZFS-managed by TrueNAS itself (creating the dataset, setting the NFS export options is an admin action on the appliance). But that’s a one-time setup, not part of every build.

7. Concrete changes to make once PR #9656 merges

The PR is currently in Work in progress + Needs review state, milestone 05 (second-quarter 2026), so we can plan but shouldn’t pin against a moving branch. The list below assumes the final-merged interface stays close to what’s shipped now.

7.1 Phase A — switch the build to ROOTFS_TYPE=nfs-root and let it produce the per-model template

What changes

  • In playbooks/build_image.yml, extend armbian_build_compile_args per board with: 
    ROOTFS_TYPE=nfs-root
ENABLE_EXTENSIONS=netboot
ROOTFS_COMPRESSION=none
ROOTFS_EXPORT_DIR=<path>
NETBOOT_TFTP_PREFIX=armbian/<board_model>
  • Decide where ROOTFS_EXPORT_DIR lives. Two layouts to choose between, both eliminate the privileged extract step:
    • (A1) Builder mounts TrueNAS NFS export; the path resolves to <nfs-mount>/_templates/<board_model>/. The PR’s bind-mount-into-docker logic supports this transparently as long as the path exists on the host before the build.
    • (A2) Builder writes locally to ${SRC}/output/netboot-export/<board_model>/ and a netboot_artifacts_ready userpatch rsyncs it to TrueNAS via unprivileged SSH (with the narrow rsync_path: 'sudo rsync' trick, or no sudo at all if the destination is user-owned).
  • Delete from roles/netboot_assets/tasks/per_board.yml the sub-tree handling losetup / mount / cp /boot/vmlinuz-* / DTB hunt / umount / losetup -d. The kernel + DTB + initrd are now produced by the build at known paths inside ${tftp_out}/${PREFIX}/ — the role only needs to fetch them to the controller cache for net_put to rb5009.
  • Drop the URL preflight (roles/netboot_assets/tasks/preflight.yml) — the source of truth is the build, not armbian_netboot_image_urls. Update inventory/group_vars/all.yml to remove that key.
  • Keep per_host.yml reflink+identity logic exactly as-is — it operates on a directory tree, doesn’t care how that tree was made.

Effect

  • TrueNAS become: true need either eliminated (A1) or reduced to a single narrow sudoers entry (A2).
  • No image download → no URL preflight → no stale-mirror class of failure.
  • Per-host cost shape unchanged (still 1 build + N reflinks).

7.2 Phase B — align routeros_pxe_config with the PR’s TFTP layout

The PR’s default TFTP prefix is armbian/${LINUXFAMILY}/${BOARD}/${BRANCH}-${RELEASE}. Our existing layout is armbian/<model>/. Two options:

  1. Override NETBOOT_TFTP_PREFIX=armbian/<board_model> per build to match what our template already expects. Smallest delta, keeps pxelinux_cfg.j2 unchanged.
  2. Migrate pxelinux_cfg.j2 to the upstream default armbian/<family>/<board>/<branch>-<release> — future-proof against multi-branch coexistence, but bigger churn: every /ip tftp rule’s req-filename changes too.

Option 1 is the obvious early move; option 2 only becomes useful if we ever want to ship multiple branches/releases for the same board simultaneously (e.g. edge + current).

7.3 Phase C — pick up the watchdog and dhcpcd-ROOTSERVER hooks

Both ship inside the rootfs that post_customize_image writes — we get them automatically as soon as we switch to ROOTFS_TYPE=nfs-root. No Ansible change required. Validate: verify uInitrd contains 71-netboot-rootpath under /usr/lib/dhcpcd/dhcpcd-hooks/ or /usr/libexec/, and that zz-netboot-watchdog lives under /scripts/init-premount/ — the testing-armbian-board-hardware skill is the right harness for that check.

7.4 Phase D — kernel-only refresh path (optional but high ROI)

Wrap compile.sh kernel BOARD=… BRANCH=… ENABLE_EXTENSIONS=netboot,netboot-deploy NETBOOT_DEPLOY_SSH=… in a new playbook (e.g. playbooks/refresh_kernel.yml) or a new mode of build_image.yml. Outcomes:

  • Kernel + DTBs + matching /lib/modules/<ver>/ rsynced in one shot (the PR’s code path scopes --delete to that single kernel version, so it won’t clobber an alternative kernel).
  • Avoids the BPF: Invalid name_offset / split-BTF spam class of failure caused by vmlinuz + module mismatch.
  • Refresh cycle drops from ~7 min (full build) + extraction + reflink-N to ~30 sec (kernel build cache hit) + rsync-N.

Per-host concern: if we’ve reflinked, /lib/modules/<ver> will be deduped across hosts and the upstream rsync will COW-break it — which is fine, that’s the point. The bandwidth is still ~modules-tree-size per host. No correctness issue.

7.5 Phase E — consider per-host as part of the build, not after

Only do this if Phase A’s reflink model proves limiting (e.g. we want per-host customisations that are impossible to apply post-hoc to a templated tree — things baked into debconf answers that need to be set during debootstrap, or per-host package sets). The PR supports it via NETBOOT_HOSTNAME=…. The cost is the 4× build time discussed in §5.3.

7.6 Phase F — eventually drop our build_userpatches PXE-first overlay

Today build_image.yml injects pre_config_uboot_target__999_pxe_first to force PXE first in BOOT_TARGETS. This is logically separate from PR #9656, but worth mentioning: once the upstream nfs-root path is the documented happy path, there’s a reasonable chance Armbian itself reorders boot targets when ROOTFS_TYPE=nfs-root. Not safe to delete on merge — verify on each board first; some boards (rock-5b) need additional surgery (CONFIG_PCI_INIT_R for RTL8125 enumeration, the v2026.04 bump). This stays ours until proven otherwise.

8. Risks, blockers, and pre-merge things to track

RiskMitigation
The PR is still Work in progress. The hook surface (netboot_artifacts_ready, artifact_ready, post_create_rootfs_archive) could be renamed before merge. Don’t pin against the feature branch in production. Wait for merge to main + an Armbian release containing it, then track CHANGELOG for renames.
NETBOOT_TFTP_PREFIX default differs from ours. Explicit override via build vars (§7.2 option 1). Fast and reversible.
The PR’s nfs-root path assumes a kernel built with CONFIG_ROOT_NFS + IP_PNP_DHCP as builtins. Our build_branches: edge for rk3588 may or may not honour custom_kernel_config hooks correctly depending on hook ordering against our own extension_finish_config__999_* overrides. Validate on first orange-pi-5-pro build: extract the produced vmlinuz-*, run scripts/extract-ikconfig, grep for the expected CONFIG_*=y.
The PR injects an uInitrd (with the rootpath + watchdog hooks) into TFTP, and writes an INITRD line into pxelinux.cfg. Our routeros_pxe_config template always emits an initrd line. There’s a hard-to-debug class of failure where the uInitrd from one branch is paired with a vmlinuz from a different one. Always re-stage TFTP after a rebuild; the per-host vs per-model split in netboot_assets already handles this if we’re strict about it. Consider hashing kernel + initrd at deploy time and surfacing the digest in the boot_mode verify step.
The atomic rename of the archive (mv tmp ${ROOTFS_ARCHIVE_PATH}) requires FINALDEST to be on the same filesystem as the temp file. If we move FINALDEST across an NFS-mounted boundary, the rename is no longer atomic. If we go with pattern A1 (builder writes via NFS mount), don’t cross filesystem boundaries between ${SDCARD} and ${ROOTFS_EXPORT_DIR}. Keep the archive on the builder; only the export tree crosses.
helios4 testing in the PR found two real issues: RD-image-overlaps-OS-image on mvebu (need to skip INITRD on that family), and systemd-resolved not reading /proc/net/pnp (workaround documented but not auto-fixed). Both irrelevant for rk3588 / rk3588s; mention for completeness. The second one could bite us once a board comes up over NFS but can’t resolve DNS; add a check to the testing-armbian-board-hardware harness.
The BOOT_FDT_FILE normalisation in the PR’s artifact-collect hook is rk-friendly but trips on K3/BeagleBone-style .dts values. Not relevant today; could be once we add boards. The PR already handles this (fdt_file=${BOOT_FDT_FILE%.dts}.dtb). Track upstream changes.
The .netboot_export_marker stamp guards rsync --delete from clobbering an unrelated tree. Our current _templates/<model>/ directories do not have this marker. On first migration, either touch _templates/<model>/.netboot_export_marker before running the new build, or use NETBOOT_EXPORT_FORCE=yes once. Subsequent builds carry the marker automatically.
