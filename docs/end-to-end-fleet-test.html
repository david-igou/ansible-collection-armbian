1. Overview & mental model

Three boot modes coexist on every onboarded board, selected by the default directive inside its per-board pxelinux.cfg on rb5009:

ModeKernel fromRootfs fromU-Boot path
sd TFTP (rb5009:flash:/sbc/armbian/<model>/vmlinuz) Whatever block device is labelled armbi_root (typically SD/eMMC) U-Boot PXE → fetch TFTP kernel → kernel mounts root by label
nfs TFTP (same vmlinuz) NFS export truenas:/mnt/ssd/netboot/rootfs/<host> U-Boot PXE → fetch TFTP kernel → kernel does ip=dhcp + NFS mount
local_kernel NVMe (/boot/Image on the disk-provisioned root) NVMe partition labelled armbi_root_local U-Boot’s baked-in localcmd runs nvme scan, ext4load, booti — never touches the network

The local_kernel mode is the strategic unlock: once the board owns its own kernel, apt install linux-image-edge-* on the running board is the kernel-update mechanism. No rb5009 TFTP churn, no per-host module rsync. The cost is a one-time NVMe provision (Phase C), and forever after the board is autonomous.

Why we still test SD and NFS regularly. Both are recovery surfaces. nfs is the safe fallback when a board’s local disk has been wiped or its on-disk kernel is broken; sd is the manual recovery for when even network boot fails. If either silently regresses we won’t notice until we need them — which is always at 3 a.m.

2. Pre-flight: SSH, inventory, staging

The test runs from a workstation/jumpbox that can reach:

  • All 5 boards (default user: igou) over SSH
  • rb5009 (network_cli, user igou+cet1024w)
  • crs328 (the boards’ PoE switch, same network_cli plumbing)
  • truenas (the netboot server, user truenas_admin with sudo)

SSH-agent hygiene

Across the lifecycle the per-host SSH host key changes several times: the board boots NFS (NFS rootfs’s host keys), then SD (stock Armbian’s host keys), then local-kernel (NVMe rootfs’s host keys). Two things prevent SSH host-key prompts from blocking:

  1. ansible.cfg in the repo root sets host_key_checking = False. Belt-and-suspenders: export ANSIBLE_HOST_KEY_CHECKING=False on every invocation.
  2. For raw ssh (when ansible can’t reach a board because the user doesn’t exist yet) use -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null.

If a workstation has a populated SSH agent with stale identities that rate-limit auth, prefix every ansible* call with env -u SSH_AUTH_SOCK — that drops the agent for that invocation and forces fallback to the on-disk key chain (~/.ssh/id_ed25519 by default).

Pre-flight verification — one-liners
# Verify each tier is reachable on the right credentials.
env -u SSH_AUTH_SOCK ansible boards -m ping -o
env -u SSH_AUTH_SOCK ansible truenas.igou.systems -m ping -o
env -u SSH_AUTH_SOCK ansible rb5009.igou.systems \
  -m community.routeros.command -a 'commands="/system identity print"'

# Verify staged artefacts.
env -u SSH_AUTH_SOCK ansible truenas.igou.systems -b \
  -m shell -a 'ls /mnt/ssd/netboot/rootfs/_templates/'
env -u SSH_AUTH_SOCK ansible rb5009.igou.systems \
  -m community.routeros.command -a 'commands="/ip tftp print where real-filename~\"sbc/armbian\""'

Stage netboot assets & TFTP rows

Two playbooks own server-side state. Both are idempotent — re-running them as the first step of a campaign is a cheap sanity check that re-creates per-host rootfs clones with fresh identity (machine-id, SSH host keys, hostname) but doesn’t touch the templates.

One-time / idempotent staging
# Extract .img.xz → per-model template, clone per-host rootfs
env -u SSH_AUTH_SOCK ansible-playbook playbooks/stage_netboot_assets.yml

# Fetch vmlinuz/initrd/dtb to controller cache → push to rb5009 + register TFTP rows
env -u SSH_AUTH_SOCK ansible-playbook playbooks/stage_router.yml
Tee-shaped surprise: stock NFS rootfs has no igou user. The per-host NFS rootfs is a clone of the template extracted from Armbian’s .img.xz. The template is stock Armbian (root with a locked password and an empty /root/.ssh), so when the board boots from NFS, ansible’s default user (igou) can’t SSH in. Phase C’s reprovision_to_local.yml needs ansible reach on NFS. Two fixes, both pre-Phase-C:
  • Quick injection — on truenas, write ~/.ssh/id_ed25519.pub into the per-host NFS rootfs at /mnt/ssd/netboot/rootfs/<host>/home/igou/.ssh/authorized_keys and add an igou entry to etc/passwd / etc/shadow / etc/group / etc/sudoers.d/igou. Survives reboots.
  • Run bootstrap_armbian.yml against the running NFS-booted board (connects as root with armbian_netboot_default_password). Only works if you first re-enable password auth in the NFS rootfs’s /etc/ssh/sshd_config (Armbian disables it by default) and a root password is set.

4. Per-board lifecycle

The same 4-phase pattern (A → B → C → C2 → D) runs against each board. Each phase has a write step (pxelinux.cfg on rb5009 and/or partition table + rootfs on the board itself), a PoE cycle, a wait for TCP/22, and an evidence-capture SSH probe. Per-board artefacts land in /tmp/iter-FLEET-<host>/<phase>/.

Phase A — boot from SD

Sets default sd in the per-board pxelinux.cfg on rb5009. U-Boot fetches the TFTP-hosted kernel/initrd/dtb and the kernel command line includes root=LABEL=armbi_root, which is the default label Armbian flashes onto SD cards. The kernel mounts whichever block device has that label.

Phase A run — per-board
# Write pxelinux.cfg (no auto-cycle, so we can capture evidence with raw SSH)
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/set_boot_mode.yml \
    -e target_hosts=<host> \
    -e armbian_netboot_boot_mode=sd \
    -e armbian_netboot_cycle_board=false

# Cycle PoE separately
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/poe_control.yml --limit <host> \
    -e armbian_netboot_poe_action=cycle \
    -e armbian_netboot_poe_cycle_delay=30

# Capture evidence as root (stock Armbian has password 1234, no igou user)
unset SSH_AUTH_SOCK
sshpass -p 1234 ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
  -o PreferredAuthentications=password -o PubkeyAuthentication=no \
  root@<ip> 'findmnt -no FSTYPE,SOURCE /; cat /proc/cmdline; uname -r'

Expected evidence on a working SD boot:

  • findmnt / → ext4 /dev/mmcblkNp1 (SD card’s root partition)
  • /proc/cmdline → starts with root=LABEL=armbi_root rootfstype=ext4
  • uname -r → matches the kernel package present on the SD card’s rootfs
SD kernel modules must match TFTP vmlinuz. The kernel comes from rb5009, the modules from the SD’s /lib/modules/. If the SD card was flashed from a different Armbian release than the one extracted into the TFTP layout, the kernel may boot but lose drivers for ethernet, USB, or PCIe. Symptom: TCP/22 never comes up even though the kernel reached userspace. Fix: re-flash the SD card with the same Armbian version used to populate rb5009’s vmlinuz.

Phase B — boot from NFS

Identical TFTP path as sd, but pxelinux’s append line tells the kernel root=/dev/nfs nfsroot=<truenas-ip>:<path>,nfsvers=3,rw ip=dhcp. The initrd brings up the NIC, gets a DHCP lease, and mounts the per-host NFS rootfs as root.

Phase B run
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/set_boot_mode.yml \
    -e target_hosts=<host> \
    -e armbian_netboot_boot_mode=nfs \
    -e armbian_netboot_cycle_board=false
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/poe_control.yml --limit <host> \
    -e armbian_netboot_poe_action=cycle -e armbian_netboot_poe_cycle_delay=30

# After TCP/22 comes back up:
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible <host> -m shell -a 'findmnt -no FSTYPE,SOURCE /; cat /proc/cmdline'

Expected evidence on a working NFS boot:

  • findmnt / → nfs <truenas>:/mnt/ssd/netboot/rootfs/<host>
  • /proc/cmdline → starts with root=/dev/nfs nfsroot=…
  • hostname → the inventory hostname (proves rootfs_clone’s identity reset ran)

Phase C — reprovision NVMe (reprovision_to_local.yml)

The destructive step. Four sub-phases:

  1. Set boot mode nfs + verify the board comes up rooted on NFS.
  2. Cross-binding validation (no two layouts share a mount path, exactly one /).
  3. For each disk in armbian_netboot_local_disks: run systemd-repart against it, then rsync the running rootfs onto the freshly-formatted partitions. Filesystem labels are how preserved partitions stay idempotent across re-runs.
  4. Set boot mode local + verify the board comes back up rooted on the NVMe (findmnt / = ext4 + the device matching the layout).
Phase C run
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/reprovision_to_local.yml \
    --limit <host> \
    -e target_hosts=<host> \
    -e armbian_netboot_poe_cycle_delay=30

Total time per board: ~7 minutes (most of it is rsync --one-file-system copying the ~2 GiB rootfs from NFS to NVMe). The lifecycle has auto-revert: if the local verify step fails, it sets pxelinux back to nfs and cycles, leaving the board reachable.

-e ansible_user=root leaks into delegated tasks. If you don’t want to pre-inject igou into the NFS rootfs and instead pass -e ansible_user=root to make the reprovision reach the board, that override also applies to delegated routeros calls — rb5009 only accepts igou+cet1024w and the play will fail with “Authentication failed”. Pre-injecting igou is the cleaner answer.

Phase C2 — converge to local_kernel

After Phase C, the board is on mode local — TFTP kernel, NVMe rootfs. To get fully autonomous (no TFTP) we converge one more time to local_kernel:

Phase C2 run
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/set_boot_mode.yml \
    -e target_hosts=<host> \
    -e armbian_netboot_boot_mode=local_kernel \
    -e armbian_netboot_poe_cycle_delay=30

The pxelinux label for local_kernel is just localboot 0. U-Boot’s baked-in localcmd (installed at image_build time) takes over from there and runs: 

nvme scan;
ext4load nvme 0:1 ${kernel_addr_r} /boot/Image;
ext4load nvme 0:1 ${ramdisk_addr_r} /boot/uInitrd;
setenv ramdisk_size ${filesize};
ext4load nvme 0:1 ${fdt_addr_r} /boot/dtb/<board.dtb>;
booti ${kernel_addr_r} ${ramdisk_addr_r}:${ramdisk_size} ${fdt_addr_r}

Verification: PoE cycle the board, then check rb5009’s TFTP HITS for the board’s vmlinuz/initrd/dtb stayed flat. If they incremented, U-Boot was still using the PXE path (something’s wrong with the baked localcmd — usually means the image_build hook didn’t fire).

Confirm local_kernel isn’t falling back to TFTP
# Snapshot vmlinuz HITS, cycle, snapshot again
HITS_BEFORE=$(env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible rb5009.igou.systems -m community.routeros.command \
  -a 'commands="/ip tftp print where real-filename~\"<model>/vmlinuz\""' \
  2>/dev/null | grep -oE '[0-9]+$' | tail -1)
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/poe_control.yml --limit <host> \
    -e armbian_netboot_poe_action=cycle -e armbian_netboot_poe_cycle_delay=30
# Wait for TCP/22 …
HITS_AFTER=$(env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible rb5009.igou.systems -m community.routeros.command \
  -a 'commands="/ip tftp print where real-filename~\"<model>/vmlinuz\""' \
  2>/dev/null | grep -oE '[0-9]+$' | tail -1)
echo "vmlinuz HITS delta: $((HITS_AFTER - HITS_BEFORE)) (expect 0)"

Phase D — in-place kernel update

The whole point of local_kernel: apt on the running board owns the kernel. The Armbian postinst hook rewrites /boot/Image, /boot/uInitrd, and the /boot/dtb/ directory whenever a kernel package is installed or upgraded. On the next PoE cycle, U-Boot’s localcmd loads whatever /boot/Image now points to.

Phase D run
# Snapshot current kernel
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible <host> -m shell -a 'uname -r; ls -la /boot/Image'

# Install / upgrade kernel
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible <host> -b -m shell \
    -a 'DEBIAN_FRONTEND=noninteractive apt-get install -y \
        --allow-downgrades linux-image-edge-rockchip64=<target> \
                            linux-dtb-edge-rockchip64=<target>'

# Cycle and verify uname -r changed
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/poe_control.yml --limit <host> \
    -e armbian_netboot_poe_action=cycle -e armbian_netboot_poe_cycle_delay=30
# After TCP/22:
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible <host> -m shell -a 'uname -r'
Hardware-compat risk. Today’s run hit a real-world pitfall: the unofficial Armbian build that produced the original on-disk kernel (7.0.7-edge-rockchip64) has a higher Debian version string than the public apt repo’s current edge (26.2.1 → kernel 6.19.0-edge-rockchip64), so the only available “upgrade” is a kernel downgrade. On orange-pi-5-pro that downgrade booted but lost the YT6801 NIC driver, leaving the board unreachable. The mechanism was proven (apt postinst updated /boot/Image, U-Boot loaded it). Recovery: switch pxelinux to nfs, cycle, mount NVMe at /mnt/nvme, copy the NFS rootfs’s /boot/vmlinuz-7.0.7-edge-rockchip64 + /lib/modules/7.0.7-edge-rockchip64/ over, repoint symlinks, set boot mode back to local_kernel, cycle.

5. The one-shot fleet playbook

Running each phase manually is good for the first run — you see the wiring and own the failure modes. Once that’s clear, playbooks/test_fleet_e2e.yml drives the whole loop end-to-end across every host in boards (or a subset).

One-shot fleet test — recommended usage
# Full fleet (all 5 boards), default target group
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/test_fleet_e2e.yml

# Subset (use -e target_hosts=, not --limit — plays delegate to rb5009/truenas/PoE)
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/test_fleet_e2e.yml \
    -e target_hosts=opi5pro-01.igou.systems,rock-5b-01.igou.systems

# Skip phases you’ve already proven
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/test_fleet_e2e.yml \
    -e skip_sd=true -e skip_kernel_update=true

# Pin the Phase D kernel target (e.g. for a regression-confirmed older version)
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/test_fleet_e2e.yml \
    -e kernel_pkg=linux-image-edge-rockchip64 \
    -e kernel_update_pin=26.2.1

The playbook is composed of seven plays. Parallelism is per-play (ansible’s default forks applies across hosts), except for Phase C which is forced to serial: 1 — running systemd-repart + rsync against the NFS rootfs on multiple boards simultaneously causes NFS read contention that hangs the I/O loop.

Per-board outputs

Each phase writes a small evidence file under /tmp/iter-FLEET-<host>/<phase>/: 

/tmp/iter-FLEET-opi5pro-01/
├── A-sd/sd-boot-evidence.txt
├── B-nfs/nfs-boot-evidence.txt
├── C2-localkernel/local-kernel-evidence.txt
└── D-kupdate/kernel-update-evidence.txt

Phase C (reprovision) doesn’t write a fleet-specific evidence file — the standalone reprovision_to_local.yml already emits a diagnostic bundle on failure under ./diagnostics/ (path configurable via -e armbian_netboot_diagnostic_bundle_dir=). The successful-path proof is implicit in Phase C2 (which asserts the board boots from the freshly-rsynced NVMe rootfs).

Exit semantics

Any phase failure halts the playbook for the affected host(s) immediately — ansible’s default. Other hosts in the parallel phases continue to completion (their own per-host state is independent). The lifecycle _lifecycle_set_and_verify.yml wrapper auto-reverts a failed boot-mode transition back to nfs (the safest reachable state), so a Phase C2 failure won’t leave a board stuck on a broken local_kernel.

Phase D failure does NOT auto-revert. If apt install succeeds but the new kernel breaks the board’s NIC (the YT6801 regression hit during today’s run), the cycle leaves the board offline. Recovery is manual: set the board to nfs mode (set_boot_mode.yml on rb5009 only, no SSH to the board needed), cycle, mount the NVMe at /mnt/nvme from the NFS-booted board, copy the NFS rootfs’s working kernel binary + modules onto the NVMe, re-point /boot/Image, converge back to local_kernel. See §6 “Common gotchas” for the recipe.

7. Common gotchas the test exposed

GotchaWhere it bitesMitigation

Deep-dive: why Phase C is slow on large NVMes

systemd-repart sets up a loop device view of the target NVMe (with a 1 MiB offset for the partition table) so it can write the GPT atomically. mkfs.ext4 then runs against that loop device. The loop device’s per-ioctl discard chunk is hard-capped at 128 KiB, while the NVMe itself natively supports 2 TiB discard chunks: 

# on the running rock-5b
$ cat /sys/block/loop0/queue/discard_max_bytes
131072                  # 128 KiB — loop driver default

$ cat /sys/block/nvme0n1/queue/discard_max_bytes
2199023255040           # 2 TiB — NVMe native

When mkfs.ext4 defaults invoke BLKDISCARD on the whole device, the kernel breaks the request into 128 KiB chunks. For a 477 GiB partition that’s ~3.7 million individual ioctls — each one a syscall round-trip with writeback-throttle (wbt_wait) bookkeeping. The kernel stack trace from our run confirms this: 

# pid 1349 = mkfs.ext4 (child of systemd-repart pid 1348)
$ cat /proc/1349/stack
[<0>] wbt_wait+0xbc/0x130             # writeback throttle
[<0>] __rq_qos_throttle+0x38/0x58
[<0>] blk_mq_submit_bio+0x59c/0x848
[<0>] __submit_bio+0x8c/0x238
[<0>] submit_bio_wait+0x5c/0xa8
[<0>] blkdev_common_ioctl+0xde8/0xf18  # ← BLKDISCARD ioctl

# its I/O stats — userspace has barely written anything
$ cat /proc/1349/io
rchar: 11397
wchar: 2257
write_bytes: 0

The ~7 GiB/min throughput we observe is the kernel chewing through millions of 128 KiB discard ioctls. The NVMe itself can do effectively-instant TRIM at its native chunk size; the loop driver is the throttle. The same overhead exists on the smaller boards — it just stays under 15 min there.

Recommended combination: pre-discard with blkdiscard (best speedup, lowest risk), and set SYSTEMD_REPART_MKFS_OPTIONS_EXT4="-K" in the systemd-repart invocation env (so even a re-run on a non-fresh disk doesn’t re-pay the cost). Leave --discard=yes on systemd-repart as a safety net so any partition-boundary blocks the wipe missed still get TRIM’ed.

Proposed patch to roles/disk_provision/tasks/_apply_repart.yml
# Before the existing "Apply repart: run systemd-repart" task, add:
- name: "Apply repart: pre-discard whole disk for fast wipe (NVMe native chunk size)"
  ansible.builtin.command:
    cmd: "blkdiscard {{ disk_binding.device }}"
  become: true
  when: (disk_binding.fast_wipe | default(true)) | bool
  changed_when: true
  # Optional: failed_when: false  — devices without discard support
  # (some eMMC, some USB SSDs) exit 2 here; mkfs would silently skip
  # discard too, so failure isn't fatal.

# Then change the existing systemd-repart command to set the mkfs env:
- name: "Apply repart: run systemd-repart"
  ansible.builtin.command:
    cmd: >-
      systemd-repart
      --definitions={{ _dp_repart_defs }}
      --empty={{ _dp_repart_empty }}
      --dry-run=no
      --discard=yes
      {{ disk_binding.device }}
  environment:
    SYSTEMD_REPART_MKFS_OPTIONS_EXT4: "-K"   # skip per-block discard at mkfs time

The per-host opt-out (fast_wipe: false on a disk binding) leaves the door open for boards that need the slow path (e.g. SD cards with broken TRIM firmware), but defaults to fast for the common NVMe case.

Phase D recovery recipe (when a new kernel bricks the board)

When apt installs a new kernel that fails to boot from NVMe (typical symptoms: TCP/22 never returns, DHCP lease class-id stays U-Boot.armv8 rather than transitioning to a Linux client-id), recover via NFS:

Recovery — restore working kernel onto NVMe via NFS
# 1. Switch board back to NFS (router-only, no SSH to the board needed)
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/set_boot_mode.yml \
    -e target_hosts=<host> -e armbian_netboot_boot_mode=nfs \
    -e armbian_netboot_poe_cycle_delay=30

# 2. From the NFS-booted board, mount NVMe and copy NFS rootfs's working kernel onto it
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible <host> -b -m shell -a '
    mkdir -p /mnt/nvme && mount /dev/nvme0n1p1 /mnt/nvme
    cp -a /boot/vmlinuz-<working-ver> /mnt/nvme/boot/
    cp -a /boot/uInitrd-<working-ver> /mnt/nvme/boot/ 2>/dev/null \
      || cp -a /boot/initrd.img-<working-ver> /mnt/nvme/boot/
    chroot /mnt/nvme /bin/bash -c "
      rm -f /boot/Image /boot/uInitrd
      ln -sf vmlinuz-<working-ver> /boot/Image
      ln -sf uInitrd-<working-ver>  /boot/uInitrd \
        || ln -sf initrd.img-<working-ver> /boot/uInitrd"
    [ -d /mnt/nvme/lib/modules/<working-ver> ] \
      || cp -a /lib/modules/<working-ver> /mnt/nvme/lib/modules/
    umount /mnt/nvme'

# 3. Converge back to local_kernel
env -u SSH_AUTH_SOCK ANSIBLE_HOST_KEY_CHECKING=False \
  ansible-playbook playbooks/set_boot_mode.yml \
    -e target_hosts=<host> -e armbian_netboot_boot_mode=local_kernel \
    -e armbian_netboot_poe_cycle_delay=30

Future speed & consistency improvements

This section catalogues optimisations beyond the fast_wipe mitigation already shipped. Each entry estimates implementation effort, expected speedup or consistency gain, and trade-offs. Sorted by impact-to-effort ratio. Entries marked shipped have landed in playbooks/test_fleet_e2e.yml; the rest remain open.

Parallelise Phase C (NFS rsync contention) — shipped + validated (throttle: 2)

Status: Phase C now defaults to throttle: 2 (was serial: 1). Dial via -e fleet_phase_c_throttle=N; fleet_phase_c_throttle=1 restores pure-serial behaviour for operators on under-provisioned NFS servers. ZFS-per-host + vmtouch pinning remain open (would unlock fully-parallel). Validated on the 5-board fleet run: Phase C wall time 881 s (over 5 boards in batches of 2) vs ~1 751 s serial-over-4 in the prior baseline.

Phase C is currently serial: 1 because four simultaneous rsyncs of the per-host NFS rootfs all read from the same TrueNAS pool, contending on the NFS server’s mds/dnlc caches and saturating the 1 GbE link. Two mitigations make parallel feasible:

  • Ansible throttle: N on Phase C (docs): let 2 boards run Phase C in parallel while keeping the floor low enough that NFS doesn’t hang. Cuts Phase C wall time by ~2× for a 5-board fleet without the contention risk of fully-parallel.
  • ZFS dataset-per-host on TrueNAS: today every per-host NFS rootfs is a sibling under a single dataset. Splitting each into its own dataset lets ZFS read-ahead + ARC cache scale per-host. With 5 datasets, the rsync source contention drops to near-zero. Requires a one-time TrueNAS reorganisation.
  • Read-cache pinning: vmtouch -t the per-host rootfs file tree before Phase C so the rsync source reads are page-cache hits, not NFS-server disk reads. Cheapest win.

Expected combined effect: full-fleet Phase C drops from ~25 min (serial) to ~5-7 min (2-board throttle + dataset split + page-cache warm).

Replace rsync with CopyBlocks= for the bulk transfer

systemd-repart supports CopyBlocks=, which raw-block-copies a source device or image directly into a newly-created partition via copy_bytes_full(). Demonstrated throughput in the wild: ~1.3 GB/s (block-level, no rsync metadata overhead). For a ~2 GB Armbian rootfs that’s ~2 seconds vs rsync’s ~40 seconds.

Implementation path: image_extract produces a per-model raw rootfs image (e.g. orange-pi-5-pro.rootfs.img) alongside the existing template directory. The disk_provision role’s .repart.d/<part>.conf for the root partition adds CopyBlocks=/path/to/orange-pi-5-pro.rootfs.img. Per-host identity reset (machine-id, hostname, SSH host keys) moves from the rootfs-clone role into a post-CopyBlocks fixup task that edits the freshly-copied filesystem in-place.

Trade-off: loses per-host-already-customised state on the NFS source (since CopyBlocks ignores anything not in the master image). Fine for greenfield re-provision, harmful if operators have manually tweaked per-host NFS rootfses.

Pin Phase D’s kernel target for deterministic upgrades — partly shipped

Phase D used to run apt install linux-image-edge-rockchip64 with state: latest unconditionally. This produces “no-op” results when the locally-installed unofficial-build version is newer than the apt repo’s latest, which is the dominant case in our fleet today (the 26.05.0-trunk build vs the repo’s 26.2.1). Three improvements:

  • Per-board kernel pin in inventory — shipped: a per-host armbian_netboot_kernel_target: "26.05.0-trunk" hostvar pins Phase D to a specific version (state: present, allow_downgrade: true). Precedence: hostvar > -e kernel_update_pin > apt latest. Phase D’s evidence file records the effective target and which precedence rung it came from.
  • Two-step Phase D: (1) downgrade to a known-old apt-repo version (26.2.1) — proves the swap works; (2) re-install the inventory-pinned version — restores fleet homogeneity. Each step verifies uname -r changed after PoE cycle.
  • Image-build trigger from kernel CVE feed: cron job that watches DSAs + the Armbian kernel-package changelog, opens an issue in the collection repo when a fleet kernel needs rebuilding. Forces Phase D to be useful even when the apt repo lags.

Tighter PoE-cycle budget — partly shipped

Each phase pays a fixed cost: 30 s capacitor drain + ~30 s TCP/22 wait + ~30 s SSH stability + ~30 s wait_for_connection delay. ~2 min per transition × 4 transitions per board = ~8 min just on PoE cycles. Knobs to dial:

  • armbian_netboot_poe_cycle_delay: 30 s is conservative for RK3588 voltage-select reliability. Boards on stable PoE-HAT firmware can drop to 10 s without regressions; halves cycle-related wait. Inventory knob — tune per fleet.
  • wait_for_connection delay: 30 in wait_for_ssh_with_cycle_retry.yml is a pre-poll sleep. For boards that consistently come up in < 20 s, drop to delay: 10; the polling loop catches the same TCP/22 open without the upfront waste. Open — in-tree task file.
  • Skip Phase A’s revert-to-NFS — shipped + validated: Phase A’s second cycle is gone. Phase B now owns the SD → NFS transition end-to-end via _lifecycle_set_and_verify (writes default nfs + PoE-cycles + verifies). On the validation run Phase A dropped from 538 s → 260 s (per board) while Phase B picked up 237 s — net savings ~40 s per board because one of the two cycles is no longer needed.

Together: ~3-5 min off the per-board lifecycle without changing what’s tested.

Phase A — replace sshpass raw-SSH with ansible-native — shipped + validated

The Phase A probe used to be a delegated shell: task that invoked sshpass -p 1234 ssh ... root@<host> with SSH_AUTH_SOCK="" set in the task environment to bypass the controller’s ssh-agent. It worked, but it baked an assumption (SD is at the pre-bootstrap stock-Armbian state with a password-auth root account) and bypassed Ansible’s connection layer entirely.

Phase A now uses the same in-tree primitives as test_hardware_e2e.yml Phase 1 (with one new flag for the SD-state-unaware case):

  1. cold_boot_with_retry.yml with _skip_ssh_stability_check: true — PoE cycle + TCP/22 wait, retried on flake via armbian_netboot_boot_retry_attempts (default 1 at fleet-play scope — one rock-5b SD voltage-select flake survives). The wait_for_connection step inside cold_boot_single_attempt is gated on the new flag, so the inventory-user identity isn’t consulted yet.
  2. auto_bootstrap_if_needed.yml — probes as the inventory user. Fast no-op on a previously-bootstrapped SD card; runs bootstrap_armbian inline against root + armbian_netboot_default_password on a fresh-flashed SD card. Phase A is now agnostic to whether the SD card carries the igou user or not.
  3. wait_for_ssh_with_cycle_retry.yml + setup + assert on ansible_mounts['/'] (rootfs not in ['nfs', 'nfs4'] and device starts with /dev/). No more 'mmcblk' in stdout regex — the SD slot enumeration is per-board, so local-block + non-NFS is the durable invariant across the fleet.

Validated end-to-end on the post-recs validation run: 5/5 boards PASS in 29 min 38 s; opi5pro-01 specifically exercised the bootstrap-fallback branch (its SD card had only root + password 1234) while the other four hit the fast no-op path because igou was already present.

Open: dd a known image to SD as a pre-flight (full state reset)

The auto_bootstrap_if_needed approach handles the “has the SD card been bootstrapped yet?” question reactively: probe-then-bootstrap. An alternative considered during this refactor is proactive: kick off the fleet test with an early netboot phase that dd’s the public Armbian image to /dev/mmcblkN on every board, so every board starts the run in the same known (stock-Armbian, un-bootstrapped) state.

Trade-offs:

  • Pros: explicit per-run reset — no cross-iteration state drift on the SD card (machine-id, host keys, manually-installed packages, mid-bootstrap remnants); Phase A’s probe-then-bootstrap path becomes deterministic-bootstrap; surfaces SD card hardware failures (write errors) immediately rather than during a later phase.
  • Cons: adds a heavy step (download + decompress + dd ~2 GB) to every fleet run; the current approach already converges on the same end state via Phase C (NVMe reprovision from the canonical NFS template); doesn’t buy anything for boards that only boot from NVMe (Phase A is the only SD-using phase).

Not implemented. Would slot in as a new Phase 0 — dd canonical image to SD play that runs while the board is on NFS (so the SD card is unmounted), using the existing per-host NFS rootfs as the dd host. Punt on this until there’s evidence the reactive approach drifts.

Skip --empty=force on already-discarded disks

The current fast_wipe path runs blkdiscard (~1 s) then systemd-repart --empty=force --discard=no. The --empty=force still creates a loop device to write the new GPT atomically. For repeat provisions where the disk already carries our exact partition layout (per-host idempotent re-runs), this is wasted work. Two cleaner paths:

  • Hash-check the existing GPT: compare the on-disk partition signature against what the layout would produce. Identical → skip systemd-repart entirely, jump to rsync.
  • Use --empty=allow: keeps any existing partition table that matches; only writes new entries. Fits the preserve_on_reprovision flow already in the role.

Image-build determinism (campaign reproducibility)

Today the unofficial Armbian build process pins armbian/build at HEAD of the chosen branch (trixie edge), which can drift between weekly rebuilds. Consistency improvements:

  • Pin armbian/build commit SHA per release: record the SHA in vars/boards.yml; image_build checks out that SHA explicitly. Reproducible across operator workstations.
  • Capture U-Boot env + defconfig in the published artefact: today the build logs include the localcmd bake; persist a u-boot-metadata.json sibling to each .img.xz with the baked env vars, defconfig SHA, and target board model. The fleet test can compare runtime fw_printenv output against the metadata for a drift-detection assertion.
  • SBOM: kernel package version, all U-Boot drivers compiled in, image size, partition layout — emitted into a .sbom.json per build. Consumed by Phase D’s drift check.

Pre-discard NVMes during NFS lifetime

Even with fast_wipe, the blkdiscard itself is < 1 s, but the underlying NVMe TRIM takes finite background time to actually free the cells. For boards that frequently re-provision, schedule a periodic fstrim (or blkdiscard of the unused partition) while the board is NFS-booted — so when Phase C fires, the NVMe is already in “all blocks empty” state and the systemd-repart write path is purely sequential.

Failure isolation (one bad board ≠ failed fleet test)

Today a single board’s Phase C failure halts the play for that host and the playbook exits non-zero. With serial: 1, the remaining boards never get tested. Improvements:

  • any_errors_fatal: false with max_fail_percentage so up to N boards can fail before the play aborts.
  • Per-board exit code accumulator (a set_fact that records each board’s pass/fail status); the Summary play emits a structured table at the end. Operators get the “4/5 pass, rock-5b NVMe absent” signal in one read.
  • run-iter.sh-style per-board GitHub-tracker comment auto-posting (already exists for test_hardware_e2e.yml; port to the fleet test).

Consistency: post-run summary report

Today the Summary play just prints the artefact directory path per host. Tighter feedback loop with:

  • Per-phase wall-time histogram (so an operator can see Phase C drifted from 8 s to 28 min over the campaign).
  • Per-board comparison table (so “rock-5b is the outlier” is visible at a glance).
  • Phase D uname -r before/after delta highlighted (so no-op kernel updates and successful swaps look different).
