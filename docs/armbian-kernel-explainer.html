Armbian kernels — build-time vs apt-time

When compile.sh runs, does it build a kernel from source or pull one from an apt repository? And what does apt upgrade do on the running board afterwards? This page answers both, then ends at a recipe for keeping kernels current across multiple boards on different kernel trees. Pinned to armbian/build v26.2.0-trunk.844 (the ref this collection uses) and cross-checked against the Armbian developer guide.

1. TL;DR

  • Build time: compile.sh always compiles the kernel from source. It clones KERNELSOURCE, checks out KERNELBRANCH, applies the patches under patch/kernel/archive/${KERNELPATCHDIR}, runs make, and emits linux-image-${BRANCH}-${LINUXFAMILY}_*.deb and friends into output/debs/. It does not pull a prebuilt kernel from apt.armbian.com.
  • Apt time: every Armbian image ships /etc/apt/sources.list.d/armbian.sources pointing at apt.armbian.com (or beta.armbian.com on nightly builds). apt update && apt upgrade will fetch newer versions of linux-image-${BRANCH}-${LINUXFAMILY} from there and install them with standard dpkg semantics.
  • Collision rule: your locally-built deb and the apt.armbian.com deb have the same package name. If the upstream version-string is higher, apt upgrade replaces yours silently. armbian-config ⇒ "Disable Armbian kernel/firmware upgrades" is the supported pin.
  • For this collection: all of our userpatches are U-Boot-side (PXE-first BOOT_TARGETS, CONFIG_PCI_INIT_R, the rock-5b v2026.04 pin). The kernel artifact is unmodified Armbian. So kernel apt-upgrades are safe; linux-u-boot-* apt-upgrades would silently regress the netboot invariant. See §9.

2. Two layers of "kernel" in an Armbian board's lifecycle

The confusion this page exists to clear up is that there are two independent moments where a kernel gets onto a board, and they use completely different mechanisms:

LayerWhenWhere the kernel comes fromDriver
Build Once, on the builder host, ahead of imaging Compiled from upstream git (Armbian's fork or mainline) inside the build container ./compile.sh BOARD=… BRANCH=…
Apt Every time the user runs it on a running board (or unattended-upgrades fires) Prebuilt .deb on apt.armbian.com, built by Armbian's CI apt update && apt upgrade (or armbian-config)

Crucially, both produce packages with the same name (linux-image-${BRANCH}-${LINUXFAMILY}). dpkg only sees a version number — it does not know or care that one was hand-rolled. This is the source of the collision question in §7.

3. Build time: what compile.sh actually does to a kernel

The flow inside one compile.sh invocation is roughly:

Every step that mutates kernel source code happens before the make at step 5: the patch series, any pre_config_kernel hooks, and the KERNEL_CONFIGURE=yes menuconfig dialog. After step 5 the artifact is sealed: it is just a versioned .deb.

lib/functions/compilation/kernel-debs.sh · armbian/build (excerpted) package naming

display_alert "Packaging linux-image" "${LINUXFAMILY} ${LINUXCONFIG}" "info"
create_kernel_deb "linux-image-${BRANCH}-${LINUXFAMILY}" "${debs_target_dir}" kernel_package_callback_linux_image "linux-image"

display_alert "Packaging linux-dtb" "${LINUXFAMILY} ${LINUXCONFIG}" "info"
create_kernel_deb "linux-dtb-${BRANCH}-${LINUXFAMILY}"   "${debs_target_dir}" kernel_package_callback_linux_dtb   "linux-dtb"
…
# (in the control-file emit):
Package: ${package_name}
Provides: linux-image, linux-image-armbian, armbian-$BRANCH, wireguard-modules
  • The deb name is literally templated as linux-image-${BRANCH}-${LINUXFAMILY}. For our rock-5b on BRANCH=edge in the rk35xx family that resolves to linux-image-edge-rk35xx. For an orange-pi-5-pro on BRANCH=current (same family on this collection's pin) it resolves to linux-image-current-rk35xx.
  • Note: LINUXFAMILY is not BOARD. Many boards collapse onto the same family — and therefore the same kernel deb. See §9.

4. The four BRANCH values and the kernel trees they point at

The Armbian developer guide describes BRANCH as: "Set kernel and U-Boot branch manually to skip dialog prompt", with options vendor, legacy, current (recommended), and edge (Build Switches). The flag is a single selector that maps to a different upstream kernel tree per family.

For the rk3588 family (the only one this collection consumes), the family file config/sources/families/rockchip-rk3588.conf splits as:

BRANCHKERNELSOURCEKERNELBRANCHKernel versionStatus
legacyarmbian/linux-rockchiprk-5.10-rkr85.10.xdeprecated, slated for removal
vendorarmbian/linux-rockchiprk-6.1-rkr5.16.1.xRockchip BSP — best peripheral coverage
currentinherited from rockchip64_common.inc — mainline LTStracked LTS tage.g. 6.12.xrecommended general-purpose
edgeinherited from rockchip64_common.inc — mainline tiplatest stable tage.g. 6.17.xnewest, less curation
Don't confuse "branch" axes. "Armbian branch" (current/edge/…) is an Armbian-side selector. "Kernel branch" (the git ref on the kernel tree) is what that selector resolves to. The collection's U-Boot explainer §2 makes the same point for the U-Boot side, and the resolution mechanism (family file → case-arm → board file → userpatches) is the same.

KERNEL_CONFIGURE is orthogonal to BRANCH. With KERNEL_CONFIGURE=yes the build pauses at make menuconfig for interactive edits; with KERNEL_CONFIGURE=no (this collection's default, roles/armbian_build/defaults/main.yml) the build uses the family's checked-in config/kernel/<family>-<branch>.config verbatim. Either way, the build still compiles from source — the switch only controls whether you get a chance to tweak the .config.

5. The .deb packages a build produces

One successful compile.sh run produces (per the kernel-debs packaging function quoted in §3):

linux-image-${BRANCH}-${LINUXFAMILY}
The kernel image (/boot/vmlinuz-*), modules (/lib/modules/*), and — for in-tree DTBs — the device tree blobs under /usr/lib/linux-image-…/. The artifact that PXE / U-Boot eventually loads.
linux-dtb-${BRANCH}-${LINUXFAMILY}
Device tree blobs under /boot/dtb/ on Armbian images (path is family-dependent). For ARM SBCs this is the file U-Boot fetches over TFTP as board.dtb in the netboot flow.
linux-headers-${BRANCH}-${LINUXFAMILY}
Source-tree subset under /usr/src/, needed for DKMS, out-of-tree module builds. Skipped on some older kernels (the build logs say so).
linux-libc-dev-${BRANCH}-${LINUXFAMILY}
UAPI headers, mostly transparent for normal use.
linux-u-boot-${BRANCH}-${BOARD} aside
Built by a separate flow (see U-Boot explainer), but relevant here because it lands in the same image. This is the deb that carries this collection's custom PXE-first BOOT_TARGETS — and the deb whose apt-upgrade would silently regress the netboot invariant.

All four kernel debs declare Provides: linux-image, linux-image-armbian, armbian-${BRANCH}. The armbian-${BRANCH} alias is what Armbian's armbian-bsp-cli-${BOARD} meta-package pins against to keep an image internally consistent (e.g. so you can't end up with linux-image-current-rk35xx and linux-dtb-edge-rk35xx co-installed).

6. Apt time: what happens when you run apt update && apt upgrade

The Armbian image that compile.sh produced has, in its rootfs:

/etc/apt/sources.list.d/armbian.sources · shipped by armbian/build
Types: deb
URIs: http://apt.armbian.com
Suites: bookworm
Components: main bookworm-utils bookworm-desktop
Signed-By: /usr/share/keyrings/armbian.gpg
  • For nightly images, distro-agnostic.sh does sed -i 's/apt/beta/' so the URIs become beta.armbian.com. Stable Armbian releases keep apt.armbian.com.
  • The Debian sources (deb.debian.org) ship in a separate /etc/apt/sources.list. Standard userland packages come from there; kernels / DTBs / U-Boot come from apt.armbian.com.

When the user runs apt update && apt upgrade:

  1. apt fetches the Armbian repo index and discovers that apt.armbian.com has, say, linux-image-current-rk35xx version 26.2.0-S0001-D0001-P0000-Cf01eHfe66-HKf2c8-V73e7-Bcd0b-Rc127 (Armbian's hash-suffixed version scheme).
  2. apt compares against the locally-installed version (whatever compile.sh stamped at build time — typically something like 26.2.0-trunk.844).
  3. If upstream is newer by dpkg's lexical version comparison, apt schedules an upgrade. It removes the old linux-image-… postinst hooks, drops the new kernel into /boot/, runs update-initramfs, regenerates boot.scr (because the Armbian linux-image postinst calls armbian-update-initramfs which calls mkimage).
  4. On next boot the new kernel runs.

Nothing in this path is netboot-aware. The board doesn't know whether its rootfs is on SD, eMMC, or NFS — the kernel deb just installs into whatever rootfs it finds itself in. And that is exactly where it falls apart on a netbooted board: there are two physical copies of "the kernel" on the network, apt only touches one of them, and the one apt touches is not the one that boots.

6.1 Two kernels on the network — only one of them boots

On a netbooted board in this collection, "the kernel" exists in three locations, owned by three different mechanisms:

Location Path Written by Read at boot?
rb5009 TFTP store flash:/sbc/armbian/orange-pi-5-pro/{vmlinuz,initrd.img,board.dtb} stage_netboot_assets.yml (net_put from controller cache) Yes — U-Boot fetches all three from rb5009 over TFTP, per the KERNEL / INITRD / FDT lines in pxelinux.cfg/01-<mac>
NFS rootfs /boot/ <per-host-export>/boot/vmlinuz-X.Y.Z-… apt upgrade (linux-image postinst) No — this directory is never consulted on a netbooted board; boot.scr here is for SD-boot only
NFS rootfs /lib/modules/ <per-host-export>/lib/modules/X.Y.Z-…/ apt upgrade (linux-image postinst) Yes — the running kernel modprobes from /lib/modules/$(uname -r)/ as a runtime path

apt upgrade only writes to rows 2 and 3. Row 1 — the file that actually gets tftpbooted by U-Boot — is invisible to dpkg. apt has no idea rb5009 exists.

6.2 Boot-time read path on a netbooted board

  1. PoE on; SoC powers on; U-Boot runs from SPI/SD/eMMC.
  2. U-Boot DHCPs; offer carries next-server pointing at rb5009.
  3. U-Boot's PXE bootmeth fetches pxelinux.cfg/01-<mac> from rb5009. That file says, literally: KERNEL armbian/orange-pi-5-pro/vmlinuz.
  4. U-Boot TFTPs that path from rb5009 into RAM at kernel_addr_r. Same for INITRD and FDT. The kernel binary that runs came from rb5009, not from the NFS rootfs.
  5. U-Boot bootis into the kernel. Kernel parses the APPEND line, sees root=/dev/nfs nfsroot=<ip>:<path>, mounts the NFS rootfs from TrueNAS.
  6. systemd starts; the running kernel modprobes drivers from /lib/modules/$(uname -r)/ on the NFS rootfs — where $(uname -r) is whatever version was compiled into the vmlinuz from step 4.

6.3 The apt-upgrade write path, file by file

Suppose the running board (uname -r = 6.12.X-current-rk35xx) runs apt update && apt upgrade, and the upstream linux-image-current-rk35xx has bumped to 6.12.Y-current-rk35xx. dpkg performs:

Effect on the per-host NFS rootfs · all paths relative to <nfs_rootfs_path>/<inventory_hostname>/
--- removed (old linux-image deb) ---
/boot/vmlinuz-6.12.X-current-rk35xx
/boot/initrd.img-6.12.X-current-rk35xx
/boot/config-6.12.X-current-rk35xx
/boot/System.map-6.12.X-current-rk35xx
/lib/modules/6.12.X-current-rk35xx/        ← gone, entire directory

+++ added (new linux-image deb) +++
/boot/vmlinuz-6.12.Y-current-rk35xx
/boot/initrd.img-6.12.Y-current-rk35xx
/boot/config-6.12.Y-current-rk35xx
/boot/System.map-6.12.Y-current-rk35xx
/lib/modules/6.12.Y-current-rk35xx/        ← new

postinst hooks then run inside the rootfs:
- update-initramfs (regenerates initrd.img-6.12.Y)
- armbian-update-uboot / mkimage (regenerates /boot/boot.scr —
  which only matters for SD-boot, not netboot)
  • Everything in this diff is inside the NFS rootfs. rb5009's flash is not reached at any point.
  • The DTB package linux-dtb-current-rk35xx performs an analogous swap under /boot/dtb/ in the rootfs — also invisible to rb5009.

6.4 What happens on the next reboot

rk3588 Armbian configs build most networking and storage drivers in-tree (built into vmlinuz, not modules), so the typical practical outcome is "board still boots, you can still ssh in, but audio/DRM/peripheral modules are missing." The worst-case outcome — a driver you actually need for ssh is a module — is rare on this family but not impossible (Wi-Fi, some USB-NICs).

Correction to an earlier draft of this page. A previous version of §6 claimed "the next netboot picks up the new vmlinuz from the same export." That was wrong. On a netbooted board the kernel binary comes from rb5009's TFTP store, not from the NFS rootfs's /boot/. The export's /boot/ is dead code at boot time; it gets updated by apt upgrade and then ignored.

6.5 How to actually pick up a new vmlinuz on a netbooted board

Because apt upgrade doesn't reach rb5009, you need a separate step to re-stage the TFTP-served files. Two paths today, plus one that could exist:

Path 1: rebuild + restage supported
ansible-playbook playbooks/build_image.yml         # compile fresh kernel from source
ansible-playbook playbooks/stage_netboot_assets.yml  # extract /boot/* from .img.xz; net_put to rb5009
This is the only path the collection currently supports. Note that build_image.yml compiles against the pinned armbian_build_ref (v26.2.0-trunk.844), so it can fall behind apt.armbian.com. To pull the build pin forward, bump armbian_build_ref in roles/armbian_build/defaults/main.yml and re-run.
Path 2: don't let apt upgrade the kernel on netbooted boards recommended
Hold linux-image-*, linux-dtb-* (and linux-headers-* if installed) on netbooted boards. This makes kernel currency a build-pipeline concern only, eliminating the divergence entirely. See the corrected Recipe A in §9.
Path 3 (doesn't exist today): "copy from rootfs to TFTP" role
After apt upgrade, a role could read <per-host-export>/boot/vmlinuz-* + initrd.img-* + <per-host-export>/boot/dtb/<board.dtb> and net_put them to rb5009 under the per-model TFTP path, overwriting the stale ones. This would be safe because the per-model TFTP store is a single shared copy for that board model (kernel+initrd+DTB have to be in lockstep with the rootfs's /lib/modules/). Note the asymmetry: rb5009's TFTP is per-model, but the NFS rootfs is per-host — so if you took this path, you'd need to ensure all hosts in a model group apt-upgrade in lockstep, or accept that "first one wins" the TFTP slot and the others are running on stale modules.

Path 2 is the path of least surprise: the collection treats the .img.xz as the kernel source of truth, and apt is for userland packages only.

7. The collision question: does apt upgrade overwrite a locally-built kernel?

Yes. The locally-built deb and the upstream deb have the same Package: name. dpkg only sees a version-string. If apt.armbian.com's version compares higher, the locally-built kernel is removed and replaced.

If you applied kernel userpatches at build time (custom drivers, out-of-tree backports, CONFIG flips beyond what menuconfig saved), treat apt upgrade as destructive of those patches. Either hold the package (next section) or accept that the rebuild cadence has to keep up with apt.armbian.com's cadence.

8. armbian-config's "freeze upgrades" switch

Armbian ships a supported pin for the kernel + U-Boot + DTB packages. From the Armbian user guide:

"Enable Armbian kernel/firmware upgrades / Disable Armbian kernel upgrades"

Internally this is just apt-mark hold against the relevant package names — linux-image-${BRANCH}-${LINUXFAMILY}, linux-dtb-${BRANCH}-${LINUXFAMILY}, linux-u-boot-${BRANCH}-${BOARD}, and friends. You can do the same thing by hand:

Manual pin equivalent · run on the board
# Pin everything Armbian-provided to the currently-installed version.
sudo apt-mark hold \
    linux-image-current-rk35xx \
    linux-dtb-current-rk35xx \
    linux-headers-current-rk35xx \
    linux-u-boot-current-rock-5b \
    armbian-bsp-cli-rock-5b

# Or, only pin U-Boot (this collection's actual concern):
sudo apt-mark hold linux-u-boot-current-rock-5b
  • Holds survive reboots. They do NOT survive a rootfs reflash from a freshly-built .img.xz — you'd be installing a new rootfs, so its hold state starts empty.
  • Verify with apt-mark showhold.
  • Holds block upgrades, not security advisories. You'll see the held packages listed in apt list --upgradable.

9. Multi-board · multi-tree: keeping kernels current at scale

Here's where it gets practically important. Three axes interact:

  • Board (e.g. orange-pi-5-pro, rock-5b). One .img.xz per board model.
  • Branch (current, edge, …). One kernel tree per branch. Two boards on different branches are on different upstream cadences.
  • Family (rk35xx for both rk3588 boards in this collection). Two boards in the same family share the kernel deb name (linux-image-${BRANCH}-${LINUXFAMILY}) — but not the U-Boot deb (which is per-board).
BoardBRANCHLINUXFAMILYKernel debU-Boot deb
orange-pi-5-pro current rk35xx linux-image-current-rk35xx linux-u-boot-current-orangepi5-pro
rock-5b edge rk35xx linux-image-edge-rk35xx linux-u-boot-edge-rock-5b

Each cell in that kernel deb column is an independent apt cadence on apt.armbian.com. Maintaining "kernels current" across both boards means tracking both: linux-image-current-rk35xx publishes when Armbian's CI rolls forward the current branch's LTS kernel; the edge variant rolls more often, against mainline tip.

Three practical recipes

Recipe A: trust apt for kernels (SD-boot boards only), rebuild on schedule for the rest.

For boards running off SD/eMMC, let apt upgrade handle kernel/DTB packages — they have no local customisations in this collection, so they're safe to track upstream. Pin linux-u-boot-* so U-Boot stays on your custom PXE-first build. Re-run playbooks/build_image.yml on a slower cadence (quarterly? on armbian/build trunk bumps?) to refresh both the kernel and the U-Boot binaries in the .img.xz baseline.

Do not use this recipe on netbooted boards. §6.1 explains why: apt only touches the NFS rootfs's /boot/ and /lib/modules/, but a netbooted kernel comes from rb5009's TFTP. Letting apt advance the in-rootfs kernel while the TFTP-served one stays pinned creates a module-version mismatch on next reboot.

Recipe A wiring — SD-boot boards · per-board, run once
# On the running board (post-bootstrap):
sudo apt-mark hold linux-u-boot-$(cat /etc/lsb-release | grep BOARD_BRANCH | cut -d= -f2)-$(armbian-board-name)
# Or hardcode the names you know:
sudo apt-mark hold linux-u-boot-current-orangepi5-pro
sudo apt-mark hold linux-u-boot-edge-rock-5b

# Then a normal apt upgrade is safe:
sudo apt update && sudo apt upgrade -y
  • This recipe trades "kernel patches stay yours" (we don't apply any) for "kernel currency happens automatically." Good fit when you have a homelab fleet of SD/eMMC-booting boards and no per-board kernel modifications.
  • If U-Boot changes ARE needed (security CVE in a U-Boot subsystem you use), you have to rebuild from this collection's pipeline — apt won't help you because the package is held.
Recipe A wiring — netbooted boards · per-board, run once
# On a netbooted board, hold the kernel + DTB + headers ALSO, so apt
# doesn't desync the in-rootfs /lib/modules/ from the TFTP-served vmlinuz:
sudo apt-mark hold \
    linux-image-current-rk35xx \
    linux-dtb-current-rk35xx \
    linux-headers-current-rk35xx \
    linux-u-boot-current-orangepi5-pro

# After this, apt upgrade is safe but only updates userland.
# Kernel currency is driven by build_image.yml + stage_netboot_assets.yml.
sudo apt update && sudo apt upgrade -y
  • The kernel/DTB packages have to be held with the same ${BRANCH}-${LINUXFAMILY} suffix the board is running. Get it from dpkg -l 'linux-image-*-rk35xx' on the board.
  • This collection does not wire holds in any playbook today — it's operator state, not part of bootstrap_armbian.yml. A small role using ansible.builtin.dpkg_selections would be the right home if/when the fleet grows.
Recipe B: full pin, full rebuild.

Pin everything Armbian-supplied. Treat the .img.xz from playbooks/build_image.yml as the authoritative kernel + U-Boot baseline; refresh boards by reflashing (or by rebooting netbooted boards onto a re-staged rootfs) on whatever cadence suits you.

Most appropriate when you've got kernel userpatches (not the case in this collection today) or when you need reproducibility across the fleet more than you need upstream currency.

Recipe C: bump armbian_build_ref.

This collection pins armbian/build to a specific trunk tag in roles/armbian_build/defaults/main.yml (armbian_build_ref: "v26.2.0-trunk.844"). Bumping that pin and re-running playbooks/build_image.yml picks up every kernel patch and KERNELBRANCH bump that Armbian merged in the interim — for every board, on every branch, in a single deliberate step. The armbian_build role's manifest skip-build logic short-circuits rebuilds when nothing relevant changed, so this is cheap on a re-run.

10. What this collection actually does today

Here's the calibrated answer to "do I need to worry about apt overwriting my custom kernel?" for this repo specifically, as of main:

  • The collection applies zero kernel userpatches. The build_userpatches_common entries in playbooks/build_image.yml target U-Boot only (BOOT_TARGETS ordering, CONFIG_PCI_INIT_R for rk3588 PCIe init, the rock-5b v2026.04 BOOTBRANCH pin).
  • So at the artifact level, kernel deb upgrades from apt.armbian.com are byte-for-byte equivalent to a fresh local rebuild against the matching Armbian tag — only faster, and without burning builder host time.
  • U-Boot deb upgrades from apt.armbian.com would silently replace our PXE-first build with Armbian's stock PXE-at-position-6 build. On boards that still run U-Boot from SD (most), this only matters if you later run armbian-install or a SPI flash update tool — apt itself doesn't flash U-Boot. On boards whose U-Boot lives in SPI (rock-5b on edge, which already had Approach B applied via playbooks/persist_uboot_env.yml), the SPI binary isn't touched by apt at all; only the SD payload could drift.
  • On netbooted boards the artifact-equivalence above does not translate into runtime safety: per §6.1, the kernel apt upgrades inside the NFS rootfs is not the kernel U-Boot loads from rb5009. So even though the kernel deb itself is safe to track upstream, advancing it on a netbooted board without re-staging TFTP desyncs /lib/modules/ from the running kernel.
  • The minimum hold list therefore depends on boot mode:
    • SD-boot board: hold only linux-u-boot-${BRANCH}-${BOARD}. Kernel/DTB packages can be left to apt's normal upgrade cadence (the same files that get updated in /boot/ are the ones the next SD-boot loads).
    • Netboot board: hold linux-image-${BRANCH}-${LINUXFAMILY}, linux-dtb-${BRANCH}-${LINUXFAMILY}, linux-headers-${BRANCH}-${LINUXFAMILY}, and linux-u-boot-${BRANCH}-${BOARD}. Kernel currency is then driven entirely by build_image.yml + stage_netboot_assets.yml.

The exact hold per board, given today's vars/boards.yml + playbooks/build_image.yml:

Inventory hostBoot modeHold command
orange-pi-5-pro-NN SD-boot apt-mark hold linux-u-boot-current-orangepi5-pro
orange-pi-5-pro-NN Netboot apt-mark hold linux-image-current-rk35xx linux-dtb-current-rk35xx linux-headers-current-rk35xx linux-u-boot-current-orangepi5-pro
rock-5b-NN SD-boot apt-mark hold linux-u-boot-edge-rock-5b
rock-5b-NN Netboot apt-mark hold linux-image-edge-rk35xx linux-dtb-edge-rk35xx linux-headers-edge-rk35xx linux-u-boot-edge-rock-5b

This isn't wired into any playbook in the collection today — it's a documentation footnote, not a role. If/when the fleet grows past hand-rolled apt operations, a small role wrapping ansible.builtin.dpkg_selections would belong next to bootstrap_armbian.

11. Gotchas

Same family ⇒ same kernel deb name ⇒ shared apt cadence. Two boards in rk35xx on the same BRANCH consume literally the same kernel package from apt.armbian.com. A regression in Armbian's CI for one board's kernel hits every board sharing that family + branch combo simultaneously. This is by design (kernels are family-wide), but it means "stagger kernel rollouts" is not a property apt gives you — you'd have to pin some hosts and unpin them later.
linux-headers-… can be absent on some kernel versions. The packaging code in kernel-debs.sh has a "Skipping linux-headers package for ${KERNEL_MAJOR_MINOR}" branch. If a build step depends on headers being present, gate on ls /var/lib/armbian_build/output/debs/linux-headers-* 2>/dev/null.
The KERNEL_CONFIGURE=no default skips menuconfig but not the build. The role's armbian_build_compile_args.KERNEL_CONFIGURE: "no" (roles/armbian_build/defaults/main.yml) only suppresses the interactive prompt — it does not skip kernel compilation. There is no documented switch that swaps the in-build kernel for a pre-fetched .deb from apt.armbian.com; if you want apt's version in the image, you'd have to run apt upgrade in a customize-image.sh hook against the rootfs.
Nightly vs stable apt repo. distro-agnostic.sh swaps apt.armbian.com → beta.armbian.com when IMAGE_TYPE=nightly. The v26.2.0-trunk.844 builds this collection consumes are NOT nightly (BETA is unset), so the produced images point at stable apt.armbian.com. If you ever flip an image to nightly, the upgrade cadence becomes significantly more aggressive.
